# 回答帳リプレイによる詰碁誤答パターンの検証基盤（2026-08-09）

## 1. 目的

詰碁モードの誤答を減らすため、**回答帳に記録済みの全問を「回答帳なし」で解かせ直し、
記録手順と突き合わせて誤答パターンを統計的に取り出す**。

これまでの誤答調査は「実戦で誤答が出る → その1問を case A〜AG として個別に解剖する」形で、
**その誤答が全体の何割を占めるのか**が分からなかった。個別ケースの対策（追記1〜39）は
どれも実測に基づいているが、優先順位づけの根拠が無い。この基盤はそこを埋める。

## 2. なぜ回答帳だけで再現できるのか

回答帳の entry は次を持つ:

```json
{"size": 13, "to_play": "B",
 "canonical_black": ["A1", ...], "canonical_white": [...],
 "lines": [["D1","B1","A2","C1","B3"]], "created": "2026-08-04"}
```

`canonical_*` は盤の8対称のうち辞書順最小の向き（標準形）に変換した石の配置で、
`lines` も**同じ向き**（記録時に同じ `t0` で変換している）。したがって

- 石の配置 → 認識グリッド（`grid[i][j]`、i は上からの行、点は `(x, size-1-i)`）
- 正解手順 → そのグリッド上の GTP 列（黒から交互）

を無損失で復元できる。**実測: 464 entry すべてで grid 復元の往復（`grid_to_stones` →
`canonicalize`）が保存キーに一致**。

**回答帳には誤答した問題だけでなく、解析が長かったので次から即答させたい問題（＝正解した問題）も
入っている**。したがってこのコーパスは正解・誤答の両方を含み、正解／誤答の別は
「回答帳なしで解かせ直して記録手順と一致したか」で**この基盤自身が決める**。

回答帳に無いのはキャプチャ設定（どのホットキーで撮ったか＝`black_to_attack` / `frameless`、
その回の `ko` / `margin`）だけで、これらは**保護されたログ**（`keep_current_log`。回答帳 spec
追記3）から取れる。既存 entry は既定設定（F4＝自動推定・枠あり）で回す。

## 3. 本番コードを写経しない

出題盤の決定（ソルバゲート → 枠張り → 枠なし）は `KaTrainGui._do_tsumego_capture_apply` と
`_choose_tsumego_frame`（約215行）にあり、GUI クラスのメソッドになっている。これを
ハーネス側に書き写すと本番と乖離し、**「別物を測る」**危険がある（この失敗はこの
コードベースで繰り返し起きている＝CLAUDE.md の case AA/AD/AF）。

代わりに **`katrain.__main__` を非表示ウィンドウで import し、実メソッドを軽量スタブに
束縛して呼ぶ**:

```python
_KivyConfig.set("graphics", "window_state", "hidden")   # import 前に立てる
import katrain.__main__ as gui_main
for name in BORROWED:                                    # _choose_tsumego_frame 等9個
    setattr(ReplayHost, name, getattr(gui_main.KaTrainGui, name))
```

束縛でよいのは、関数の `__globals__` が `katrain.__main__` のままなので `OUTPUT_INFO` /
`KaTrainSGF` / `region_analysis_extra_settings` 等のモジュールグローバルが解決されるため。
枠張り経路が `self` に要求するのは **`log` / `config` / `engine` の3つだけ**で、
Clock・controls・board_gui・play_mode は1つも出てこない（実測: 909-1277行の `self.` 全出力）。

**`KIVY_WINDOW=mock` は使えない** — Kivy 2.3.1 に mock provider は無く、指定すると
「Window provider なし」で**無言の sys.exit(1)** になる。

## 4. 手順

1. entry → grid（canonical 向き）
2. `choose_board`：`_do_tsumego_capture_apply` の盤決定部だけをなぞる
   （`extract_problem` → 規模ゲート → `problem_is_hopeless` → `_choose_tsumego_frame`
   → `_tsumego_frameless_board`）。重い部分は全部本番メソッド
3. `game.tsumego_book_entry` / `_transforms` を**設定しない**＝回答帳の再生は完全に無効
   （`tsumego_book_next_move` は `getattr` でこの2つしか見ない）
4. 記録手順の白の応手を打ち込みながら、各黒番で
   `_apply_tsumego_region` と同じ2段解析（全盤fast → リージョン限定 + ownership）を撃ち、
   実 `generate_move()` を呼ぶ
5. 記録手と一致しなければそこで打ち切り

### エンジンのウォームアップは必須

`_tsumego_frame_solver_reading_finish` の待ちは **30秒固定**（`_tsumego_frame_trial_wait`
の既定 timeout）なのに、TensorRT の初回モデルロードは**実測 36.3 秒**かかる。冷えたまま
1件目が枠経路だと枠試算が `root=解析失敗` になり、しかも**解析が取れなかった枠は
「壊れていない」扱いで素通りする**（`frame_solver_verdict` が own=None で `(False,None,None)`）。
＝検証されていない枠が黙って採用され、**誤った成功に見える**。

対策は2つ: (a) 本編前に `warm_up_engine` でモデルをロードさせる、(b) 枠試算ログに
`解析失敗` が出た回を `frame_read_failed` として結果に残す。

## 5. 記録する診断

**全手番**で（不一致だけだと「誤答に多い経路」なのか「もともと多い経路」なのか分からない）:

| フィールド | 意味 |
|---|---|
| `want` / `chosen` | 記録手 / AI が打った手（GTP） |
| `want_in_pool` / `want_visit_rank` / `want_prior_rank` | **仮説1**: 正解手は候補に居たか、どの順位か |
| `want_passes_min_visits` | `min_visits`(10) の足切りを通ったか |
| `want_cand` / `chosen_cand` | その候補の visits / prior / pointsLost / winrate |
| `decider` | 最終決定を出した機構（gain / class_promotion / ko_escape / declass / rescue / …） |
| `root_already_succeeded` | root 時点で「既に成功」と読まれていたか |
| `role_logged` | 手番側の役割（attack / defend / 不明） |
| `strategy_log` | 不一致手番のみ、戦略の判定ログ |

**キー名を `want` / `chosen` にしてはいけない**（診断辞書の `**diag` が呼び出し側の GTP
文字列を上書きし、候補プールに無い手＝ソルバ経路の着手などで打った手そのものが None に
なって失われる。実際に1度踏んだ）。

## 6. 第2パス（`answer_book_verify.py`）— 不一致は誤答とは限らない

詰碁には別解があり、回答帳はユーザーがアプリで見た1本しか持たない。不一致手番ごとに
「記録手を打った後」と「AI の手を打った後」の**役割石の同深さ ownership**
（`_region_child_verdict` + `tsumego_success_ownership`＝本番の格下げ確認・脱出採否が
使うのと同じ尺度・同じ `TSUMEGO_VERDICT_UNTIL_DEPTH`(12)）を測って分類する:

| クラス | 条件 | 意味 |
|---|---|---|
| `alternative` | own(chosen) >= `ko_success_ownership`(0.5) | AI の手も成立＝別解 |
| `true_miss` | own(want) >= 0.5 かつ own(chosen) < 0.5 | **本物の誤答** |
| `undecided` | どちらも < 0.5 | 答えがコウ／セキ等で ply1 では決着しない |

同時に `delta = own(want) - own(chosen)` が出る。これはユーザーの体感
「正解手は相手の死judgment を維持または強める／誤答手は薄れる」の**そのままの数値検定**に
なっている。

**別解も実用上は失敗**（アプリの解答樹に無ければ受け付けられず、ユーザーが記録する羽目に
なる）だが、対処は別物 — 本線への寄せ方（タイブレーク）の問題であって死活の読み違いではない。

## 7. この計測の限界（結論を読むときに必ず考慮する）

- **canonical 向きで測っている**（元のキャプチャの向きではない）。KataGo は厳密には
  回転不変ではないので、元の対局と1手単位で一致する保証はない。
- **キャプチャ設定は既定**（F4＝役割自動推定・枠あり）。役割指定ホットキーや枠なしで
  撮った問題は、元と違う枠で出題されている可能性がある。
- **1run のトリアージ**。手選択は run 間で 10〜30% 変動する（`e2e_suite.py` が3run回すのは
  このため）。不一致ケースは**別途3runで確認**して、決定的な誤答とフレークを分ける。
- **ソルバ経路の永続キャッシュ**（`~/.katrain/tsumego_cache/`）は本番と共有している。
  過去の誤答が焼き付いていればそれも再現される（case AB）。これは仕様どおりだが、
  「現在のコードの実力」を測りたいときは `solver_cache=false` で A/B すること。

## 8. 使い方

```bash
# スイープ（全 >=5手 の記録手順・約30〜50分）
python docs/superpowers/specs/calibration-data/tsumego/answer_book_replay.py --min-line 5 --resume

# 不一致の第2パス
python docs/superpowers/specs/calibration-data/tsumego/answer_book_verify.py --resume

# 集計（仮説1・仮説2の検定）
python docs/superpowers/specs/calibration-data/tsumego/answer_book_summary.py
```

`--resume` は出力 JSONL に既にある `(key, line_index)` を飛ばすので、中断・再開できる。
`--keys` で個別ケースだけ、`--route frame|solver` で経路を絞れる（静的ゲートでの事前フィルタ）。

## 9. 実測結果（2026-08-09 / 回答帳 464 entry・>=5手の 420 手順・1373 判断・1run）

### 9.1 全体

- **1手番あたり 86.8% 一致**（1192/1373）
- **手順まるごと一致 56.9%**（239/420。3〜4手を連続で当てる必要がある）

### 9.2 仮説1「有力手が候補に出てこない」→ **形を変えて実在**

不一致 181 手番で `want_in_pool` は **181/181 = 100%**。「候補リストに出てこない」は完全に否定。

> **訂正**: この指標は**全1373判断でも 100%** で、分散ゼロの飽和指標＝検定になっていない。
> `candidate_moves` はリージョン解析の反映時にリージョン外候補が除去されるので、リージョン内に
> ある記録手は構造的に必ず入る。仮説1の実質的な検定は下記の `want_passes_min_visits`
> （**全1373判断中 False は15件**、うち10件が不一致）と visits 順位分布のほうである。
正解手の visits 順位は 0位が63・1〜2位が95＝**87% が上位3手**に入っている。

ただし **`min_visits`(10) で落とされた不一致が10件**あり、中身が case O の指紋そのもの:

```
58fd6879  want=B11  prior=0.222  visits=7   pointsLost=+10.29
348063b3  want=E2   prior=0.277  visits=8   pointsLost=+32.02
```

policy は高く評価しているのに value が壊れて visits が付かず、目数が壊滅的に見える。
`ko_escape_candidates`（root policy を測り直す機構）は既にあるが**コウ一色のときしか
発火しない**。「policy 上位手が visits に飢えている」ときにも走らせるのが素直な拡張。

### 9.3 仮説2「白死の判定が薄れる」→ **corpus 全体では非支持・真の誤答では明確に支持**

`delta = own(記録手) − own(AIの手)` は中央値 **+0.001**・正の割合 55.2% ＝コイン投げ。

ただし後述の **true_miss 13件では記録手 +0.59〜+0.94 / AIの手 −0.92〜+0.44** と明確に分離する。
体感は正しく、**発生源が ownership 選択則ではなくソルバ経路だった**。

### 9.4 不一致181件の分類（第2パス）

| クラス | 件数 | frame | frameless | solver |
|---|---|---|---|---|
| alternative（AIの手も成立） | 97 (53.6%) | 89 (69%) | 0 (0%) | 8 (24%) |
| undecided（ply1 で決着しない） | 71 (39.2%) | 40 (31%) | 18 (100%) | 13 (38%) |
| **true_miss（本物の誤答）** | **13 (7.2%)** | **0** | **0** | **13 (38%)** |

**`alternative` は経路で解釈が変わる**。枠は「攻め方が成功したら5目勝ち」に調整するので
枠あり盤では相手石が広く死と読まれ、どの手でも +0.98 に張り付く（root既解決が全判断の50%）。
frame 経路の `alternative` は「別解と確認できた」ではなく**「枠あり盤ではこの尺度で判別できない」**
と読むこと（frameless が 0% alternative・100% undecided なのが裏返し）。

### 9.5 **ply1 ownership で判別できる誤答13件は全件がソルバ経路**

> **訂正（2026-08-10・独立レビューによる反証）**: 当初これを「本物の誤答は全件がソルバ経路」と
> 書いたが、それは**分類器がソルバ盤でしか判別能力を持たない**ことの言い換えだった。
> 経路ごとの判別能力の実測:
>
> | 経路 | own_want の最大 | 両方成立 | 両方不成立 | chosen だけ成立 |
> |---|---|---|---|---|
> | frame (129) | +1.00 | 79 | 40 | **10** |
> | frameless (18) | **−0.31** | 0 | 18 | 0 |
> | solver (34) | +0.94 | 7 | 13 | 1 |
>
> frameless は**記録された正解手すら閾値 0.5 に届かない**ので `true_miss`（want>=0.5 かつ
> chosen<0.5）は数学的に発生不能。frame は飽和して両者が一緒に動く（|delta|<0.05 が 77/129）。
> したがって **frame / frameless に誤答が無いことの証拠にはならない**。
> 正しい言い方: 「ply1 の役割石 ownership で判別可能な誤答は全件ソルバ経路だった」。

```
22bfefd9  記録手 D2 (+0.93/子) → ソルバ D1 (-0.85/子)   visits順位1 / policy順位3
3eb79f02  記録手 D2 (+0.94/子) → ソルバ C3 (-0.91/子)   visits順位0 / policy順位1
5c45fb84  記録手 G2 (+0.82/子) → ソルバ E7 (-0.92/子)   visits順位1 / policy順位1
19c3101b  記録手 D3 (+0.83/子) → ソルバ C2 (-0.88/子)   visits順位0 / policy順位1
```

**13件すべてで記録手は KataGo の visits 順位0か1**＝通常解析なら見えていた手を、
「厳密解」であるはずのソルバが負ける手で上書きしている。

追試:

| 条件 | 結果 |
|---|---|
| 同条件で再走 | **13/13 が不一致で再現**（フレークではない） |
| `solver_cache=false` | **13/13 変わらず**（case AB のキャッシュ汚染ではない） |
| `solver_enabled=false`（KataGo経路で出題） | **10/13 が手順まるごと正解に転じる** |

原因は**抽出が画面の詰碁と別問題になっている**（case AA/AC/AD/AE/AF 系）。
`problem_is_hopeless` は「解けないと証明できた抽出」しか弾かないので、
**「解けるが別問題」は素通りする**。

### 9.6 KataGo 本命から外すことの損得（最重要）

`chosen != top_by_visits[0]` を「外した判断」とし、`want_visit_rank == 0`（本命に従えば
一致した）を反実仮想に取る:

| | 件数 |
|---|---|
| 外した判断 | 176 / 1373（12.8%） |
| そのうち当たり | 92（52.3%） |
| 本命に従っていたら当たっていた | 63（35.8%） |
| **差引** | **+29 手（外すのは全体としては得）** |

**機構別の損得**:

| decider | 外した判断 | 当たり | 本命が正解だった | どちらも外れ | 差引 |
|---|---|---|---|---|---|
| gain | 79 | 43 | 20 | 16 | **+23** |
| solver_or_book | 50 | 30 | 19 | 1 | **+11** |
| class_promotion | 19 | 10 | 7 | 2 | +3 |
| **ko_escape** | 22 | 7 | **13** | 2 | **−6** |
| unknown | 6 | 2 | 4 | 0 | −2 |

**`ko_escape`（コウ脱出）だけが純損**。発火22回で、本命に従っていれば13回当たったのに
自分は7回しか当てていない。機構ごとの一致率でも突出して低い（31.8% / ベースライン 86.8%）。

### 9.7 ~~手数別 — 初手が突出して弱い~~ → **生存者バイアスにより撤回**

> **訂正（2026-08-10）**: ハーネスは**最初の不一致で打ち切る**ので、depth d の判断は
> depth 0..d-2 を全部当てた手順にしか存在しない。実データが恒等式になっている:
> **depth0 n=420 match=321 → depth2 n=321 match=292 → depth4 n=292**（母数が前の depth の
> 一致数そのもの）。したがって「初手 76.4% / 以降 91%」は**条件付き確率の比較**であり、
> 「初手が弱い」の根拠にならない。§9.9 の優先順位からこの項目は外した。
> 非条件付きの depth 別一致率を測るには、不一致後も記録手を打って続行するモードが要る。

（以下は打ち切りありの生データ。上の但し書きの前提で読むこと）

| 深さ | 判断数 | 一致率 |
|---|---|---|
| 初手 | 420 | **76.4%** |
| 3手目 | 321 | 91.0% |
| 5手目 | 292 | 91.4% |
| 7手目以降 | 340 | 90〜95% |

誤答181件のうち **99件（55%）が初手**。詰碁は初手で決まり以降は一本道なので方向としては
自然だが、**改善の投資先は初手選択**だと数字で確定した。

### 9.8 差が出なかった軸（否定された仮説）

| 軸 | 一致率 |
|---|---|
| route | frame 86.7% / frameless 85.9% / solver 87.8% |
| 役割 | 攻め方 87.3% / 守り方 84.7% / 不明 86.9% |
| root既解決 | False 85.0% / **True 88.6%**（むしろ既解決のほうが高い） |

**`root_already_succeeded` は誤答と無関係**。調査中に一度「誤答の45%が既解決」として原因候補に
挙げたが、それは**誤答側しか測っていない数字**で、正解側も同じ割合だった。
**比較対象のない割合を原因の証拠にしない**。

### 9.9 次に手を入れるならどこか（優先順）

1. ~~**ソルバの答えを KataGo と突き合わせる**~~ → **実装済み（下記 §10）**。
2. **`ko_escape` の採否を締める**（唯一の純損機構・net −6）。**ただし n=22 で有意ではなく
   （discordant 7 vs 13 の McNemar は p≈0.26）、`decider` ラベル自体が不完全**
   （`declass` / `rescue` / `verified` / `tie_band` は `Final decision:` 行の書式上一度も付かず、
   それらの判断が `gain` に混ざっている）。機構別の損得を結論にする前にラベル付けを直すこと。
3. **`min_visits` に飢えた policy 上位手の救済**（case O 型・10件）。
4. ~~初手に投資する~~ → 生存者バイアスのため撤回（§9.7 の訂正）。

## 10. 対処1の実装と検証（2026-08-09）

`TsumegoSolverStrategy._solver_answer_rejected`（`ai.py`）+ 設定 `solver_cross_check`（既定 true）。
設計の詳細は `.claude/rules/ai-parameters.md` の同名の行を参照。

### 10.1 判定と安全側の倒し方

- 尺度は**役割石の同深さ ownership の絶対値**（`tsumego_success_ownership` >=
  `ko_success_ownership`、`gain_verify_visits`=800）。
- **2段構え**: 第1段はソルバ手だけ測り、成立していれば解析1本で抜ける。成立していない
  手番だけ第2段で KataGo の visits 上位2手を測る。
- **却下には「対抗馬が実際に成立していること」を要求する**。答えがコウ/セキで ply1 に
  成否が出ない局面では両方 <閾値 になり却下しない＝**ソルバの答えを残す**側に倒れる
  （`tsumego_declass_confirmed` と同じ非対称性）。実測でこの安全弁が働いた例:

  ```
  ソルバ手 E7 は -0.92/子 で成立していませんが、本命 D2, E1 も成立していないため
  ソルバの答えを残します
  ```

- **却下は sticky**（`game.tsumego_solver_session = False`）。却下の意味は「抽出が
  別問題」で、それは手ではなく**問題**の性質だから、以降その問題ではソルバを使わない。

### 10.2 「ソルバ手が本命と違うときだけ測る」では足りない

最初の実装は `ranked[0] == solver_gtp` で早期 return していたが、真の誤答13件のうち
**3件（e6794025 / 22bfefd9 / bcccd4ca）はソルバ手が KataGo の visits 最多手そのもの**で、
それでも両方外れており記録手は visits 2位に居た。トリガーを「常にソルバ手の成立を確かめる」
に変えた（コストは第1段の解析1本）。

### 10.3 A/B（ソルバ経路 90 手順）

| | correct | 中央値 | p90 | 最大 | >20s | 合計 |
|---|---|---|---|---|---|---|
| A 修正前 | 56 (62.2%) | 7.1s | 24.3s | 79.0s | 12件 | 986s |
| B 突き合わせ（役割 None） | 64 (71.1%) | 7.1s | 11.4s | 67.7s | 2件 | 758s |
| C B + 役割=`problem_type` | **66 (73.3%)** | 7.2s | 11.3s | 67.7s | 2件 | 758s |
| **D C + `solver_time_limit_ms`=5000** | **65 (72.2%)** | 6.9s | 10.8s | **17.4s** | **0件** | **637s** |

**採用は D**。ユーザー要件「キャプチャから正解手順の最終手まで1問20秒以内」を90手順すべてで
満たす（最大 17.4 秒）。C→D の −1 は下記のノイズ水準の内側。

**ノイズ水準の実測**: 同一設定の再走で verdict が **3/90（3.3%）変動**する。個々の1件の
増減はこの幅に埋もれるので、判断は必ず総数で行うこと。

遷移: correct→correct 55 / mismatch→correct **9** / mismatch→mismatch 25 /
correct→mismatch **1**。退行1件（`aaa53c31`）は**3run 中2回は正解**＝run 間変動で、
系統的な退行ではない。真の誤答13件のうち **9件が回復**。

**所要時間は合計 986s → 755s と速くなる**。sticky 却下が「毎手ソルバを解き直して
30 秒タイムアウトを踏む」経路を消すため。

### 10.4 ハーネス側の欠陥（計測を疑うべきだった例）

修正直後の計測で 1問 100.8 秒・`31.0秒`(= `solver_time_limit_ms` 30s のタイムアウト)が
3連発した。原因は**実装ではなくハーネス**で、判断ごとに game を作り直すため
sticky 却下が次の手番に伝わっていなかった（GUI では game が手番をまたいで生きるので伝わる）。
`build_game(..., solver_disabled)` で GUI と同じ挙動に直した。

**「遅い」と出たら実装より先に計測系が本番の状態を再現しているかを疑うこと。**
