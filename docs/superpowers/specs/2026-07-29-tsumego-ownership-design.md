# 詰碁キャプチャ: ownership を目的関数にした着手選択（ai:tsumego）設計書

日付: 2026-07-29
ステータス: 承認済み

## 目的

詰碁キャプチャの黒番AIが「盤全体の目数が最良の手」ではなく「**対象石群の死活を最も自分に有利に動かす手**」を
選ぶようにする。詰碁の正解判定は対象石群の死活で決まるのに、KataGo の目的関数は盤全体の目数であり、
この不一致が誤答の主因である。

## 背景: 目数ベースでは解けないことの実測

先行する2ブランチ（枠の配線バグ修正 `ee0376c`、枠なしモード `2049937`）で盤面とリージョンの
問題は解消したが、誤答は残った。原因は目的関数の不一致で、**盤面や枠をどう調整しても解けない**
構造的ジレンマとして現れる。

| ケース | 状態 | root scoreLead / 勝率 | 1位 | 正解手 |
|---|---|---|---|---|
| case B | 枠なし | +37.72 / **1.000** | A5 | B4 +1.84 |
| case B | 枠なし + komi 44.5 | +0.98 / 0.712 | A5 | B4 +1.23 |
| case C | 枠なし | −53.29 / **0.000** | J1 | H1 +2.24 |
| case C | 枠なし + komi −46.5 | +0.34 / 0.464 | **G7（空き地）** | H1 +4.22 (2 visits) |

- **飽和させる**と詰碁の成否が勝敗に影響せず、KataGo は死活を読む動機を持たない
- **バランスを取る**と今度はリージョン内の空き地の手が価値を持つ

枠はこの両方を「盤を埋める＋バランスを取る」で同時に解こうとしていた設計であり、
枠なし＋リージョンだけではジレンマを解けない。**目的関数を変えるのが本筋**。

## ownership が信号になることの実測

候補手ごとの ownership（`includeMovesOwnership`）で、目数が取り逃す差が出る。

### case C（正解 H1 はコウ、AI は J1 を選び黒が死んだ）

```
move   ptLost  visits   B_own（黒石群のownership平均）
J1     +1.85     897   -0.515   ← AIの選択
H1     +2.03     882   -0.129   ← 正解
```

目数では J1 が上、**ownership では H1 が明確に上**。しかも H1 の値は 0 付近で、
**コウ＝どちらのものとも決まっていない状態が中間値として現れる**。

### case B（正解 B4、AI は A5 を選び白が生きた）

連ごとに見ると、攻撃対象の白 G7 は ROOT / A5 / B4 いずれも −0.76 で動かない。
しかし**全連の変化を合計すると B4 が勝つ**（サイズ加重・黒視点）:

```
連                ROOT    A5      B4      B4の寄与
G0(B,1) B8       +0.95   +0.95   +0.92    -0.03
G3(B,1) D4       +0.44   +0.44   +0.01    -0.43
G4(B,1) B3       -0.61   -0.61   -0.12    +0.49
G5(B,1) A2       -0.65   -0.65   -0.43    +0.22
G6(B,1) B1       -0.70   -0.70   -0.54    +0.16
G7(W,2) B5 C5    -0.76   -0.76   -0.76     0
G8(W,6)          -0.77   -0.78   -0.66    +0.66
G9(W,1) F1       -0.42   -0.42   -0.39    +0.03
                        合計:   A5 = -0.06   B4 = +1.10
```

なお同じ局面で D5 は gain +3.49 と最大だが pointsLost が +4.87 と大きい。
**目数のガードが必要**なことを示している。

## アプローチ

採用: **目数ガードで大損の手を弾き、残りを ownership gain で順位付ける**。

不採用:

- **対象石群を事前に同定して、その連だけを見る** — case B の実測では ROOT で最も
  中間値なのは無関係な単独の黒石 D4(+0.44) で、攻撃対象の白 G7(−0.76) ではなかった。
  同定を誤ると完全に外れるため、全連の変化を合計するほうが頑健
- **ownership gain だけで選ぶ（目数ガードなし）** — case B で 4.87目損の D5 が選ばれる
- **目数と ownership の加重和** — 重みの意味づけが恣意的で調整が難しい。
  ガード（ハード制約）＋ gain（目的関数）のほうが各パラメータの役割が明確

## 設計

### 1. 着手選択

リージョン限定解析が完了した候補手 `cn.candidate_moves` に対して:

```
1. 目数ガード
   best = min(pointsLost)
   候補 = { m | m.pointsLost <= best + max_points_behind }   （既定 max_points_behind = 2.0）

2. ownership gain（手番側から見て有利な向きを正とする）
   sign = +1 if 手番 == B else -1
   gain(m) = Σ_{盤上の全石 s} sign × ( own_after(m, s) − own_root(s) )

3. gain 最大の手を選ぶ。同点は pointsLost が小さい方
```

石ごとに合計するので、大きい連の死活ほど重く効く（連の平均ではなくサイズ加重）。
空き地の手はどの石の ownership も動かさないので gain ≈ 0 となり自動的に沈む。

実測での検算:

| ケース | 目数ガード通過 | gain 最大 | 結果 |
|---|---|---|---|
| case C | J1(+1.85), H1(+2.03), L1(+2.24), K1(+3.13) 等 | **H1 +1.61**（J1 は −1.59） | 正解 |
| case B | A5(−0.08), B4(+1.70)。D5(+4.87) は除外 | **B4 +1.10**（A5 は −0.06） | 正解 |

### 2. ownership データの取得

`engine.py:457-458` は `includeOwnership` / `includeMovesOwnership` を
`self.config["_enable_ownership"]` で制御している。ユーザーのローカル設定では
現在 `false` なので **`true` にする必要がある**（パッケージ側 `katrain/config.json` は既に `true`）。

候補手ごとの ownership は `cn.analysis["moves"][gtp]["ownership"]` に入る。
`analysis_dumps` が per-move ownership を捨てるのは SGF へ保存する時だけで、
メモリ上の解析結果には残る（`game_node.py:26-28`）。

ROOT の ownership は `cn.analysis["ownership"]`（= `cn.ownership`）。

配列→盤座標の変換は既存の `var_to_grid(array, (size_x, size_y))` を使う。
戻り値は `grid[y][x]` で y は下origin。`Move.coords` が `(x, y)` なので `grid[y][x]` で引ける。

### 3. 実装場所

`ai.py` に既存の `OwnershipBaseStrategy` 系（`AI_SIMPLE_OWNERSHIP` / `AI_SETTLE_STONES`）が
あり、per-move ownership を使う前例になっている。同じパターンで新戦略を追加する:

- `constants.py`: `AI_TSUMEGO = "ai:tsumego"` を追加。どのリスト（`AI_STRATEGIES_ENGINE` /
  `AI_STRATEGIES_RECOMMENDED_ORDER` / `AI_STRENGTH` 等）に登録するかは、既存の
  `AI_SIMPLE_OWNERSHIP` / `AI_SETTLE_STONES` の登録先に倣う（両者で登録先が異なるため、
  実装時に既存コードを確認して合わせる）。手順は `.claude/rules/ai-settings-gui.md` に従う
- `ai.py`: `@register_strategy(AI_TSUMEGO)` を付けた `TsumegoOwnershipStrategy` を追加
- `config.json`（パッケージ側とユーザーローカルの両方）: `ai/ai:tsumego` の設定に
  `max_points_behind` を置く
- `__main__.py`: キャプチャ適用時の黒番を `AI_DEFAULT` から `AI_TSUMEGO` に変更

### 4. フォールバック

ownership が取れない場合（`_enable_ownership` が false、古い KataGo 等）は
`candidate_moves[0]`（= 現行 `ai:default` と同じ挙動）にフォールバックし、
その旨を `OUTPUT_INFO` でログに出す。無言で劣化させない。

## 検証

### ユニットテスト

`ai.py` の戦略は Kivy 非依存で、`katrain_debug` のスタブ経由でテストできる。
ownership 配列を固定値で与えた偽の解析結果に対して:

- gain 計算が手番の符号を正しく扱う（黒番と白番で符号が反転する）
- 目数ガードが `best + max_points_behind` を超える手を除外する
  （case B の D5 相当: gain 最大だが pointsLost 超過 → 選ばれない）
- gain 同点時に pointsLost の小さい方が選ばれる
- ownership が無い場合に `candidate_moves[0]` へフォールバックする
- `var_to_grid` の座標変換が `Move.coords` と一致する（既知の石の ownership を引けること）

### 実機検証

case A / B / C を含む問題群で `ai:default` と比較する。判定は
「アプリが正解と判定したか」で行う（コウ・セキに持ち込む別解も正解）。

## 限界（既知・未解決）

- **`max_points_behind = 2.0` は case B / C の2ケースからの推定値**。問題群で調整が要る。
  小さすぎると正解手を弾き（case C の H1 は +2.03）、大きすぎると大損の手が入る（case B の D5 は +4.87）
- gain は全連の合計なので、詰碁と無関係な連が同時に動く局面では信号が希釈される
- **KataGo の読み自体が誤っている問題は直らない**。case B は gain では正解に転んだが、
  攻撃対象の白 G7 の ownership は動いておらず、KataGo はこの白を「どちらにせよ生きている」と
  読んでいる。正解に転んだのは黒の死に石が蘇る副次効果によるもので、保証ではない
- 飽和時（勝率0/1）は KataGo の探索自体が甘くなり ownership の推定精度も落ちる。
  komi によるバランス調整の併用は有効な可能性があるが、本設計には含めない（別途評価する）

## 追記（2026-07-29）: gain 飽和による誤答と ε 同着タイブレーク

実戦で誤答が出た（13路・左上・黒番、正解 C12 に対し AI は D12 を選択）。
キャプチャ経路と同じクエリ（region A–J×5–13 / 1800 visits / wideRootNoise 0 / ownership）で再現した結果:

- **root の時点で対象の白石が全て死に判定**（W:A11,B11 / C10,D10 / E12,E11 / D8 がいずれも +0.99〜+1.00、
  root は勝率 98.5%・+3.1目）。ownership に伸びしろが無く、正解手を打っても gain は動かない
- 目数ガードを通る上位3手（C12 / D12 / E13）の gain は **±0.03 のノイズ**しか出ない
  （本物の死活差は同局面の C13/C11 で −3.8〜−4.6 と桁が違う）
- 同一局面を繰り返すと gain の大小が run ごとに入れ替わり、**選択がコイン投げになる**
  （実測 4 run: C12 が 3回、D12 が 1回。実戦は D12 を引いた）
- 一方 pointsLost は毎 run 安定して C12 が 0.6目良い。旧実装は `(gain, -pointsLost)` の
  タプル比較なので、gain が浮動小数で完全一致しない限り pointsLost は評価されなかった

**設計前提の限界**: 「正解手は ownership を有利に動かす」は root が未決着のとき（case C のコウ≒0）
だけ成立する。KataGo が既に勝ちを読み切っている局面（＝解答の途中では普通に起きる）では
正解手も gain 0 で、信号が消える。

**対処**: `gain_epsilon`（既定 0.3）を追加し、best gain との差が ε 以内の手は同着として
pointsLost で決める。ノイズ実測 ≤0.03、case B / case C の実信号は 1.16 / 3.20 なので
両ケースの挙動は変わらない。設定は `config.json` の `ai/ai:tsumego`（ai:tsumego は GUI 非表示のため
`AI_OPTION_VALUES` への登録は不要）。

**検証**（fresh engine を毎回起動して trial）: 探索が C12 を見つけた 8 trial で
**修正後は 8/8 が C12**、旧実装なら 4/8 が E13/D12（ノイズ勝ち）だった。

**併発していた第2の要因: 探索の飢餓（対処済み）**。KataGo の探索自体が半数以上の trial で崩れ、
C12 に 12〜29 visits しか振らないまま「+14〜+21目損」と誤評価する。この状態はどの選択則でも
救えない。原因は `wideRootNoise = 0.0`（「深掘り・ノイズなし」という当初設計）で、root の探索が
1手に集中して正解手が visits を貰えないこと。各設定 8 trial（fresh engine 毎回起動）の実測:

| region クエリ設定 | 旧選択則での正解 | ε 修正後の正解 | 追加コスト |
|---|---|---|---|
| 1800 visits / wRN 0.0（旧既定） | 1/8 | 3/8 | — |
| **1800 visits / wRN 0.04（採用）** | 3/8 | **7/8** | ほぼ 0 |
| 6000 visits / wRN 0.0 | — | 6/8 | +5秒/手 |
| 6000 visits / wRN 0.04 | — | 7/8 | +5秒/手 |

visits 増は wRN 0.04 の上に乗らない（7/8 で頭打ち）ため、visits は 1800 のまま
**wideRootNoise を 0.04 に変更**した（`tsumego_capture/region_wide_root_noise`、既定 0.04。
0.0 に戻せば旧挙動）。ε 修正と wRN 変更は**両方必要**で、同一サンプルで
旧コード 1/8 → ε のみ 3/8 → ε + wRN 0.04 で **7/8**。
残る 1/8 は正解手が候補にすら上がらない完全な読み落としで、打つ手がない。

## 追記2（2026-07-30）: コウが正解の問題と枠のコウダテ

別の実戦誤答（13路下辺、正解は D1 でコウに持ち込む手。AI は E2 を選び白が生きた）を再現したところ、
**ownership も目数も信号が正しかった**（＝選択則の問題ではない）。枠の側が壊れていた。

- ROOT で白の対象石は **−1.00（無条件生き）**、黒は **−23.7目 / 勝率 0.7%**
- 正解の手順（D1 E2 C2 D2 B1）を打つと **−26.2 / 勝率 0.01%** とさらに悪化する

原因は `put_ko_threat`。`ko_p`（config `frame_ko`）は**攻め方と守り方のどちらにコウダテ形を
与えるか**の切り替えで、`ko_p=False` では守り側にコウダテが渡る。正解がコウ止まりの問題では
黒にコウダテが無く白がコウに勝つ＝**白の無条件生き**になり、正解手が価値を失う。
KataGo の「白 −1.00」は誤読ではなく正しい読みだった。

同じコアから枠を張り直した実測:

| | root スコア（黒） | AI の選択 |
|---|---|---|
| case2（コウが正解）ko_p=False | **−23.0** | B1 / E2 ✗ |
| case2 ko_p=**True** | **+0.68** | **D1 ✓**（1800中1762visitsが D1、他は全て −18目以上） |
| case1（コウでない）ko_p=False | **+2.92** | 3手目 C12 ✓ |
| case1 ko_p=**True** | **+14.22** | 初手が E13 ✗ に悪化 |

**`frame_ko: true` を既定にするのは誤り**で、どちらが正しいかは問題ごとに異なる（＝その問題の
答えがコウかどうか。lizgoban が手動トグルにしている理由）。ただし**枠の root スコアが判定材料になる**:
枠は「攻め方成功 = `offence_to_win`(5) 目勝ち」に調整する設計なので、`|lead|` が 5 から遠いほど枠が壊れている。

### 採用した対処: 枠の自動選択

キャプチャ時に `frame_ko` とその反転の両方で枠を張り、短い解析（既定 400 visits）で root スコアを取り、
`frame_balance_distance = abs(abs(lead) - 5)` が小さい方を採用する（`pick_balanced_frame`）。

- 400 visits で十分に判別できる（case1: 2.18 vs 9.80 / case2: 19.02 vs 3.08）。実測コストは 2本で約 1.2 秒
- 両方の枠が同一（コウダテ形が置けない盤）なら試算をスキップ
- 解析が取れなければ設定値の枠にフォールバック
- 設定: `tsumego_capture/frame_ko_auto`（既定 true）、`frame_ko_trial_visits`（既定 400）

検証: 自動選択を通した end-to-end で **case1 は ko_p=False を選んで C12（正解）**、
**case2 は ko_p=True を選んで D1（正解）**。

**落とし穴（要注意）**: `grid_to_sgf` は `RU` を出力しない。`BaseGame` は未指定なら設定の
ルールを入れる（chinese）が、素の `GameNode` を直接解析すると engine 既定の **japanese** になり、
面積計算前提の枠のスコアが **25目規模でずれる**（実測: 同一盤面で −23.0 → +2.3 と符号ごと反転し、
枠の破綻を見逃す）。枠バランスを測るコード・診断スクリプトでは必ず `RU` を明示すること。

## 追記3（2026-07-30）: 1visit の手が gain 争いに勝つ

3例目の誤答（13路右上、正解 M7。AI は **J7＝−16.5目**を選択）。枠の自動選択は正しく働いており
（実戦の SGF は ko_p=True の枠と完全一致＝コウ問題として正しい枠が選ばれていた）、
枠も ownership も目数も正常だった。原因は候補手の **visits** にある。

KataGo は root の子手を最低1回は評価するので、**1visit の手が moveInfos に載る**。その手の
ownership とスコアは探索結果ではなく **NN の生評価1回**で、gain が実手の10〜100倍のノイズになる:

```
探索された手   M7(v1324) gain +0.002 / L9(v65) +0.007 / N10(v50) +0.059
1visit の手    N6(v1)    gain +0.550 / M13(v1) +1.188   ← これが勝つ
```

実測4 run 中1 run で 1visit の M13 が選ばれた（残り3 run は 1visit の手が候補に出ず正解）。
GUI に出ていた「J7 −16.5目/303visits」は**子ノードの解析が親の手に書き戻された値**
（`set_analysis` が親の move dict を child の rootInfo で更新する）で、決定時の値ではない。

**対処**: `min_visits`（既定 10）未満の候補を除外する。目数ガードより**前**に落とすのは、
1visit の楽観的なスコアが `best_loss` を押し下げてガードを不当に狭め、本命手まで弾くのを防ぐため。
全候補が min_visits 未満（＝解析がほとんど進んでいない）ならフィルタせず従来どおり全候補で判断する。

**検証**（実機・3 run × 4局面、設定はユーザー config）:

| 局面 | 選ばれた枠 | 選択 | 結果 |
|---|---|---|---|
| case1 初手 | ko=False (+2.8 / +16.0) | A11 ×3 | 実戦は B12 が受理。A11 とは 0.03目差の同着（下記の限界を参照） |
| case1 3手目 | ko=False (+3.0 / +15.6) | C12 ×3 | 正解 |
| case2 初手 | ko=True (−23.4 / +2.5) | D1 ×3 | 正解 |
| case3 初手 | ko=True (−7.4 / +4.3) | M7 ×3 | 正解 |

**残る限界**: case1 の初手は A11(loss −0.05) と B12(loss −0.02) が 0.03目差で、ε 同着後の
目数タイブレークが A11 を選ぶ。実戦でアプリが受理したのは B12。**visits の多い方**を採る案は
case1 3手目で正解 C12(354visits) が D12(769visits) に負ける run があるため採用しない
（目数のほうが安定した信号）。

## 追記4（2026-07-30）: コウは「コウダテがある前提」で評価する

4例目の誤答（13路右上、正解 N10＝コウ。AI は N8＝セキを選択）。枠の自動選択は正しく働き
（実戦 SGF は ko_p=True の枠と完全一致）、枠自体も機能していた（白11子を取れれば +10.75目）。
**KataGo の評価も枠内では正しかった**:

- N10 の後、黒自身の連（L10-L11-M11-M12-N12）が呼吸点1（N13）になり、白 N13 で黒5子が取られる
- つまり N10 はコウにしかならず、黒はコウに勝たないと大損。20000 visits でも評価は変わらない
- 枠が攻め方に与えるコウダテは**1つだけ**で、白は B9 の1手（しかも +2目の得）で消せる

一方、**コウを黒が1回勝った局面は +8.09目 / 勝率 99.8%**（セキの N8 は −12.4目）。
つまり正解手 N10 は枠の中でも正しく、足りないのはコウダテだけだった。

詰碁は**コウダテがあるものと仮定して正解が決まる**（コウに持ち込めればそれが最大の成果）。
枠にコウダテを増やす案は試作したがバランスが崩れ（case2 が +2.3 → −16.1 で誤答に退行）、
配置先の地形次第で有効な脅しにならず不採用。代わりに**評価側で慣習を実装した**。

### 採用した対処: コウ手は「取り返した後」で評価する

候補手ごとに、打った石が**単独で呼吸点1** → 守り側がそこに打って取る → **攻め方の取り返しが
コウで弾かれる**、という形かを KaTrain 自身の着手判定（`IllegalMoveException("Ko")`）で判定する。
コウなら `ignore_ko=True` で取り返した局面を作り、そこを短く解析（既定 800 visits）した
scoreLead で評価する。通常評価の最善手を `TSUMEGO_KO_MARGIN` 超えて上回る場合のみ
その手を打つ（当初 0.5目。**追記7 で 5.0目 に変更**）。判定は本譜を汚さない使い捨てゲーム
（`tsumego_simulation_game`）で行う。

- `tsumego_ko_win_node()` / `tsumego_simulation_game()` — `ai.py`、ユニットテスト `tests/test_tsumego_ko.py`
- 設定: `ai/ai:tsumego` の `ko_win_assumption`（既定 true）、`ko_win_visits`（既定 800）
- コストはコウが見つかった候補だけ解析1本（実測 +1秒）。ハードコード定数: 判定する候補は
  visits 上位3手まで、マージン 0.5目

**検証**（実戦の戦略コードを実行、各2回、設定はユーザー config）:

| 局面 | 枠 | 選択 | 結果 |
|---|---|---|---|
| case1 初手 | ko=False | A11 ×2 | （B12 と 0.03目差の同着。下記の限界参照） |
| case1 3手目 | ko=False | C12 ×2 | 正解 |
| case2 初手 | ko=True | D1 ×2 | 正解 |
| case3 初手 | ko=True | M7 ×2 | 正解 |
| **case4** | ko=True | **N10 ×2** | **正解**（コウ判定: 通常 −21.7目 → コウ勝ち前提 +3.1目） |

コウと判定されたのは case4 の N10 のみで、他の局面の挙動は変わらない。

### 併せて修正: 枠選択が拮抗したときのタイブレーク

同じ問題を再キャプチャしたところ、今度は **ko_p=False の枠**が選ばれて再び誤答した。
両枠のバランス距離が **12.36 vs 11.61** とほぼ同点で、400 visits の試算では区別できずコイン投げに
なっていた。しかも ko_p=False では守り側にコウダテが渡るため、「攻め方がコウに勝った局面」を
作っても守り側が取り返せてしまい、**コウ判定が発動しない**（実測: ko_p=False で −19.9、
ko_p=True で +5.4）。

そこで `pick_balanced_frame` に **`FRAME_BALANCE_TIE_MARGIN`(2.0目)** を導入し、バランス距離が
これ以内で拮抗する場合は **攻め方にコウダテを渡す枠（ko_p=True）を優先**するようにした。
詰碁はコウダテがある前提で正解が決まるので、迷ったら攻め方に渡すほうが慣習に近い。
差が大きい場合は従来どおりバランス優先（case1 は距離 2.2 vs 11.0 なので ko_p=False を維持）。

再検証（実戦の戦略コード、各2回）: case4 の再キャプチャ局面（黒 K9 → 白 L11 の順で入った版）も
**N10 ×2 で正解**。他の5局面も変化なし。

### 殺す詰碁と生きる詰碁の両方に効く理由

`ko_p` の条件は `for_offense_p = xor(ko_p, xor(黒が攻め方か, 黒番か))` なので、**黒番である限り
`ko_p=True` は常に「黒（＝AI）にコウダテを渡す」**。黒が攻める詰碁なら攻め方パターン、
黒が守る詰碁なら守り方パターンが置かれ、受益者はどちらも黒になる。タイブレークの
「拮抗したら ko_p=True」はそのまま「迷ったら AI にコウダテを渡す」を意味する。
コウ勝ち評価も黒視点のスコアで見るので、殺すコウでも生きるコウでも同じくプラスとして出る。

コウ判定は「自分の**1子**が呼吸点1 → 守り側がそこを取る → 取り返しがコウで禁じられる」形を探す。
取られる1子は打った石自身とは限らないため（殺す詰碁では打った石自身、生きる詰碁では別の自石が
取られてコウになる形が普通）、打った石を最優先で試したうえで、他の1子アタリも
`_TSUMEGO_KO_MAX_ATARI_STONES`(6) 個まで調べる。

## 追記6（2026-07-30）: 枠外の代償地帯が gain の符号を反転させていた

## 追記7（2026-07-30）: コウ勝ち前提が「無条件に殺せる正解」を捨てていた

6例目の誤答（13路下辺、正解 **K1** で白を無条件に殺せる。AI は **L1** でコウにして不正解）。
追記6 の gain 修正は正しく効いており（`gain集計石41子`）、原因は **追記4 のコウ勝ち前提の
マージン `0.5目` が小さすぎた**こと。誤答局面の実測（region 1800 visits）:

```
move  visits   ptsLost  lead*sign  gainREG   ko?    koWin     gap
  K1    1776     +0.12     +11.44    +0.00     -            ← 無条件に殺す正解
  L1       1    +34.26     -22.70   -28.03    KO   +12.50   +1.06  ← 選ばれた
```

K1 は 1800 visits のうち 1776 を集める圧倒的な最善で、白は既に死んでいる（gain ±0.00）。
一方 L1 は **1 visit**・−34目・gain −28（白が生き返る）。それが「コウ勝ち前提 +12.50目 >
通常最善 +11.44目」で採用された。差はわずか **+1.06目**。

### なぜ +1.06目 出るのか（構造的なバイアス）

コウ勝ち前提のノードは (打つ → 守り側が取る → 取り返す) と進めた局面なので、**攻め方が
1手多く打ち、相手の石を1子取った状態**になっている。通常最善の局面と手数が揃っていないため、
比較は構造的にコウ側へ数目ぶん偏る。この +1.06目 はその「おまけ」であって、詰碁としての
成果の差ではない。**通常最善が既に無条件で殺しているとき、この偏りだけでコウが勝ってしまう。**

逆にコウが本当の正解である問題では、通常最善はセキ止まり等の失敗なので差は桁違いに大きい。
記録済みの実測値:

| ケース | 通常最善 | コウ勝ち前提 | 差 | 正しい判定 |
|---|---|---|---|---|
| **case E（本件・誤答）** | **+11.44**（無条件に殺す K1） | +12.50 | **+1.06** | 不採用 |
| case4（追記4・正解がコウ） | −12.4（セキの N8） | +3.1 | **+15.5** | 採用 |
| case4 再キャプチャ | −12〜−19 | +5.4 | +17〜+25 | 採用 |

### 採用した対処1（本命）: 成功しているならコウを検査しない

**詰碁の正解は目数ではなく結果の順序で決まる: 無条件に殺す（生きる） > コウ > セキ。**
目数はクラス内のタイブレークにすぎず、クラスを跨いだ比較には使えない。上の +1.06目 はまさに
「クラスを跨いで目数比較した」結果である。

そこでコウ勝ち前提の適用条件を、その本来の役目に絞る。この機構は追記4 で
「枠の中では攻め方のコウダテが乏しく、正解のコウ手がセキより悪く見える」局面の**救済**として
入れたものなので、**通常最善が既に成功しているなら適用してはいけない**。

成否の判定にはスコアの符号を使う。枠は「成功した側が `offence_to_win`(5)目勝ち」に調整される
設計なので、手番側から見た `best_normal` の符号がそのまま成否になる。`player_sign` 込みで見るので
**攻める詰碁・生きる詰碁のどちらでも成立**し、攻守の役（`black_to_attack_p`）を知る必要がない
（この値は枠生成時に `guess_black_to_attack` で決まるだけで game には残らない）。

記録済みの実測値すべてで一致する:

| ケース | 通常最善 | 判定 | 正しいか |
|---|---|---|---|
| case E（本件） | **+11.44**（K1 が無条件に殺す） | 既に成功 → コウ検査を省略 | ✓ |
| case4（正解がコウ） | −12.4（セキの N8） | 失敗 → 救済を試す | ✓ |
| case4 再キャプチャ | −12〜−19 | 失敗 → 救済を試す | ✓ |
| case4 ko_p=False の枠 | 負（コウ勝ちも −19.9） | 救済を試すが却下 | ✓ |

- `tsumego_already_succeeded()` / `TSUMEGO_SUCCESS_LEAD`(0.0)、設定 `ko_success_lead`
- コウ解析（800 visits）より**前**に判定するので、成功局面では解析1本ぶん速くなる

### 採用した対処2（保険）: マージンを 5.0目 に引き上げる

対処1 が主で、マージンは「救済が必要な局面で、構造的な偏りだけでコウが選ばれる」のを防ぐ保険。
実測の分離幅は +1.06 と +15.5 なので 5.0 は両者から 3倍以上の余裕がある。

- `TSUMEGO_KO_MARGIN` を 0.5 → **5.0**、設定 `ko_win_margin` で上書き可能
- 判定を純関数 `tsumego_ko_beats_normal()` に切り出してユニットテスト化（実測2ケースを固定）
- 採用/不採用の両方のログに**差と閾値**を出す（0.5 のときは差が見えずログから異常に気づけなかった）

**検証**（同一スクリプト・同一エンジンで新旧を比較、region 1800 visits、3 run）:

| 設定 | 選択 | コウ判定 |
|---|---|---|
| **新既定（成功ゲート + margin 5.0）** | **K1 ×3 ✓** | 「通常最善 +11.4目で既に成功」で省略 |
| 成功ゲートのみ（margin 0.5 に戻す） | **K1 ✓** | 同上（マージン値に依存しない） |
| 旧挙動（ゲート無効 + margin 0.5） | L1 ✗ | 採用（差 +1.04目、pointsLost +34.71） |

2行目が対処1 の価値を示している。**マージンという魔法の数字に頼らず、意味で決まっている。**

`min_visits` をコウ検査に課さない設計は**維持**した（探索分散で正解のコウ手が数 visits に沈む
ことがあり、そこで弾くと追記4 の慣習が効かなくなる）。1 visit の L1 は成功ゲートで落ちる。

**残る限界**: 成否の判定はスコアの符号なので、枠が大きく偏っている問題（`frame_balance_distance`
が大きいまま採用された枠）では誤判定しうる。その場合はマージンが保険として働く。
枠自体が壊れている問題は [[追記2]] の枠自動選択の領域。

## 追記8（2026-07-30）: gain は「探索の浅さ」を測っていた（case F）

|---|---|---|---|---|---|

| N6 | 89–90 | 0.11 | +1.44 | **+11.06〜+11.98** | 502visits で +0.66 |

visits を与えると gain が消える＝**死活の信号ではなく探索解像度の差**。この局面は root の

### 対処1: 深さゲート（`gain_min_visit_ratio`、既定 0.5）

gain で**目数最善手を覆せるのは、その手と探索の深さが比較できる候補だけ**に限る。
実測比は誤答 N7 0.31–0.34 / N6 0.11 に対し case D の正解 A4 は 1.00 なので 0.5 で分離できる。
追加クエリ 0・レイテンシ 0。

### 対処2: 同深さ検証（`gain_verify` / `gain_verify_visits` 800 / `gain_verify_margin` 0.3）

覆す判断が出たときだけ両者の**子局面を同 visits で解析し直し**、対象石の ownership を
**絶対値**で直接比較する（別クエリ同士は root 基準が揃わないので差分は使えない →

gain_probe で内訳を見ると、この盤の gain は死活の信号ではなく**追記8 の「探索の浅さ」ノイズ**
そのものだった: gain 上位は D5(8visits) +3.60 → D8(6v) +3.19 → A8(**1v**) +2.64 … と visits の
少ない順に並び、選択手 D10(253v) は +1.73、正解 B3 は負。石別の内訳では |delta|≥0.15 の石が
1つも無く（相手石15子は既に -0.83〜-0.99 で決着済み）、**どの手も盤面を動かしていない**。
リージョン外の地が支配的で、詰碁の成否がスコアにもオーナーシップにも現れていない。

実 generate_move: **枠なし D10 2/2 NG ／ 枠あり B3 2/2 OK（ko どちらの枠でも）**。
つまり枠を捨てた判断そのものが誤答の原因で、選択則側の対処は存在しない。

### 原因2: 枠の採否判定が浅すぎた — 生き問題は「解けたら生き」なので浅い読みでは死ぬ

`frame_destroys_problem`（追記9）は trial 400visits の root ownership で下していた。case N の
有効な枠（ko=False）の1子平均を**プロセスを分けた独立サンプル**で測ると:

| 設定 | 実測（1子平均） | 判定 |
|---|---|---|
| 400visits / wRN=0.04 | -0.69 / -0.80 / -0.98 | 全部「死」→ 枠を捨てる（＝誤答） |
| 1800visits / wRN=0.04 | +0.95 +0.93 +0.78 +0.92 +0.42 -0.02 -0.08 -0.23 -0.95 | **二峰性**。閾値 0.5 をまたぎコイン投げ |
| 3000visits / wRN=0.04 | +0.85 / +0.28 / +0.91 | まだ閾値をまたぐ |
| 6000visits / wRN=0.04 | +0.96 / +0.98 / +0.99 / +1.00 | 生きで安定（ただし1本 4.8〜8.4秒） |
| **1800visits / wRN=0** | **+0.97 / +0.97 / +0.96 / +0.96** | 生きで安定（1本 約1.7秒） |

`frame_destroys_problem` の docstring が予告していた非対称性（「殺し問題では手番側の攻め石が
壁と連絡して自明に +1.00 になるが、生き問題では手番側の石自体が戦いの対象なので、読み切れないと
有効な枠でも枠なしに落ちうる」）が、初めて実害として出た形。**生き問題でこの判定は「エンジンが
その詰碁を解けたか」を聞いているのと同じ**なので、浅い読みでは必ず死側に倒れる。

一方、本当に壊れている枠はどの設定でも死のまま（case F ko=False: 400 で -0.09〜-0.24、
1800/wRN=0 で -0.67〜-0.76、6000 で -0.92〜-0.95。case G: どれでも -0.98）。

**二峰性の正体は深さ不足ではなく `wideRootNoise` だった**（2026-07-30 追記）。wRN=0.04 は
着手選択で候補リストを広げるための設定で、「手番側が生きているか」という**裁定**では root の
探索が critical line に集中できず ownership が決着しない。wRN=0 にすると 1800visits で
+0.96〜+0.97（4/4）と安定し、6000visits/wRN=0.04（1本 4.8〜8.4秒）が 1800visits/wRN=0
（1本 約1.7秒）で置き換わる。**深さで殴るのではなく、裁定に不要なノイズを外すのが正解だった。**

**注意（測り方）**: 同一プロセスで同じ局面を測り直しても独立サンプルにならない（NN キャッシュが
効いて 0.2 秒で返る）。分散を見るときは engine 起動を挟むこと。

### 対処1: 枠を捨てる前に `frame_validity_visits`(1800) を wideRootNoise=0 で読み直す

`frame_validity_verdicts` / `frame_solver_verdict`（新規）。浅い読み（`frame_ko_trial_visits`=400、
wRN は設定値）で死と出た枠だけ読み直し、**読めた中で最も深い読みだけで**裁定する（平均すると
浅いノイズが復活する）。読み直しが取れなければ浅い読みの判定＝従来動作（枠を捨てる）。
コストを払うのは捨てる寸前の枠だけで、さらに**読み直しは浅い読みが生きに近い枠から順に行い、
有効な枠が1つ出た時点で打ち切る**（残りを深く読んでも出題する枠は変わらない）。

### 対処2（バックストップ）: 捨てる先の枠なし盤を測ってから捨てる

`frame_over_frameless`（新規）。全枠が壊れ判定のときだけ枠なし盤を読み、手番側コアの1子平均が
`FRAME_OVER_FRAMELESS_MARGIN`(0.5) 以上上回る枠があればそれを使う。**枠なしは安全側の
フォールバックではない**（リージョン外が丸ごと相手の地になる）ことを判断に入れる。
枠なし側は trial の浅い読みで足りる（枠と違って深さにほぼ不感: 400/1800/6000 の1子平均は
case N -0.75/-0.79/-0.77、case F -0.70/-0.65/-0.64、case G -0.65/-0.63/-0.68 で最大差 0.06。
枠なし盤では手番側の生死がリージョン外の地で決まっていて読みの深さで動かない）。

実測（1子平均。枠は ko の2通り／枠なしは `frameless_region`。枠は wRN=0.04 時代の値）:

| ケース | 枠の攻め方推定 | 枠 ko=False | 枠 ko=True | 枠なし | 結論 |
|---|---|---|---|---|---|
| D | 正（黒=攻め） | +1.00 | +1.00 | +0.99 | 枠（400 で生き＝比較に来ない） |
| E | 正（黒=攻め） | +1.00 | +1.00 | +0.92 | 枠（同上） |
| F | **反転**（黒=攻めなのに守り側の席） | -0.92〜-0.95 | -0.94〜-0.95 | **-0.65** | 枠なし（従来どおり） |
| G | **反転**（同上） | -0.98 | -0.99 | **-0.63** | 枠なし（従来どおり） |

この並びが判定の意味を説明している: 枠が壊れるのは**攻め方推定が反転したとき**で、そのとき
手番側の石は相手の壁の中に置かれるので深く読むほど確実に死ぬ（構造的な死）。一方 case N は
推定が正しく、死と出ていたのは単にエンジンがまだ解けていなかったから（読みの浅さ）。
深さはこの2つを分離する。

対処1 を入れた後は case N が「生き」で安定するため、この比較が結論を変える実測ケースは無い。
ただし wRN=0.04 で読み直していた時期の実測では -0.23 / -0.08 の run をこの比較が拾って
正解にしていた（3run 中 2）ので、それでもなお死と出る難問への保険として残す。

## 追記19（2026-07-31）: 正解が root 探索の visit 配分から漏れ、候補が全部コウになった（case O）

13路左上・枠あり・黒番初手。正解は A11 で白を**無条件に**殺せる（黒A11 白C10 黒C13 白B13
黒B12 白A10 黒A8 白A13 黒B12）。AI は B12 を打ち、白 A11 でコウにされて不正解。

### 症状と誤答の構造

これまでの誤答は「候補プールの中で正しい手を選べなかった」形だったが、case O は
**正解がプールに入っていない**。root のリージョン解析（1800visits）の visit 配分:

```
B12 v1172 / C10 v622 / 残り46手すべて v1
```

正解 A11 は v1 で、その 1visit の評価は `pt +28.74 / 白石 ownership -7.03（＝白は生き）`。
ところが A11 の**子局面を独立に 1800visits で解析すると** `lead +11.53目 / 白10子すべて
+0.99（＝白は全滅）`。root の value 推定が**約29目ずれている**。

| 手 | root 1visit の評価 | 子局面 1800visits |
|---|---|---|
| A11（正解） | pt +28.74 / 白石 own −7.03 | **lead +11.53 / 白10子 +0.99** |

この 1visit の数字で `min_visits`(10)・目数ガード(best+2.0)・gain・救済・コウ検査プールの
**すべて**から締め出されるため、選択パイプラインのどの経路にも A11 は入れない。

### 深さでは届かない（実測）

root visits を上げても visit 配分は変わらなかった。**PUCT は value が壊れている手を二度と
訪れない**ので、深さで殴る対策は原理的に効かない。

```
root  1800visits: B12 v1172 / C10 v622 / A11 v1
root 12000visits: B12 v7815 / C10 v4141 / A11 v1   ← 変わらない
```

### 既存のコウ経路検査は正しく働いていた

`tie_ko_screen`（追記15〜17）は B12・C10 の**両方をコウ経路と正しく判定**していた（2/2 run）。
足りなかったのは対抗馬プールで、`eligible`（目数ガード ∩ min_visits）から作るため
{B12, C10} しか無く、`clean な対抗馬が居ないため維持します` と諦めるしかなかった。

**「目数ガード内が全部コウ経路」は、詰碁の順序（無条件 > コウ）からすると
"正解はプールの外にいる" という信号そのもの**である。これをトリガーにする。

### 対処: コウ一色バンドからの脱出（`_ko_escape_choice`）

- **探す先は root policy**。value は壊れていても policy は候補を正しく挙げている。実測 prior:
  `B12 .68 / C10 .20 / B13 .043 / C13 .011 / A11 .0076〜.0091 / A8 .0008 / 残り42手すべて .0001`。
  正解 A11 は 2/2 run とも 5位で固定で、下限手 (.0001) との間に10倍近い崖がある。
  `TSUMEGO_KO_ESCAPE_MIN_PRIOR`(0.001) と `TSUMEGO_KO_ESCAPE_MAX_CANDIDATES`(4) で
  「未検査だが policy が認めた手」だけを拾う（`tsumego_ko_escape_candidates`）
- **候補ごとに解析1本**（`_region_child_verdict`）で「コウ経路か」と「同深さ絶対 ownership」を
  同時に取る。コウ判定の手順は `_ko_route_screen` と同一
- **採用条件の不等号が要**（`tsumego_ko_escape_accepts`）。コウ手のスコアは「コウに勝った前提」で
  出るので無条件の正解より**むしろ高い**。既存の覆し（`tsumego_override_confirmed`: margin 超えで
  上回ること）を使うと正解が却下される。順序を決めるのはクラスであってスコアではないので、
  条件は「clean かつ tolerance 超えて劣らない」

実測（同深さ 800visits・集計はリージョン内 42子）:

| 手 | 検証値 | 目数 | 判定 |
|---|---|---|---|
| B12（選択手・コウ） | +41.95 | — | incumbent |
| B13 | +18.53 | −22.27 | コウ経路（応手 A11）→ 却下 |
| **A11（正解）** | **+41.85** | **+11.13** | clean かつ **−0.10 差**（tolerance 0.5 内）→ **採用** |
| C13 | +18.77 | −18.80 | clean だが詰碁が成立していない（−23.2）→ 却下 |

成功と失敗の差が 23 に対し、コウと無条件の差は 0.10。**tolerance 0.5 はこの2つの間に
きれいに入る**。この非対称性が安全弁でもある: 答えが本当にコウの詰碁では clean な候補が
ownership 検査を通らないので、脱出は何もせずコウを維持する。

### 回帰（実 generate_move、各3run）

case O は **A11 3/3**（旧実装 B12）。既存ケースは全て不変で、脱出は一度も発動しなかった

### 残る限界

policy が正解を下限（.0001）まで落とす詰碁は、この機構でも拾えない。case O では
**1visit の gain も** A11 を未探索手の中で1位に挙げていた（−16.99/−16.31 vs 他 −19.8〜−19.9、

## 追記20（2026-07-31）: コウ経路検査の証拠（応手 PV）が枠へ手抜きして消えた（case P）

### 症状

13路下辺・枠あり（region = `2,12,0,6`）。黒番で白8子（N4 / G3 / J3K3L3 / H2 / M2N2）を
無条件に殺す詰碁。1手目 K1・5手目 L2 は正解だが **3手目で H1 を打ち**、白 J1・黒 L2 のあと
白 G1 が黒 H1 を1子取ってコウになり不正解。正解は 3手目 **J1**（白 H1・黒 L2 で白は無条件死）。

### 選択そのものは設計どおり

    gain順: H1(v1143/1.00 pt-0.03 g+0.00) J1(v576/0.50 pt-0.06 g+0.00) ...
    目数順: J1(v576/0.50 pt-0.06 g+0.00) H1(v1143/1.00 pt-0.03 g+0.00) ...
    コウ経路検査: H1 は無条件（候補自身・拮抗応手 ['J1', 'pass', 'L1'] の PV ともコウ形なし）

gain は両者とも飽和（+0.00）、目数差 0.03 は `points_epsilon`(0.25) 内なので同着バンドの
visits タイブレークで H1(v1143) を採る — 追記14 のとおりの動作。**正解 J1 は目数最善**なので、
クラス裁定（追記15〜17 のコウ経路検査）さえ働けば H1 は格下げされ、目数ガード内の対抗馬は
J1 しか居ない（L2 は pt+4.17 でガード外）ので必ず J1 になる。**誤答の原因は検査の不発**。

### 原因: untilDepth=1 では PV が ply2 以降で枠へ出ていける

H1 の子局面（リージョン限定 800visits）で白の最善応手は J1 で安定している（v59〜99 で
単独首位＝応手の選択自体はブレていない）。消えていたのは**その PV の中身**:

| untilDepth | 白 J1 の PV | コウ検出 |
|---|---|---|
| 1（従来のリージョン解析） | `J1,L2,`**`J12`**`,K2,L11,G4` — ply3 で枠外へ手抜き | **1/4** |
| 6 | `J1,L2,`**`G1`**`,G4,M1,H1,J12` — 局所に留まりコウに到達 | **4/4** |

（プロセスを分けた 4 trial。**同一プロセスの再クエリは NN キャッシュが効いて独立サンプルに
ならない** — 1プロセス内では 3/3・4/4 と安定して見える。GUI 実戦は 1/4 の側を外した）
無条件の正解 J1 は**どちらの深さでも 4/4 clean** なので、深く縛って偽陽性が増えてはいない。

`avoidMoves` の `untilDepth=1` が縛るのは root の着手選択だけで、ply2 以降の PV は枠の外へ
自由に出られる。詰碁を読み切った KataGo にとって**負けている側の局所の抵抗は枠の一点と同値**
なので、守り方の PV は肝心のコウを打たずに枠へ手抜きする＝検査の証拠そのものが消える。
これは追記15 が「親局面の PV は白が枠へ手抜きするので使えない」として子局面解析に切り替えた
のと**同じ失敗が1手ずれて再発した**形で、深さ1の強制では ply1 しか局所化できていなかった。

### 対処

コウ経路検査の子局面解析だけ、**歩く深さと同じだけリージョン外を禁じる**
（`TSUMEGO_KO_REGION_UNTIL_DEPTH = TSUMEGO_TIE_KO_PLIES = 6`）。PV を証拠に使う範囲＝局所を
強制した範囲、という整合点で、これ以上でも以下でもない。

- `engine.request_analysis` に `region_until_depth` を追加（既定 `REGION_AVOID_UNTIL_DEPTH=1`
  ＝従来どおり）。avoidMoves の生成は純関数 `region_avoid_moves` に切り出してテスト可能にした
- 深い拘束を渡すのは `_ko_route_screen` と `_region_child_verdict` の2箇所だけ。
  本譜の候補評価・同深さ検証（`_verified_choice`）・コウ勝ち前提（`_analyze_score_lead`）は
  **untilDepth=1 のまま**（条件を変えると既存の校正値と比較できなくなる）
- `pass` は禁じない。局所で打つ手が無い側は手抜きの代わりにパスできる（着手強制はしない）
- `_region_child_verdict` の `value` は候補と incumbent を同条件で測った相対比較にしか
  使わないので、拘束を深くしても両者に同じだけ効く（case O で確認）

### 回帰（実 generate_move、各3run）

case P は **J1 3/3**（旧実装 H1）。既存ケースは全て維持:

| case | 結果 | 備考 |
|---|---|---|
| K | C13 3/3 | 追記19 の基準は C13 2/3・A10 1/3 |

root policy に足す Dirichlet ノイズは run ごとに引き直され、しかも1回の探索の間ずっと乗るので

|---|---|---|---|
| 0.04 | v90〜117 | v58〜75 | **0.44〜0.88**（本番フローで 3/6 が 0.5 を割る） |
| **0** | v663〜666 | v98〜101 | **0.15 が 4/4 で不動**（残りの応手は全部 v1） |

## 追記25（2026-07-31）: 同深さ検証を wRN=0 に揃える案は **REJECT**（コードを変える前の実測）

## 追記27（2026-07-31）: 枠の攻め方推定が極値のタイで反転した（case S）

13路右上の詰碁（正解は黒 M10 → 白 M11 → 黒 N10 → 白 K9 → 黒 M9 → 白 N7 → 黒 N9 で

gain順: L13(v11/0.01 pt+6.08 g+2.70) H12(v962/1.00 pt-0.52 g+0.58) M10(v679/0.71 pt+0.15 g-1.01)

**選択則は無実**。対抗馬（M10）はちゃんと居て機構は全部動いており、それでも H12 が

読んでいる。原因は選択則ではなく**出題した盤**のほうだった。

### 原因: `guess_black_to_attack` が -1 で反転した

保存 SGF の壁は白＝枠は「白が攻め方」として張られていた。実際は黒が攻め方なので、
`put_outside` の代償地帯（defense_area 85.5目）が**攻め方であるはずの黒に渡り**、黒はどう
打っても +21目リードする。死活がスコアから切り離され（追記21 case Q と同じ形）、目数も
gain も詰碁を測らなくなる。加えて役割反転時の defense_area(85.5) は外側面積(81)を超えており
（`fit_margin` は `abs(komi)` で見積もるので黒攻めの 78.5 しかチェックしない）、白の壁は
自分の地に接続しない浮き石になる。

判定を分けたのは**左辺の極値のタイ**だった。コアの最左列は H で、そこに H11(白) と H10(黒)
が縦に並ぶ。`min_by` は row-major 順の最初の1子を代表にするので H11(白) が採られる:

```
代表が H11(白)      -1  → black_to_attack=False（誤。実キャプチャはこれを引いた）
代表が H10(黒)     +42  → black_to_attack=True （正）
極値線を全部足す   +21  → True（正。タイの崩し方に依存しない）
```

`tsumego_frame_stones` は「反転・転置でタイの崩れ方が変わる」ことを既に知っていて、元の
向きで一度だけ判定する形にしてあった。しかしそれは**元の向きでの崩し方を固定しただけ**で、
崩し方そのものの恣意性は残っていた。

### 安全網が効かなかった理由（case G との違い）

役割反転は case G（追記9）で一度踏んでおり、`frame_destroys_problem`（手番側の本体石が
開始時点で死と読まれる枠は捨てる）で検出・回避している。ところがこの判定は**手番側が
守り方のときにしか効かない**。case S は手番側（黒）が攻め方なので、役割が反転しても黒の
本体石は壁と連絡して生きたままになる（1子平均、`frame_validity_probe.py` / `frame_role_ab.py`）:

```

枠なし               v400 +0.97              v1800 +0.97

しかも**浅い読みで「生」と出た枠はそのまま採用**していたので、同じ盤で run ごとに採否が

## 追記28（2026-07-31）: 詰碁の正解順序は**役割で逆転する**（守り方は セキ > コウ）（case T）

13路下辺の詰碁（黒 M1 → 白 J1 → **黒 L1** → 白 J2 → 黒 H2 でセキ。**黒＝守り方**）で、
初手 M1 は正解したのに3手目で L1 ではなく J2 を打ち、コウ生きに転落して不正解になった。

```

          ko_success_ownership=0.5 に届かないため省略しません

### これまでの前提「無条件 > コウ > セキ」は**攻め方の順序でしかなかった**

詰碁の正解は結果のクラスで決まるが、その順序は解く側の役割で逆転する:

| 役割 | 順序 |
|---|---|
| 攻め方（殺す） | 無条件死 > コウ > セキ（相手が生きた＝失敗） |
| 守り方（生きる） | 無条件生き > **セキ > コウ** |

守り方にとってセキがコウより上なのは、盤全体のコウダテという**外部条件に頼らず**無条件に
石が助かるから。ところが選択則が使うスカラーは全部「どれだけ得したか」を測るので、
守り方のセキ（地は0目・相手も生きる）はコウ勝ち（相手を取り切る）より必ず下に出る。
実測（case T の3手目。同深さは 800visits・untilDepth=6）:

```
                    J2（コウ生き）  L1（セキ＝正解）   順序
root 目数            -0.34          +4.30            逆（ガード best+2.0 が L1 を落とす）
gain                 +0.20          -3.83            逆
同深さ検証値（全石）  -16.66         -19.79           逆（相手33子に支配される）
同深さ 相手石/子      -0.87          -0.96            逆（セキでは相手が生きるのが正常）
**同深さ 自石/子**    **+0.99**      **+1.00**        **正**
```

**目数ではクラスの順序を表現できない**。役割が分かって初めて「何を見れば成否か」が決まる
（攻め方＝相手石が死んだか／守り方＝自石が生きたか）。従来の「両方測って厳しいほうを採る」
ヘッジ（`tsumego_success_ownership` の min）は、守り方では「相手が生きている＝失敗」と
読むのでセキを必ず失敗側に落とす。

### 役割は**枠の壁の色**から読める

`put_border` は壁を**攻め方の色**で敷き、`mark_region_corners` が同じ frame_range を
リージョンにするので、リージョン境界線（盤端でない辺）の石列がそのまま役割を表す
（`tsumego_solver_attacks`）。保存済み19ケースの実測:

- 枠あり: 全ケースで境界線が**単色100%・占有率100%**（case T: W7/7・W11/11 ／ case M: W9/9・W9/9
  ／ case O: B10/10・B9/9）
- 枠なし: 境界線に石が0〜1子（case R は13点中1子＝占有率 0.08）

0.08 と 1.00 の間が桁で空いているので占有率 0.7・純度 0.9 の二重ゲートで安全に分離できる。
**枠なしは None＝従来の役割非依存の挙動を維持**（G2/F2/H/I/N/R は一切変わらない）。
反転枠（case F/G/S の保存 SGF）では判定も反転側を返すが、それは**正しい**: 枠が反転していれば
スコアも ownership もその枠の役割に従って出るので、盤に書かれている役割こそがその局面の

## 追記29（2026-07-31）: コウが争点の局面ほどエンジンはそのコウを打たない（case U）

**症状**（13路左下・枠あり・黒番初手、region `0,8,0,8`）: 正解は **C1**（白 B1 → 黒 A3 →
白 A4 → 黒 A2 → 白 E1 → 黒 D1 で白を無条件死）。AI は **A3** を打ち、白 C1 → 黒 A4 →

### 手順前後そのものが争点

白の抵抗は最後の **E1**（捨て石）で、これは正解手順にも現れる。違いは取られる黒石の数:

| 初手 | 白 E1 の時点の黒石 | 結果 |
|---|---|---|
| **C1**（正解） | `{C1, D1}` の**2子連結** | 2子取り → 黒 D1 で即取り返せる＝**コウにならない** |
| A3（誤答） | `D1` が**単独** | 1子取り → 取り返しがコウ禁止＝**コウ** |

しかも**白 C1 の時点で黒 D1 は既にアタリ**（呼吸点は E1 のみ）なので、A3 と打った後は
黒が何を打ってもコウを避けられない。実測（`ko_route_probe.py` move=2）でも 3手目の
A4/A2 は KO、A1 は「clean」と出るが**これは PV を歩いただけの偽陰性**で、白 E1 は黒の
着手と無関係にいつでも打てる。**誤答は1手目に帰着させないと直せない**。

### 選択則は届く位置に居た

root は A3 pt−0.09 v983 / C1 pt+0.12 v811 で、目数差 0.21 は `points_epsilon`(0.25) 内＝
**目数同着バンドの visits タイブレーク**（case J で入れた機構）が A3 を採っている。つまり
クラス裁定（無条件 > コウ）さえ効けば C1 は格下げ先としてバンド内に居た。落ちたのは検出。

### 落ちた理由: リージョン解析は守り方からコウダテを取り上げる

`avoidMoves untilDepth` は**両者**を枠内に縛るので、守り方はコウダテを打てない。すると
コウを仕掛けることは守り方にとって純粋な損になり、KataGo はそれを正しく「打つ価値なし」と
読む。ところが詰碁の裁定は逆で、攻め方の「コウで殺す」は「無条件に殺す」より**下のクラス**に
落ちる。**つまりコウが問題になる局面ほど、エンジンはそのコウを打たない**。

実測（`ko_reply_ratio_probe.py` / `ko_available_probe.py`、800visits・wRN=0）:

```

  D6 v617 比1.00 lead +4.76   pv=D6,E6,A4,A2,C1,A1
  E4 v 54 比0.09 lead +4.78
  A4 v 49 比0.08 lead +5.41
  ...
  C1 v  7 比0.01 lead +8.99   pv=C1,A4,D6,E6,D7   <- コウを作る手。PV に E1 が無い
```

コウを作る C1 は **visits比 0.01** で敏感側 `TSUMEGO_KO_REPLY_RATIO_CHOSEN`(0.05) にも届かず、
しかも lead は白に不利（+8.99）と評価されている。**比 0.00 まで全応手を歩いても、PV 由来の
検出は 0/5 run**。追記24 で入れた「比を下げる」対策はこの形には原理的に効かない。

（`tsumego_defender_ko_points`）。探索の好みに一切依存しない。

- **候補手より前から打てたコウは数えない**。局面の性質であって候補の性質ではなく、数えると

  case F2 の N9 / case Q の M13 は着手前から打てるコウ。いずれも従来判定が別途拾っている）

## 追記37（2026-08-01）: 極値票の役割反転は測っても直せない — 役割指定ホットキー（case X）

### 根因: 極値票の前提「外側の色＝攻め方」がこの形では偽

原問題（コア22石）の `guess_black_to_attack` は **-68 で確定的に False（白が攻め方）**。内訳:

- **殺される側の白群が2線（B列）を這って左辺の極値線を占める**（B8/B7/B6/B5/B3 で -97）
- 残り2辺の極値石 **C10・F3 も白**（原問題の外郭石、-40）＝4辺中3辺の極値線が守り方の色

case S（追記27）のタイ崩れ（±1 の紙一重）と違い、**構造的に -68** なので極値線の集計改良では
救えない（辺スナップ線を除外しても C10/F3 だけが残りやはり白）。反実仮想は `frame_role_ab.py`:
role=True で張り直すと**両コウダテ変種とも select_tsumego_move が正解 A4**・バランス距離
0.00〜0.69・solver_core +1.00/子、反転枠は両方 C2 誤答＝役割だけが原因。

### 測定で役割を選ぶ案は3族すべて実測で却下（追記27 の完成形）

| 測定族 | 却下の実測 |
