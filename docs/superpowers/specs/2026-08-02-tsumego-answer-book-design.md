# 詰碁回答帳（answer book）設計 — 誤答問題の手動記録と対称一致再生

日付: 2026-08-02
状態: 設計承認済み（実装前）

## 1. 背景と目的

詰碁キャプチャの正答率は約70%まで来たが、残る誤答の主成分は実測で確認済みの
**エンジン側の限界枠**（case I/Q の準備手問題＝KataGo の value が visits を積んでも
壊れたまま、case W の救済残余、解答樹に無い同格別解踏み）であり、解析ロジックの
改良では原理的に潰せない。

一方、使用中の詰碁アプリは**同じ問題を盤面の四隅を入れ替えて再出題する**（回転・
鏡映のみ。辺沿いの平行移動や色反転は無い＝ユーザー確認済み）。そこで:

- 誤答した問題の**正解手順をユーザーが手動で記録**して保存する
- 再出題時に**盤の8対称の正規化キー**で照合し、ヒットしたら記録手順どおりに
  **0秒で自動解答**する

これにより「一度間違えた問題を二度と間違えない」を、正しさ保証つき
（正解はユーザーがアプリの解答から入力する）で実現する。別解ミス
（解答樹に無い正しい別解を打ってアプリに×にされる）も同時に解決する。

### 検討して却下した代替案

- **自動深掘りソルブ（宿題キュー）**: 誤答の自動検知が不可能（アプリ側が判定）で
  ユーザー操作が必要な点は同じ。残存誤答は「深掘りしても直らない」実測済みケース群
  （value 崩壊は 12000visits でも不変・df-pn は region>23 で爆発）で、深掘り結果の
  正しさを自動検証する手段も無い。
- **ソルバ永続キャッシュの位置不変化のみ**: ソルバが解けた問題は既に正答している
  ので誤答は1件も減らない（高速化のみ）。将来の小改善として保留。

## 2. スコープ

### やること

- 正規化キー計算と回答帳ストア（新規モジュール `katrain/core/tsumego_answer_book.py`、
  Kivy/KataGo 非依存）
- キャプチャ時の照合とゲームへの紐づけ（`__main__.py` のキャプチャ成功処理）
- 記録UX: 画面ボタン「正解手順を記録」→「この手順を保存」（Kivy GUI + i18n）
- 再生: 黒番戦略の先頭で回答帳を照会し、次の黒手を即返す。逸脱・非合法時は
  従来パイプラインへフォールバック
- ユニットテスト（KataGo 不要）

### やらないこと（YAGNI）

- 誤答の自動検知（アプリ側が判定するため不可能）
- 色反転・平行移動の正規化（アプリ仕様で不要とユーザー確認済み。必要になったら
  正規化関数に足すだけ）
- 回答帳の管理GUI（削除・編集は JSON 手編集で行う）
- ソルバ永続キャッシュの位置不変化
- 新しい設定キー（回答帳が空なら全経路の挙動は完全に従来どおり＝受動的機能）

## 3. 正規化キー

**入力**: キャプチャ時に認識した問題石（**枠を張る前**の AB/AW）、盤サイズ、手番。

**計算**: 盤の8対称（恒等・回転90/180/270・鏡映4 = 二面体群 D4）で石集合を変換した
8通りを作り、決定的なシリアライズ（色つき座標の整列タプル）の**辞書順最小**を
標準形とする。キー = SHA1(バージョン + 盤サイズ + 手番 + 標準形)。

**変換の扱い**: 盤→標準形の写像（変換ID 0-7）を覚えておき、再生時は逆変換で
記録手を現在の盤の向きに戻す。

**対称局面の曖昧性**: 問題の初期配置自体が対称だと、標準形に写す変換が複数
タイになりうる。照合時は**問題石を標準形に写す全変換を列挙**し、実際に打たれた
手列が前方一致する変換を採用する（通常は1つ。対称局面でも played moves が
どちらの枝かで自然に決まる）。

**キーの座標系**: `Move.coords` の (x, y)・y は下origin（`__main__.py` の
キャプチャ座標変換コメント参照）。変換関数はこの座標系で書き、テストで往復
恒等を担保する。

## 4. データ形式と保存場所

`~/.katrain/tsumego_answers.json` 単一ファイル（可読・手編集で削除可能）:

```json
{
  "version": 1,
  "entries": {
    "<sha1>": {
      "size": 13,
      "to_play": "B",
      "canonical_black": ["A11", "B11", "..."],
      "canonical_white": ["B10", "..."],
      "lines": [
        ["A10", "A8", "B12", "A9", "C11"]
      ],
      "created": "2026-08-02"
    }
  }
}
```

- `lines` は標準形向きの手順（黒白交互、手番から開始、パスは `"pass"`）。
  **複数 line 可** = 同じ問題を再記録すると line が追加され、白の別応手への
  枝分かれに対応する。同一 line の重複追加は無視。
- 起動時（初回参照時）に1回ロードし、保存時に書き戻す。ファイル破損時は
  無視してログを出し、空の回答帳として続行（出題は従来経路になるだけ）。

## 5. キャプチャ時の照合

キャプチャ成功処理（`__main__.py`、枠選択より前の認識石が手に入る箇所）で:

1. 正規化キーを計算し、回答帳を照会（辞書引き＝0秒）
2. ヒット/ミスに関わらず、ロード後の `game` にインメモリ属性を設定:
   - `game.tsumego_book_key`（記録ボタンが使う）
   - `game.tsumego_book_transforms`（盤→標準形の有効変換リスト）
   - ヒット時のみ `game.tsumego_book_entry`
3. ヒットしたらログに「回答帳ヒット」を明示

**枠張り・ソルバゲートの判断は従来どおり行う**（スキップしない）。理由:
変更が最小で、白の応手が記録から逸脱してフォールバックしたときに従来
パイプラインが今と同じ条件（枠あり等）で働く。回答帳ヒットの高速化は
着手側（照会即答）で十分得られる。

KaTrain を再起動するとインメモリ属性は消え、その出題中の再生・記録は
できなくなる（次のキャプチャから復活）。許容する。

## 6. 記録UX（画面ボタン）

- 詰碁キャプチャ出題中（`game.tsumego_book_key` がある）のみ有効なボタン
  「**正解手順を記録**」を追加。**常時可視のエリアに置く**（`katrain/gui.kv` の
  右パネル操作ボタン群など。分析ドロップダウンメニュー内は不可＝ラベルの
  トグル状態が見えず、記録中であることを見失う）。具体的なウィジェット位置は
  実装計画でレイアウトを見て確定する。ラベルは i18n
  （`.po` 編集 + `python tools/compile_mo.py`）。
- 押すと **記録モード**:
  1. 問題開始局面（root）に巻き戻す
  2. 黒のプレイヤーを一時的に Human に切り替え（auto_ai_black 停止）。
     元のプレイヤー設定は退避
  3. ユーザーが黒白両方を手入力（アプリの解答どおりに）
  4. ボタンは「**この手順を保存**」表示に変わる
- 「この手順を保存」で root からの現在パスの手列を標準形向きに変換して
  回答帳に登録（既存キーなら line 追加）し、プレイヤー設定を復元、
  ボタンは通常表示に戻る。保存時に `game.tsumego_book_entry` も設定するので、
  **root に巻き戻して黒 AI に打たせれば記録どおり動くかその場で検証できる**。
- 記録中に新しいキャプチャをしたら記録は破棄（保存されない）。

## 7. 再生とフォールバック

`TsumegoSolverStrategy._generate_move` と `TsumegoOwnershipStrategy.generate_move`
の**先頭**で共通ヘルパーを呼ぶ:

1. `game.tsumego_book_entry` が無ければ即 return（従来経路へ。オーバーヘッドなし）
2. root からの手列を有効変換それぞれで標準形向きに写し、いずれかの line と
   **前方一致**する変換を探す
3. 一致したら line の次手（黒手）を逆変換して**即返す**（解析0本・0秒）。
   ログに「回答帳から着手」を明示
4. 前方一致する line が無い（白がアプリと違う応手をした・認識ずれで盤が
   違う等）、または記録手が現局面で非合法 → **その手番から従来パイプライン**
   （ソルバ→ai:tsumego）へフォールバックし、ログに理由を明示。
   以後の手番も毎回照合し直す（白が記録の枝に戻れば再ヒットする）

両戦略の先頭に置くのは、キャプチャ経路がどちらの戦略を設定した場合
（ソルバゲート内=solver / ゲート外=枠張り+ai:tsumego）でも同じに働かせるため。

## 8. エラー処理まとめ

| 状況 | 挙動 |
|---|---|
| 回答帳ファイル破損 | ログを出して空扱い（従来経路） |
| 記録手が非合法（認識ずれ等） | その手番からフォールバック |
| 白の応手が全 line から逸脱 | その手番からフォールバック（毎手再照合） |
| 対称局面で変換がタイ | 全有効変換で前方一致を試す |
| 同一問題の再記録 | line 追加（重複 line は無視） |
| 記録中の新キャプチャ | 記録破棄 |

## 9. テスト

`tests/test_tsumego_answer_book.py`（KataGo/Kivy 不要・pytest）:

- **正規化**: 同一問題を8対称の各向きに置いた8盤が同じキーになる。
  異なる問題（1石違い）はキーが変わる
- **変換往復**: 全8変換で 盤→標準形→盤 が恒等。手座標の写像も同様
- **再生**: 記録 line からの次手取得／前方一致の白逸脱検出／非合法手で None／
  複数 line の枝選択／対称局面のタイ変換
- **ストア**: 保存→ロードの round-trip、重複 line 無視、破損 JSON の空扱い

統合確認（手動）: ユーザー提供の13路参考 SGF
（`AB[ai][bi][ci][di][ei][ej][ck][ek][bl][el][em] AW[bj][cj][dj][bk][dk][dl][dm]`、
正解 `B[aj] W[al] B[bm] W[ak] B[cl]`）を左下と右上に置いた2盤で、
片方で記録→もう片方でヒットして同手順（対称変換済み）が出ること。

既存回帰への影響: E2E スイート・P1 スイートは回答帳が空のまま走るので不変。

## 10. 成功基準

- 一度記録した問題は、四隅のどこに再出題されても**0秒で記録どおりに解答**する
- 回答帳に無い問題・回答帳が空のときの挙動は**完全に従来どおり**
- 照合・再生に解析クエリを1本も使わない（20秒制限に対して負方向のリスクなし）

## 追記1（2026-08-04）: 回答帳バナーと記録ボタンの右端固定

**回答帳のヒットがログでしか分からない**という指摘への対応。詰碁ビュー
（`tsumego_view`）は右パネルを幅1に潰すので、`controls.set_status` のステータス欄も
**画面に出ていない**＝盤と下部ナビ以外に文字を出せる場所が無い。

- **バナー**（`<TsumegoBookBanner>` in `gui.kv`。盤の**真上**に全幅で出す）:
  `KaTrainGui.tsumego_book_status`（StringProperty）が空でない間だけ高さ dp(30) を持ち、
  空なら **高さ0・opacity 0 で完全に消える**（回答帳に無い問題では従来のレイアウトと
  1px も変わらない）。石に重ならないので盤面表示を邪魔しない。
- **状態は3つ**（`tsumego_answer_book.line_status` + `ai.tsumego_book_status`）:
  `playing`（黄・記録の途中）/ `done`（緑・記録手順を打ち切った）/ `off`（橙・どの line とも
  前方一致しない＝この手番から従来パイプライン）。**「回答帳の問題だ」と出したまま実際には
  フォールバックしている状態を作らない**ため、白の逸脱で文言が変わる。`playing` の条件は
  `tsumego_book_next_move` と一致させる（占有ずれで再生できない局面は `off`）。
- 判定は §7 の再生照合と同じ純関数で**解析クエリ0本**。`update_gui`（Kivy スレッド）で
  毎回更新するが、`tsumego_book_entry` が無い盤は最初の getattr で即 "" を返す。
- **記録ボタンの見切れ**: `pos_hint center_x=0.94` は幅がテキスト依存（AutoSized）なので、
  詰碁アプリと分割表示する狭い窓（実測 盤カラム 884px）で **145px のボタンが右へ 22px
  はみ出していた**。右端から dp(6) に固定（`x: root.width - dp(6) - self.width`＝幅の変化にも
  追従）。押し出されるエンジン状態ランプは**記録ボタンが可視のときだけ**その左へ退避し、
  当たり判定の箱も 0.6 倍に詰める（狭い窓ではナビ列の右端と接するため。描画は
  `min(width,height)` 基準にしたのでランプの見た目は不変）。さらにランプの宣言をナビ列の
  **前**へ移し、数px重なった場合はナビ側がタッチを取るようにした（kv は後宣言が上）。

## 追記2（2026-08-04）: 記録ボタンの操作結果もバナーに出す

§6 の記録UXが返すメッセージは全部 `controls.set_status` だけに出していたので、
**詰碁ビューでは1つも画面に出ていなかった**（保存できたのか失敗したのか分からない）。
追記1 のバナーに数秒だけ重ねて表示する（`KaTrainGui._tsumego_message`）:

| 操作 | 文言 | 色 | 表示秒 |
|---|---|---|---|
| 保存成功 | 正解手順を回答帳に保存しました（N手） | 緑 (`save`) | 5 |
| 同一手順 | 同じ手順が記録済みです（回答帳は変更なし） | 青 (`info`) | 5 |
| 記録モード開始 | 記録モード: アプリの正解どおりに黒白両方を打ち… | 青 (`info`) | 8 |
| 手順が空/黒番でない | 手順が空か黒番から始まっていないため記録を破棄しました | 橙 (`warn`) | 5 |
| 出題中でない | 詰碁キャプチャの出題中のみ記録できます | 橙 (`warn`) | 5 |

- バナーの `flash` は再生状況（`status`）より**優先**して上書きし、消えると元の
  再生状況表示に戻る。`status` が空（回答帳に無い問題）でも flash 中は帯が出る
  ＝「記録できません」系の警告が回答帳未登録の盤でも見える。
- `set_status` は従来どおり呼ぶ（通常表示では右パネルにも出す）。
- タイマーは1本だけ持ち、連打時は前のタイマーを捨てて出し直す。新しいキャプチャ
  （`_do_new_game`）では前の盤のメッセージを持ち越さずキャンセルする。
- メッセージループスレッドから呼ばれるので、プロパティ更新は `Clock` 経由
  （`tsumego_recording` の既存パターンと同じ）。
- **帯と盤の間に隙間は入れない**（帯の下淵と盤の上淵は接する）。実測では盤ウィジェットは
  割り当てスロットをはみ出しておらず（1000px の列で 帯30 + 下部65 を引いた 901px ぴったり）、
  帯を出した直後に重なって見えた場合はレイアウト確定前の描画で、ウィンドウサイズを変えると
  解消する（`BadukPanWidget` は size/pos に bind した trigger で描き直す）。dp(4) の隙間を
  入れる案は実機で「隙間が空きすぎ」と判断して撤回した（2026-08-04）。
