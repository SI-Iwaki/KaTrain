# 詰碁着手決定の重畳発行（レイテンシ短縮）設計

日付: 2026-08-03
対象: `katrain/core/ai.py`（TsumegoOwnershipStrategy）、`katrain/core/game.py`（投機クエリの発行・掃除）、`C:\Users\iwaki\.katrain\analysis_config.cfg`（ユーザー手動編集）

## 1. 背景と問題

コウ絡みの詰碁で、盤面キャプチャから正解手順を打ち切るまで合計約20秒かかっている
（2026-08-03 GUI 実測ログ・13路枠なし・黒4手）。ユーザー（白番）は**ほぼ即打ち**なので、
時間はほぼ全部「白の応手が入ってから黒の着手が出るまでの直列チェーン」に載っている。

AI黒番1手あたりの内訳（ログ実測）:

| 段階 | 所要 | 直列/並列 |
|---|---|---|
| 定常リージョン解析（root 1800visits・ownership付き・wRN=0.04） | 2.4〜2.6秒 | 戦略はこの完了を待つ |
| score_best 同深さ検証バッチ（800visits×3〜4本） | 1.5〜1.8秒 | バッチ内は並列、root の後に直列 |
| 救済バッチ（800visits×3本、発動時） | 約1.5秒 | 検証バッチの後に直列 |
| コウ経路検査（800visits×1本・wRN=0・ud=6） | 0.9〜1.1秒 | 選択確定後に直列 |

計 4〜6秒/手 × 黒4手 ＋ 枠採否 2.8秒 ≒ 20秒。難問（10手超）ではこの線形和がそのまま伸びる。

後段3バッチの**クエリ内容は前段の「判定結果」に依存しない**（依存するのは「どれを採用するか」
の判断だけ）。つまり発行を前倒しできる。

**鍵になる実測**: 既存フローは救済段で選択手の子局面を再クエリすることがあり（同一局面・
同一設定）、そのときの 800visits は **0.1秒**で返っている（ログ QUERY:462 / QUERY:480）。
＝同一条件の再クエリはエンジン側キャッシュでほぼ無料。**「温めておいて、実クエリは従来どおり
撃つ」だけで実質の並列化になる**。これは `ponder_replies`（アイドル先読み）で校正済みの
安全構造と同じ（結果は捨てる＝着手判定への影響が構造的にゼロ）。

## 2. 目標 / 非目標

**目標**: 黒番1手あたり（root待ち＋着手決定）を 4〜6秒 → **3〜3.5秒**（コールド・
別プロセス3run平均）。E2E 全ケースの正答不変が必須ゲート。

**非目標**:
- visits・判定ロジック・クエリ内容の変更（精度に触る変更は一切しない。root 1800v と
  検証 800v は校正済みの床）
- アイドル先読み（`ponder_replies`）の予測改善 — 今回のログで visits 上位予測は
  **3手中3手とも外れ**（予測 H11/L11/K11 系 vs 実際の応手 H6/G5/J5＝全部直前の黒石への
  接触手）だが、ユーザーが即打ちだと温める時間自体がほぼ無いので効果が薄い。
  接触手ヒューリスティック（直前の黒石の隣接点を先読み集合に加える）は**将来の低優先度
  候補**としてここに記録だけする
- 枠採否判定（2.8秒・問題あたり1回）の短縮

## 3. 設計原則

- **実クエリと判定は現状のまま**。`_generate_move` → score_best 検証 → 救済 → コウ経路検査の
  流れ・クエリ内容・待ち合わせ・タイブレーク・ログは変えない
- 新規要素は**手番内投機（in-turn speculation）**だけ: 「この後の段で撃つことになりそうな
  子局面クエリ」を同一条件で先回り発行し、**結果は捨てる**。実クエリが同一条件で再クエリ
  するとキャッシュヒットで 0.1〜0.3秒
- 投機クエリは使い捨て sim の子ノードに紐づけ（`_region_prefetch_sim` と同じパターン）、
  **`generate_move` の finally で node 単位 terminate**（次のノード解析とGPUを取り合わない）
- 優先度は新定数 `PRIORITY_TSUMEGO_SPECULATION = 500`: 実クエリ（10010）と通常ノード解析
  （1010）より**下**、アイドル先読み（-40/-50）より上。実クエリのスロットを奪わず、
  ユーザーが即打ちしたときも新局面の root 解析（1010）が投機に勝つ

## 4. 段階1: 救済スーパーセットの同時温め

`select_tsumego_move` が選択手を返した直後（score_best 検証バッチの発行前。検証が発動しない
手番でも発火する）に、**救済候補になり得る手**の子局面を温める
（同一条件: `gain_verify_visits`=800・ownership=True・untilDepth=1・wRN=0.04）。

救済の最終リスト（`tsumego_rescue_candidates`）は選択手確定後でないと決まらないが、
**選択手非依存のスーパーセット**が root 解析だけから計算できる:
gain 降順トップ `TSUMEGO_GAIN_RESCUE_MAX_CANDIDATES`(3) ＋ visit比フロア
`TSUMEGO_GAIN_RESCUE_MIN_VISIT_RATIO`(0.15) ＋ min_visits を通る非 contender。

ヒット時: 救済段 約1.5秒 → 約0.3秒。今回のログでは4手中2手で救済が発動しており、
どちらもこの集合に入っている。

## 5. 段階2: コウ経路検査の温め

同じタイミングで、**最終選択手になる可能性が高い上位2手**＝投機時点の選択手
（`select_tsumego_move` の結果）＋目数最善（同一手なら1手）のコウ検査条件の子局面を温める（同一条件: 800v・wRN=0（`TSUMEGO_KO_SCREEN_WIDE_ROOT_NOISE`）・
untilDepth=6（`TSUMEGO_KO_REGION_UNTIL_DEPTH`）・ownership=True）。

ヒット時: 検査段 約1秒 → 約0.3秒。ミス時は従来どおりコールドで撃つだけ（劣化なし）。
`_declass_target_confirmed` / 格上げ経路（ud=12）は発火が稀なので温めない（YAGNI）。

## 6. 段階3: root 部分結果からの前倒し発火（段階1+2の計測後に判断）

root リージョン解析は `reportDuringSearchEvery=1` で毎秒部分結果が来る。root の
`TSUMEGO_SPECULATION_ROOT_FRACTION = 0.67`（1800v なら約1200v）時点の候補手で
段階1・2の温め集合＋**検証バッチ本体の子局面**を仮計算して発火し、判定は従来どおり
最終 1800visits の値だけで行う。セットがずれた分はミスとして捨てる。

効果: 検証バッチ実クエリも温まった状態で走り、着手決定が root 完了後 0.7〜1.5秒に縮む。
懸念は root 探索末期とのGPU競合1点のみ。発火閾値で競合窓を約1秒に限定し、
**root のウォール時間が伸びないことを実測で確認**してから採用する。
段階1+2 で目標（3〜3.5秒/手）に到達していたら実装しない（YAGNI）。

## 7. エンジン設定（ユーザー手動編集）

`analysis_config.cfg` の `numAnalysisThreads` 4 → 8。投機込みで同時5〜8本になるため、
4のままだと2周に分かれて重畳効果が半減する。編集はランタイム設定の手動管理ルールに従い
**ユーザーが行う**。編集後、単発クエリ（root 1800v）のレイテンシが混雑で伸びないかを実測し、
伸びるなら 6 に戻す。CLAUDE.md の「numAnalysisThreads=4」記述も更新する。

## 8. ログ・検証・成功基準

- 投機の発火/ヒット/ミスを `OUTPUT_DEBUG` で1行ログ（誤答調査時に「投機は判定に無関係」を
  ログだけで確認できるように。発火集合と実クエリ集合の突き合わせが読める形式）
- 回帰: `e2e_suite.py --full` 正答不変（必須ゲート）。E2E は `generate_move` を通るので
  手番内投機も実行経路に乗る
- 時間計測: 同一問題・**別プロセス**3run で「root ウォール＋着手決定」を前後比較
  （同一プロセスの再クエリは独立サンプルにならない。run1 のエンジン起動込みは比較から除外）
- 成功基準: 黒番1手あたり 3〜3.5秒（コールド）。正答は全ケース不変

## 9. 実装順

1. 段階1＋2（投機発行機構・terminate・ログ込み） → E2E 回帰＋時間計測
2. numAnalysisThreads=8（ユーザー編集） → 単発レイテンシ確認＋再計測
3. 目標未達なら段階3 → 回帰＋root ウォール非劣化の確認

## リスクと対策

| リスク | 対策 |
|---|---|
| 投機が実クエリのGPUスロットを奪う | 優先度 500（実クエリ 10010・ノード解析 1010 より下）＋ finally で terminate |
| ミスした投機の無駄GPU | もともと直列待ちで遊んでいた時間帯。実害はワットだけ |
| numAnalysisThreads=8 で単発クエリが遅くなる | 前後で root 1800v の単発レイテンシを実測、劣化なら 6 |
| 段階3で root 探索末期が遅くなる | 発火閾値 0.67 で競合窓を限定、root ウォール非劣化を採用条件にする |
| 温め条件のずれ（visits/wRN/ud/ownership の不一致）でキャッシュ全ミス | 実クエリと同じ定数・設定値から組み立てる（`ownerMap の有無を区別する` 実測 2026-08-01 の教訓を踏襲） |

### 時間計測: 環境上の落とし穴（2件・本タスクで新規発見）

**(1) site-packages の `_katrain.pth` が worktree を跨いで固定解決する**。
`C:\...\Python312\Lib\site-packages\_katrain.pth` は `C:\Users\iwaki\Documents\katrain-1.17.1.1\
katrain-1.17.1.1`（＝このリポジトリの HEAD チェックアウト）を無条件に登録するエディタブル
インストールで、`python <script>.py` 実行時は `sys.path[0]` がスクリプト自身のディレクトリに
なる（cwd ではない）。base worktree 側でスクリプトを実行しても、その場所に `katrain` パッケージ
が無ければ Python は次に `.pth` 経由で登録された HEAD のパスを見つけて **そちらを import する**
（実測: `sys.path[0]` をスクリプト自身のディレクトリに固定した状態で `import katrain` すると、
base worktree の cwd から実行しても `katrain.__file__` は HEAD のパスに解決された）。
`PYTHONPATH=<対象worktreeのルート>` を明示すれば `.pth` より先に解決されて正しい worktree の
コードが使われる（実測で確認）。**全呼び出しに `PYTHONPATH` を明示**して対処し、`self._fire_
speculation(` 文字列の有無と実ログの `投機温め:` 行の有無（base=0件・HEAD=有り、6ログ全件で
確認）で worktree 分離を検算した。

**(2) base worktree にモデル重みが無い**。`config.json` の `"model"` 値は相対パス
`katrain\models\kata1-....bin.gz`（`.gitignore` 対象・97.9MB）で、worktree ルート相対に解決される。
`git worktree add` は gitignore 対象ファイルを複製しないため base 側には実体が無く、初回実行時は
エンジンが `Initializing neural net buffer` 直後にクラッシュし、`Exception in reading stderr:
'KaTrainStub' object is not callable` からの無限リトライで数千行/417KBのログを吐きながら
自動バックグラウンド化した（プロセス kill・ログ破棄で復旧、詳細は「懸念」節）。HEAD_ROOT から
モデルファイルをコピーして解消（gitignore 対象のデータファイルのみ・コード変更なし）。

### 投機ヒットの実測（クエリレベル突合）

speculative（priority=500）クエリと、直後に発行された同条件 real（priority=10000）クエリを
(untilDepth, wideRootNoise, includeOwnership, 直前手, 手数) で突合:

| ケース | spec発行数 | 突合real数 | 突合realの応答時間 |
|---|---|---|---|
| M | 6 | 3 | 0.8秒（run1）／0.1・0.1秒（run2/3） |
| O | 3 | 3 | 0.8秒（run1）／0.0・0.0秒（run2/3） |
| V2 | 10 | 6 | 0.9・1.2・0.6・0.7秒／0.2・0.1秒 |

run2/3（プロセスがウォームな後続rep）では M/O とも 0.0〜0.2秒 のクリーンヒットが確認できた一方、
run1 や V2 の一部では 0.6〜1.2秒 と Task 3 実測（0.1秒）ほど劇的でないケースが混在した。原因は
E2E ハーネスが使う **パッケージ同梱 `katrain/KataGo/analysis_config.cfg`**（ランタイムの
`~/.katrain/analysis_config.cfg` とは別ファイル。前者は `numAnalysisThreads=12`、後者は
CLAUDE.md 記載の `4` のまま不一致）が既に 12 で動いており、投機と実クエリの発行間隔が短い局面
（コウ脱出等で即座に後続クエリが飛ぶ経路）では両者がほぼ完全並列に実行され、投機側が完了しきる
前に実クエリが飛ぶため部分的にしか NN キャッシュの恩恵を受けない。`own=False` 条件の real query
（投機は常に `own=True` で温める）はミスのまま推移しており、`ownerMap の有無を区別する` ルール
（2026-08-01 実測）はここでも一貫していた。

### 結論: 段階3の要否

本タスクの計測は簡略法（同一プロセス3rep）のため、設計が意図する厳密な別プロセスコールド3run
平均ではない。唯一「エンジン起動済み・まったく新しい局面」に近い純粋なサンプルは V2@2 run1
（root待ち1.3〜1.4秒＋着手決定3.3〜3.7秒＝合計 **4.6秒(HEAD) / 5.1秒(base)**）で、目標
3〜3.5秒には届いていない。M/O/V2 は「救済とコウ経路検査の両方が発火する重経路」に選ばれた
ケースで、生成時間のみで見ればウォーム時（run2/3）は HEAD 側が概ね1〜3秒に収まる一方、root待ちを
含めた合計は依然 3.5秒 を超える局面が残る。段階1+2 はクエリレベルでは明確な高速化（0.0〜0.2秒
ヒット、確認済み）をもたらすが、投機と実クエリの発行間隔が短い局面では並列化との競合で恩恵が
薄まる。**重経路ケースに限っては段階3（root部分結果からの前倒し発火）が目標到達の後押しになる
可能性がある**。ただし 66/69 の大半を占める「通常経路（対抗馬1〜2手・バッチ1本のみ）」は本
タスクの対象外だが、コールド 4.7〜5.4秒 だった旧基準よりそもそも軽いはずで、段階1+2 だけで
目標圏内に収まっている可能性が高い。YAGNI 原則に従い、段階3着手は実際の GUI 体感（コウ絡み
詰碁1問＝黒4手で約20秒だった元の問題）で重経路ケースのボトルネックが実際に残るかを見てから
判断することを推奨する。

### 懸念

- **PYTHONPATH 問題が過去の base 比較（K@0 A/B・progress.md記載）にも及ぶ可能性**: `k_ab.ps1`
  は base 側実行前に `PYTHONPATH` を設定しておらず、上記(1)のとおり `python docs/.../
  e2e_suite.py K` の子プロセス（`generate_move_e2e.py`）も同じ経路で HEAD の `katrain` を
  import した可能性が高い（e2e_suite.py 自身は katrain を import しないため CASES 表示等は
  正常に見えるが、実際の着手生成は誤った worktree のコードで行われていた疑いが残る）。K@0 の
  「base 2/3・既知ナイフエッジで投機起因でない」という裁定は **未検証**（本タスクのスコープ外
  につき再実行はしていない）。次回 base worktree を使う作業では必ず `PYTHONPATH` を明示し、
  可能なら K@0 A/B の再実行を推奨する。
- 上記2件の落とし穴により、base-M の初回実行（PYTHONPATH無し・モデル無し）はエンジンクラッシュ
  後に無限リトライへ入り、Bash ツールの 400秒 タイムアウトで自動バックグラウンド化した
  （`timing-base-M.log` が417KB化）。プロセス kill・ログ削除で復旧し、PYTHONPATH 付与＋モデル
  コピー後に正常完了した。以後の呼び出しは全て 600秒 弱のタイムアウトで直列フォアグラウンド
  実行し、同種の暴走は再発しなかった。
- 計測はケースごとに1プロセス（3rep内蔵）のみで、真の別プロセスコールド3run平均ではない
  （上記「計測方法」参照）。より厳密な数値が必要なら別プロセス3回×各点の再測定を推奨。
