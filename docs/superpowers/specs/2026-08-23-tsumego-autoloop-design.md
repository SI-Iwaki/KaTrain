# 詰碁の自動ループ（tsumego autoloop）設計

作成日: 2026-08-23

## 0. 目的とスコープ

BlueStacks 上の詰碁アプリ「囲碁詰めチャレ」（`fm.wars.goquest`・Flutter 製）を相手に、
**人力ゼロで「出題 → 回答 → 正誤 → （誤答なら）正解手順の収穫 → 次の問題」を回し続ける**。

現状の人力は4点: (1) キャプチャのホットキー押下と役割指定、(2) KaTrain の AI が決めた黒をアプリへ
タップ、(3) 正誤の確認、(4) 誤答時に回答帳へ正解手順を手入力。本機能はこの全部を自動化する。

正答率の目標に対する位置づけ（ブレスト 2026-08-23 の結論）:

- 一次正答率（初見問題）は KataGo パイプラインの精度で頭打ち（回答帳なしリプレイ 58%、
  不一致の 56% は別解・42% は判定不能・真の誤答 1%）。**盤面に情報が無いので改修では上がらない**
- アプリは有限の問題集を回転して再出題する。再出題は回答帳で 100%（0 秒）
- したがって「アプリ側の正答率」は `1 − 初見誤答率 × (1 − 回答帳カバレッジ)` で、
  **ループを回すほど 100% に漸近する**。初見の1回誤答は構造上ゼロにできない
  （ヒント・結果ボタンは不正解後にしか使えない＝事前に正解を知る手段が無い）
- 本機能の価値は「人力ゼロで一晩に数百問を消化し、**誤答1回で確実に収穫して二度と間違えない**」こと

### スコープ内

- ADB によるアプリ操作（タップ）と画面取得、画面状態の判定（問題画面／正解・不正解ポップアップ／ヒント赤丸）
- 新しい問題の検知 → 既存キャプチャの起動 → AI 黒のタップ → 白の応手（既存の自動反映）→ 正誤検知
- 誤答時のヒント歩き（ヒント → 赤丸 → タップ → 白の応手 → … → ヒントのグレーアウト）と回答帳への自動記録
- キャプチャ失敗・ADB 断・想定外画面の記録（台帳）と安全停止
- 1問ごとの台帳 `tsumego_ledger.jsonl`（後でまとめて改善するためのデータ）

### スコープ外（今回作らない）

- 問題 ID（ヘッダ「山田晋次 夕刊フジ出題問題(16)」）の OCR。台帳にはヘッダの切り出し画像ハッシュだけ残す（§8）
- 一次正答率を上げる改修（別 spec の領域）
- 役割の学習器（実測 3.7% の誤りはループが吸収する。§1）
- `BoardWatcher` の画像ソースを ADB フレームへ差し替えること（窓の隠れ対策。§13）
- Web 詰碁（PlayGo 等）の自動化

### 決定事項（ユーザー確認済み 2026-08-23）

| 項目 | 決定 |
|---|---|
| アプリ操作 | **ADB 一本**（`HD-Adb.exe`・`127.0.0.1:5585`）。Win32 入力は使わない |
| 役割 | 自動推定のまま打つ（ホットキー相当は `role=None`）。外れたら誤答→収穫で吸収 |
| 初見問題 | 自力で解く（結果・ヒントは不正解後のみ使える） |
| 誤答時 | 問題を見る → 戻す（初期局面まで）→ ヒント→黒タップ→白応手 を**最後の正解手まで**繰り返す → 記録 |
| 収穫の終了条件 | ヒントボタンのグレーアウト（「勝利」の赤字は一瞬なので使わない） |
| キャプチャ失敗 | 解かないと次へ進めないので、**わざと1手打って不正解にし**、読めれば収穫・読めなければ台帳に残して次へ |
| 回答時間 | アプリの **30 秒制限**は初見問題の一次回答だけに効く。ヒント歩きと回答帳再生は対象外 |
| 問題集 | 有限（出典・番号つき）。サーバからの取得はしない |

## 2. 全体構成

```
[BlueStacks: 囲碁詰めチャレ]
   ^  input tap (ADB)                       |  画面（2系統）
   |                                         v
   |                          (a) 窓キャプチャ ImageGrab ──> BoardWatcher（既存・白の自動反映・20ms/周）
   |                          (b) ADB screencap 0.5s/枚 ──> AutoLoop の画面状態判定・ヒント赤丸・収穫時の盤読み
   |
AutoLoopController スレッド (katrain/core/tsumego_autoloop.py)   ← 新規・Kivy 非依存
   |  状態機械（§3）／ADB クライアント／画面判定（§4）／座標変換（§5）／収穫（§6）／台帳（§8）
   |
   |  コールバック（既存のメッセージループ経由）
   v
KaTrainGui (__main__.py)
   - 新しい問題 → `_tsumego_capture_trigger(role=None)` を直接呼ぶ（ホットキーと同じ入口）
   - キャプチャ完了 → `on_problem_ready(game)`（`_do_tsumego_capture_apply` 末尾に1行）
   - AI が黒を打った → `on_black_move(move)`（`_do_ai_move` の `generate_ai_move` 直後に1行）
   - 収穫した手順 → `_save_answer_line(game, moves)`（記録ボタンの保存分岐を関数に切り出して共用）
```

画像ソースを2系統に分ける理由: 白の応手の取り込みは既存の `BoardWatcher`（窓キャプチャ・1周 20ms）が
低遅延で動いており触らない。一方 UI 状態・赤丸・ポップアップの分類はテンプレートを**デバイス解像度
（900×1600）で固定**したいので ADB フレームを使う（窓キャプチャは BlueStacks の窓サイズ・DPI で
解像度が変わる）。ADB フレームは 0.5 秒/枚だが、ポップアップ検知と収穫は遅延に敏感でない。

## 3. 状態機械

```
IDLE ──(ホットキー ON)──> AWAIT_PROBLEM
AWAIT_PROBLEM: ADB フレームを 2Hz で読む。ポップアップ無し かつ 盤に石がある かつ
               盤グリッドが「前問の初期グリッド」「前問の最終グリッド」のどちらとも違い、2 フレーム連続で同じ → CAPTURING
CAPTURING:     `_tsumego_capture_trigger(role=None)` を呼び、`on_problem_ready` を待つ（上限 15 秒）
               失敗（CaptureError）→ CAPTURE_FAILED
ANSWERING:     `on_black_move(move)` を受けるたびに盤座標→デバイス座標でタップ。
               白は既存 BoardWatcher が KaTrain へ注入し、AI が次の黒を決める（既存の流れ）。
               ADB フレームでポップアップを監視 → RESULT
               開始から 40 秒経ってもポップアップが出ない → STALLED（§9）
RESULT:        ポップアップを 正解／不正解 に分類（§4.2）→ 台帳に記録
               正解  → NEXT
               不正解 → HARVEST
CAPTURE_FAILED: 盤が一部でも読めていれば空点を1つタップ、読めなければ盤の中央付近を1点タップして 30 秒待つ
               （**タイムアウトが不正解ポップアップになるかは未確認**＝実装時に確認。ならなければ空点候補を数点試す）
               → ポップアップ（不正解）→ HARVEST（読めれば）／NEXT（読めなければ台帳にスクショ）
HARVEST:       問題を見る → 戻す×N（盤 == 初期グリッドになるまで・上限 20 回）
               → [ヒント → 赤丸検出 → タップ → 盤が安定するまで待つ（黒＋白の応手）→ 手順に追記] を
                 ヒントがグレーになるまで繰り返す（上限 40 手）→ `_save_answer_line` → NEXT
NEXT:          ポップアップが出ていれば「次の問題」、問題画面なら下バーの「次の問題」をタップ → AWAIT_PROBLEM
STALLED / ERROR: 台帳にスクショと状態を記録。連続 N 回（既定 3）で IDLE へ（ホットキーで再開）
```

ホットキー OFF はどの状態からでも IDLE（進行中のタップは打ち切り。KaTrain 側の局面には触らない）。

## 4. 画面判定（ADB フレーム・900×1600）

### 4.1 領域の定義

座標は**デバイス座標の比率**（0..1）で設定に持つ（既定値はこのアプリの実測。BlueStacks の解像度を変えても
比率なら追従する。比率でも合わなくなる＝アプリの UI 更新時は設定で直す）:

| 要素 | 既定（x, y） | 用途 |
|---|---|---|
| 下バー: 次の問題 | (0.472, 0.784) | タップ |
| 下バー: 結果 | (0.586, 0.784) | 使わない（参考） |
| 下バー: ヒント | (0.833, 0.784) | タップ／グレー判定（アイコン領域の平均輝度・彩度） |
| 下バー: 戻す | (0.933, 0.784) | タップ |
| ポップアップ: 次の問題 | (0.256, 0.781) | タップ |
| ポップアップ: 問題を見る | (0.489, 0.781) | タップ |
| ポップアップ: × | (0.886, 0.158) | 使わない（問題を見るで閉じる） |
| ポップアップ: 判定文の帯 | y 0.29〜0.35・x 0.1〜0.9 | 正解／不正解の分類 |
| ヘッダ（出典・番号） | y 0.15〜0.18・x 0.1〜0.9 | 台帳の画像ハッシュ |
| 盤 | `detect_board(frame)` で毎回検出 | 石の読み取り・タップ座標 |

### 4.2 ポップアップの有無と分類

- **有無**: 盤の中央付近（問題画面なら木目の黄色）が、ポップアップでは紙色（白〜薄灰）に変わる。
  `_is_yellow` 判定の画素比率で判定（既存関数の流用）。さらに `detect_board` が盤を返さない、を補助条件にする
- **分類**: 判定文の帯をテンプレート（正解「…の問題を解きました！」／不正解「…の問題が不正解でした・・」の
  **固定部分だけ**＝難易度の数字が変わる先頭を避けた右側の切り出し）と平均絶対差で比較する。テンプレートは
  `katrain/assets/autoloop/` に PNG で同梱（デバイス解像度で撮ったもの。不正解は 2026-08-23 取得済み、
  正解は実装時に1枚撮る）。両方に似ない／両方に似る → `unknown` として台帳にスクショを残し、
  **正解扱いで次へ進む**（収穫を誤って走らせない側に倒す。ヒントが押せなければ収穫は即終了するので
  逆に倒しても壊れないが、未知画面で「問題を見る」「戻す」を叩くほうが危険）
- 依存は PIL のみ（既存キャプチャと同じ。numpy/OpenCV は環境に無い）

### 4.3 ヒントの赤丸

色閾値（§1）で赤画素を集め、連結成分の外接箱が**盤の1交点の直径程度**（cell×0.6〜1.2）のものを赤丸とする。
盤の交点へは `detect_board` の盤矩形と盤サイズから最近傍で写像する。複数見つかった／見つからない → 台帳に残して
収穫中断（NEXT へ）。

### 4.4 ヒントボタンのグレーアウト

アイコン領域の平均彩度／輝度で「白（有効）」「灰（無効）」を分ける。閾値は実装時に有効・無効の両フレームから
取り、`tests/` に両フレームを置いて固定する。**ヒント押下後 1.5 秒以内に赤丸が現れない**ことも終了条件に
AND する（グレー判定の誤りで無限ループしない）。

## 5. 座標変換とタップ

- 盤座標 (i, j) → デバイス座標: ADB フレームで `detect_board` した盤矩形と盤サイズから線形に求める
  （既存 `classify_intersections` と同じ格子の式）。KaTrain の着手 `Move` → `move_to_grid` → (i, j)
- タップ: `adb -s <serial> shell input tap x y`（0.17 秒）。1タップごとに次のフレームで効果を確認する
  （石が現れた／ポップアップが閉じた／赤丸が出た）。効果が無ければ 1 回だけ再タップ、それでも無ければ台帳に残す
- タップ先は**常に BlueStacks の Android 画面の中**。デスクトップへの入力は一切送らない（Win32 入力 API を使わない
  ことで構造的に保証）
- 盤の回転：アプリは同じ問題を回転・鏡映して出すが、タップはその時点の盤座標で行うので無関係

## 6. 収穫（ヒント歩き）の手順と記録

```
base = game.tsumego_app_grid            # キャプチャ時の認識グリッド（アプリ盤の座標系）
key  = game.tsumego_book_key            # 同じキャプチャで計算済み（回答帳の照会キー）
tap 問題を見る; 待つ(ポップアップが消える)
repeat ≤20: 読む; if grid == base: break; tap 戻す; 待つ
assert grid == base  （違えば台帳に残して NEXT）
moves = []
loop ≤40:
    tap ヒント; 待つ(≤1.5s) 赤丸
    if 赤丸なし and ヒントが灰: break      # 終了
    (i,j) = 赤丸の交点; tap (i,j)
    expected = apply_move_to_grid(grid, i, j, "B")    # 既存関数（取りも反映）
    待つ: 観測 grid が expected を含み、かつ 2 フレーム連続で不変（白の応手まで落ち着く）
    diff = 観測 − expected（白石の増分）
    moves.append(((i,j),"B")); if diff == 1石: moves.append((w,"W")); grid = 観測
    else if diff が 0: grid = expected       # 白が応じない＝最終手
    else: 台帳に残して break（読めない）
_save_answer_line(game, moves)   # 記録ボタンの保存分岐と同じ（canonicalize の変換 t・moves_to_canonical・add_line・keep_current_log）
```

- 白の応手は**アプリ盤の差分**で取る（KaTrain の `BoardWatcher` は収穫中は止める。戻す操作で盤が初期局面に
  戻るので、動かしたままだと `Mismatch` を出し続ける）
- 収穫の最終手が白で終わる場合もそのまま記録する（`add_line` の条件は「黒番始まり」だけ）
- 記録手順は次回から回答帳の再生で 0 秒・100% になる（既存機構）。白の応手が記録と違う再出題では
  従来どおり通常パイプラインに落ち、誤答すれば別 line として追記される（`lines` は複数持てる）

## 7. KaTrain 側の接続点（変更は最小）

| 箇所 | 変更 |
|---|---|
| `__main__.py` ホットキー表 | `tsumego_autoloop.hotkey`（既定 `ctrl+alt+a`）を追加。`Theme.KEY_*` と重ねない制約は既存どおり |
| `_tsumego_capture_trigger` | 変更なし。AutoLoop は `role=None, frameless=False` で直接呼ぶ（2 秒デバウンスはそのまま効かせる） |
| `_do_tsumego_capture_apply` 末尾 | `self._autoloop.on_problem_ready(self.game)` を1行（`tsumego_app_grid` / `tsumego_book_key` が載った後） |
| `_tsumego_capture_failed` | `self._autoloop.on_capture_failed(message)` を1行 |
| `_do_ai_move` | `generate_ai_move` の返り値の `move` を `self._autoloop.on_black_move(move)` へ（黒番・詰碁中のみ） |
| `_do_tsumego_record_toggle` の保存分岐 | `_save_answer_line(game, moves, source)` に切り出し、ボタンと AutoLoop で共用 |
| `_stop_board_watcher` | 収穫に入る前に AutoLoop が呼ぶ（既存 API のまま）。再開は不要＝次の問題のキャプチャが `_start_tsumego_watch` を呼ぶ |
| 盤上バナー | 既存 `_tsumego_message` で状態を出す（「自動ループ: 12問目 正解 9 / 誤答 3 / 収穫 3」） |

AutoLoop 本体（`katrain/core/tsumego_autoloop.py`）は Kivy 非依存で、GUI への作用はすべてコールバック
（`trigger_capture` / `save_line` / `stop_watch` / `start_watch` / `notify`）経由。純関数（画面判定・座標変換・
差分→手順）は単体テスト可能な形に分ける。

## 8. 台帳 `~/.katrain/tsumego_ledger.jsonl`

1問1行。後から「どこで落ちたか」をまとめて見るためのもの（既存の1問1ログ `tsumego_*.log` は従来どおり）。

```json
{"ts": "2026-08-23T06:30:12", "key": "<sha1|null>", "size": 13, "route": "book|ai:tsumego|ai:tsumego_solver|null",
 "outcome": "correct|wrong|error|capture_failed|unknown_popup|stalled",
 "elapsed_s": 17.4, "n_black": 4, "harvest": "saved|duplicate|skipped:<理由>|null", "line_len": 7,
 "header_hash": "<sha1 先頭16桁|null>",
 "shots": ["C:\Users\...\.katrain\logs\autoloop\20260823_063012_001_stalled.png"],
 "log": "tsumego_20260823_063001.log"}
```

実装との対応（2026-08-23 の最終レビューで揃えた）: `route` は**回答帳ヒットなら `book`、それ以外は
黒の `player_subtype` 文字列**（`ai:tsumego` / `ai:tsumego_solver`。枠あり／枠なしの別は持たない）。
`shots` は `_save_shot` が返す**絶対パス**（`shots_dir` 直下・`<日時>_<連番>_<タグ>.png`）。`role_guess` は
**記録しない**（枠の役割推定は自動ループの外の判断で、コントローラからは見えない）。`header_hash` は
AWAIT→CAPTURING へ入るフレームのヘッダ帯（`vision.header_hash`）で、キャプチャできなかった問題にも付く。
`log` はその問題の詰碁ログのファイル名（`_game_log_path` の basename）で、台帳から 1問1ログ を引くための鍵。

- スクショは `~/.katrain/logs/autoloop/` に、**正常系では保存しない**（失敗・unknown・stalled のときだけ）
- `header_hash` はヘッダ帯の 32×4 縮小グレースケールの sha1 先頭16桁。同じ出典・番号なら同じ値になるので、
  回答帳キーが認識ずれで外れた回の追跡に使う（OCR は §13）
- 保持: 追記のみ。ローテーションしない（1行 300B・1万問で 3MB）

## 9. 失敗処理と安全弁

| 事象 | 扱い |
|---|---|
| ADB 未接続／切断 | 起動時に `connect`＋`devices` で確認。失敗なら開始しない。途中で `input tap` が失敗したら 1 回再接続、だめなら ERROR→IDLE |
| キャプチャ失敗 | §3 CAPTURE_FAILED。空点を1つタップして不正解にし、読めれば収穫 |
| ANSWERING 40 秒超でポップアップ無し | STALLED。スクショ。次のフレームでポップアップが出れば RESULT に復帰、出なければ 次の問題 を試す |
| unknown ポップアップ | 正解扱いで NEXT（§4.2） |
| 収穫の途中失敗（赤丸なし・盤が読めない・戻せない） | `harvest: skipped:<理由>`、そのまま NEXT。**部分手順は保存しない**（中途半端な line は再生時に「記録外」へ落ちるだけで害は小さいが、正解として残すものではない） |
| 連続失敗 | ERROR/STALLED が連続 3 回で IDLE（暴走防止）。バナーとログで通知 |
| 上限 | 1問あたりタップ上限 60・収穫上限 40 手・問題数上限 `max_problems`（0=無制限） |
| 停止 | ホットキー OFF／KaTrain 終了／新規対局。停止時は進行中の操作を打ち切るだけで、アプリ側は触らない |

**30 秒制限**: 初見問題の予算は キャプチャ（1〜3 秒・ソルバ検算 +1 秒）＋ 黒1手あたり（着手決定 0.5〜5 秒 ＋
タップ 0.2 ＋ アプリの白 ≈0.5 ＋ 注入 0.1〜0.45）。5 手の手順で典型 10〜18 秒、重経路コールドで 30 秒に
届きうる。超過はアプリが不正解にし、ループは通常の誤答として収穫する（タイムアウト専用の処理は要らない。
台帳の `elapsed_s` と `outcome` で頻度を見て、多ければ別途 visits 等を詰める）。

## 追記2（2026-08-23）— 認定証オーバーレイ（未知のフルスクリーン画面からの脱出）

段位が上がるとアプリは「認定証」を出す（紙色の背景・金の装飾・左上に ×）。**この節と追記4 が「フルスクリーン画面」「× は画面の左上」と書いているのは誤りで、追記5 で訂正した**（実機は問題画面の上に載るダイアログ）。盤が覆われるので `popup_present` は真になり、判定文が無いので RESULT は unknown → 正解扱い → NEXT → `popup_next` をタップ → 効かない → AWAIT → popup → NEXT … と**無限にタップし続けていた**（`_step_await_problem` は popup を見た瞬間 NEXT へ行くので AWAIT の締切に届かない）。

対策は 2 段。(1) `overlay_present`＝「popup_present ∧ タイトル帯が紙色（平均輝度 >= `OVERLAY_TITLE_LIGHT_MIN`=160。実測 結果ポップアップの濃紺帯 81〜100 / 認定証 247）∧ 左上に × がある」（**この署名と探索窓は追記5 で入れ替えた**＝切り抜き fixture から校正したため実機では常に偽だった）なら、`_step_result` / `_step_await_problem` / `_step_next` の先頭で `find_close_glyph` の点をタップして 1 周待つ（状態は変えない・`OVERLAY_MAX_TAPS`=5 を超えたら失敗として打ち切る）。`find_close_glyph` は左上の暗画素の bbox 中心だが、**素の「R+G+B<450」では金の装飾枠が混ざって bbox が 22x22 → 54x53 に膨らみサイズ判定を外す**ので、暖色（R−B > `CLOSE_GLYPH_WARM_MAX`=40。実測 × は −6・金は +78）を数えず、y も最初の暗行から 90px（900 幅基準）で切る。fixture は `tests/data/autoloop/certificate.png`（実機窓の切り抜き 505x657＝**縦横比が実機 900x1600 と違う**ので px 閾値はフレーム幅の比でスケールする）。(2) 種類を問わない保険として `_step_next` の連続タップを数え、`NEXT_MAX_TAPS`=4 を超えたら × 相当の点（見つからなければ比率 (0.045, 0.035)）を 1 回タップ、2 倍を超えたら `_error_step` で打ち切る（AWAIT で石のある盤が読めたら 0 に戻す）。

## 追記3（2026-08-23）— 複数インスタンスの接続先選択

複数の BlueStacks インスタンス（`bluestacks.conf` の adb_port 5555/5565/5575/5585）がある環境では、
`discover_serial` が「最初に `devices` へ device で応答した port」を返すため、詰碁アプリが前面に
無いインスタンスへ誤接続することがあった。`AdbClient.foreground_package()`（`dumpsys window` の
`mCurrentFocus=`/`mFocusedApp=` 行から `u0 <pkg>/` を読む）を追加し、`discover_serial` は応答した
serial を全部集めてから前面パッケージが `fm.wars.goquest`（`APP_PACKAGE`）のものを優先して返す
（一致が無ければ従来どおり最初の1本）。`__main__._autoloop_find_serial` は前回記憶した serial も
同じ確認をしてから使い、外れていれば discover へフォールバックする。`tsumego_autoloop.adb_serial`
を明示指定した場合はこの探索を通らず、指定値をそのまま使う（`_autoloop_trigger_locked` が
`settings.adb_serial or self._autoloop_find_serial(settings)` で分岐）。

## 追記4（2026-08-23）— 誤タップ防止（結果ポップアップの署名・当てずっぽうのタップ廃止）

実機で認定証がフェード中に × を連打し、認定証が消えた後の**問題画面のヘッダの ← 戻る**（≒(40,80)/900x1600）を押してアプリがホームへ戻る事故が出た。原因は 3 つ: (1) `popup_present` が「盤の上端が黄色でない」だけなので、ホーム・遷移中・認定証まで結果ポップアップ扱いになり `popup_next` を撃っていた、(2) `_handle_overlay` が検出 1 フレーム目から連続でタップしていた、(3) NEXT の上限超えに `CLOSE_FALLBACK_POINT`(0.045,0.035) の**盤面を見ない**タップがあり、その座標が問題画面では ← 戻るだった。

対策: (1) `result_title_band_dark`（`OVERLAY_TITLE_BAND` の平均輝度 < `RESULT_TITLE_DARK_MAX`=140）を結果ポップアップの署名として `popup_present` に AND する。実測 popup_wrong / popup_correct **81.1**・出現途中 100.5 に対し認定証 **247.2**（140〜160 は「濃紺でも紙色でもない」不感帯＝どちらの経路もタップしない）。**問題画面 53.7・遷移 43.5 もアプリの青ヘッダで暗い側**なので帯だけでは問題画面と分離できず、そこは従来どおり黄色帯の条件が担う。`overlay_present` は「黄色でない ∧ 濃紺でない ∧ 紙色(>=160) ∧ × が見える」（**追記5 で訂正**＝認定証はダイアログなのでこの帯はその上に残るヘッダ＝実測 44.5 で「濃紺でない」が成立せず、実機では一度も真にならなかった）。(2) `_handle_overlay` は `OVERLAY_MIN_FRAMES`=2 連続で確認してから 1 回タップし、次まで `max(OVERLAY_TAP_WAIT_S=1.5, 2×settle)` 待つ。上限は `OVERLAY_MAX_TAPS` 5→**3**、`find_close_glyph` が None なら 1 回も押さない（オーバーレイでないフレームでカウンタは 0 に戻る）。(3) `CLOSE_FALLBACK_POINT` は**削除**し、NEXT は `NEXT_MAX_TAPS`(4) 超で即 `_error_step("next: ポップアップが閉じません")`。(4) AWAIT の締切再タップは `board_rect` が読めるフレーム（＝問題画面）に限り、読めなければ「盤が見えない画面です（タップしません）」を出して `unknown_screen` のスクショを 1 枚残すだけにする（2 回目の締切超過で従来どおり `_error_step`）。**知らない画面では 1 タップも撃たない**が新しい不変条件。

`popup_present` にはさらに3つ目の AND 条件として中央の内側の小盤の黄色率 `POPUP_INNER_BOARD_BOX` `>= POPUP_INNER_BOARD_YELLOW_MIN`(0.5) を追加した（結果ポップアップは必ずここに小盤を出す。実測 popup_wrong 0.87 / popup_correct 0.83 / animating 0.86 に対し認定証 0.0＝盤の無いホーム・メニュー画面を確実に除外する）。`_handle_overlay` は `_step_answering` / `_step_stalled` の先頭でも呼ぶ（従来の AWAIT_PROBLEM/RESULT/NEXT に加え）＝認定証の署名は結果ポップアップと無関係なので、先頭で割り込まないと answer_timeout_s(40秒)→STALLED→STALL_EXTRA_S(60秒) を丸ごと待ってからしか閉じにいけない。
## 追記5（2026-08-23）— 認定証の**実機ジオメトリ**（ダイアログだった）

追記2/追記4 の検出は**切り抜きのスクショ（505x657）から校正しており、実機では別の帯を見ていた**。実機の全画面スクショ（900x1600・`tests/data/autoloop/certificate_device.png`）で実測したジオメトリ: 認定証は**フルスクリーンではなく問題画面の上に載るダイアログ**（y 0.175〜0.83・紙色・盤は見えない）で、アプリのヘッダ（左上の ← 戻る ≈(0.045, 0.05)・「囲碁詰めチャレ」・難易度/出典 y≈0.16）はその上に残る。閉じる **× はダイアログの左上 ≈(0.09, 0.20)**、シェアする ≈(0.88, 0.20)。つまり旧実装の探索窓（x 0〜0.13 / y 0.005〜0.10）が見ていたのは**ヘッダの ←**で、ここを押すとアプリがホームへ飛ぶ（追記4 の事故そのもの）— **この点は決してタップしない**。

新しい署名（`overlay_present`）は 4 つの AND: 盤の上端の黄色帯が消えている（`POPUP_STRIP` < 0.5。実測 0.017）∧ 中央に結果ポップアップの小盤が無い（`POPUP_INNER_BOARD_BOX` < `OVERLAY_INNER_BOARD_YELLOW_MAX`=0.2。実測 0.0 / 結果ポップアップ 0.83〜0.87）∧ ダイアログの紙の帯が明るい（`OVERLAY_PAPER_BAND`=(0.2,0.25,0.8,0.28) の平均輝度 >= `OVERLAY_PAPER_MIN`=200。実測 247.2）∧ `find_close_glyph` が × を見つけている。**旧条件の「タイトル帯が紙色（>= `OVERLAY_TITLE_LIGHT_MIN`=160）」は削除**した— `OVERLAY_TITLE_BAND` はダイアログの上に残るアプリのヘッダなので認定証でも**濃紺（実測 44.5）**で、この条件は実機で常に偽だった（切り抜き fixture だけが 247.2 を返していた）。`popup_present` は変更なし（第3項の内側の小盤 >= 0.5 が認定証を既に除外している）。

`find_close_glyph` の探索窓は `CLOSE_GLYPH_BOX`=(0.04, 0.17, 0.125, 0.225)＝**ダイアログの左上だけ**。暗画素（R+G+B<450）かつ非暖色（R−B<=40＝金の装飾を落とす）の bbox を採り、サイズ判定を **12〜70px**（900 幅基準・`frame.size[0]/900` でスケール。実測 × は 36x35px）とする。窓の上端にはヘッダの暗い帯が、左端にはダイアログ外の暗い背景が掛かるので、**bbox が判定を外れたら 8 近傍の塊に分けて判定に収まる最も左上の塊を採る**（UI の帯は窓の幅いっぱいに伸びるので上限で、ダイアログ外の縁は幅が足りず下限で落ちる）。実測: fixture で (80, 309)＝比率 (0.089, 0.193)、**問題画面（problem.png）では None**（← を × と取り違えない）。旧 fixture `certificate.png`（切り抜き 505x657）はジオメトリが実機と別物で新しい署名を満たさないので**削除**し、全アサーションを `certificate_device.png` に移した（検出器を切り抜きに合わせて曲げない）。`_handle_overlay` の振る舞い（2 フレーム連続確認・1.5 秒待ち・`OVERLAY_MAX_TAPS`=3）は変更なし。
