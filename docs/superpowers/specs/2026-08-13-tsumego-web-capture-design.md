# Web サイト詰碁キャプチャ（格子線＋座標ラベル方式）設計・実測記録

日付: 2026-08-13
対象: `katrain/core/tsumego_capture.py`（Web 認識ブロック）・`katrain/core/tsumego_capture_glyphs.py`・`katrain/__main__.py`（トリガー分岐＋全体表示適用）
校正データ: `docs/superpowers/specs/calibration-data/tsumego-web/`

## 背景・要件

詰碁キャプチャは BlueStacks 上の詰碁アプリ専用の認識（「黄色領域の縁＝盤の端、第1線は半セル内側」の規則配置）だったが、ユーザーが PlayGo.gg（playgo.gg 詰碁ラン）でも使いたいという要望。実スクリーンショット2枚で確認した Web 盤面の構造差は:

1. **座標ラベル帯が黄色領域の内側にある**（A〜T・1〜19、帯幅約1セル）。既存方式では全交点が約半セルずれ、盤サイズ判定が全滅する（実測 格子線スコア 9:0.20 / 13:0.04 / 19:0.13、全部閾値 0.5 未達）
2. **問題に合わせて盤の一部だけを表示する（部分表示）**。9路ボス問題の実測: 右端の J 列の線と下端の 1 の線が表示領域の外（格子間隔 101.7px から外挿すると縁の約 9px 外）
3. ユーザー要件: **全体表示（盤全体が見えている）は詰碁ではなく盤面把握＝最善手問題**なので、枠・リージョン・ai:tsumego を通さず**通常モードの解析**に回す。**肝心の詰碁は部分表示が多い**ので、部分表示は絶対座標を復元して既存の詰碁パイプラインへ

## 設計

### 認識（tsumego_capture.py の Web ブロック）

- **入口 `recognize_board`**: 既存方式 `detect_size_and_classify` を先に試し、CaptureError のときだけ Web 方式へフォールバック。BlueStacks 経路はビット単位で不変（実測: 既存サンプル3枚とも kind="app" のまま、既存テスト全パス）
- **格子線検出**: 「細い暗線」プロファイル＝両側 `WEB_THIN_GAP`(6px) が非暗の暗画素だけを行/列ごとに数える。石・影・木目の太い暗塊は両側チェックで構造的に落ちる。閾値 `WEB_LINE_MIN_FRACTION`(0.25) 以上の連続帯を線候補にし、`_web_fit_uniform` で等間隔グリッドにフィット（内側の欠け＝石で隠れた線は補間、縁のアーティファクトは等間隔に乗らない外れ値として捨てる）。さらに `_web_extend_hidden_lines` が端の線の完全埋まり（1線が石で満杯）を外挿+石色検査で救う
- **辺の可視判定**: 最外線の外側 0.55 セル以遠をラベル帯とし、グリフ（連結成分）が線数の 1/3 以上の線に付けば「その辺は盤の端が見えている」。**帯の有無ではなくグリフの有無で判定する**（実測: 部分表示の切れた下辺には 0.87 セルの黄色余白が残る＝幅では区別できない）
- **ラベル OCR**: グリフを 10x14 に正規化してテンプレートとのハミング距離最小で分類。**ラベルはズーム非依存の固定 UI フォント**（実測: セル 101.7px の盤でも 44.5px の盤でも高さ 13-14px）なので、テンプレートはズーム率が変わっても一致する。数字（行）と文字（列）は別の帯にしか現れないため、帯の向きでアルファベットを絞る＝紛らわしい対 0/O・5/S・8/B は衝突しない（絞らない場合の最近接ペア実測: 0-O 11 / 8-B 13。絞った後: 8-6 22 / C-G 23、正しい分類の距離は 15 以下）
- **絶対座標**: 行は「番号+線index＝一定」、列は「文字index−線index＝一定」の多数決（2/3 未満の一致は不安定としてエラー）。盤サイズは上端が見えていれば最上行の番号、右端が見えていれば最右列の文字。**どちらも切れていれば可視域が収まる最小候補サイズに倒す**（`size_fallback`、ログに残す）
- **石の分類**: 既存 `_classify_patch`（BlueStacks と同じ閾値）を検出済み線の交点に適用。実測色は空点 (229,195,109)・黒 50台・白 240台で既存閾値のまま通る

### 経路の振り分け（__main__.py）

- `web_full`（4辺すべて見えている）→ 新メッセージ `capture-fullboard-apply`: `grid_to_sgf` → `_do_new_game(move_tree=...)`（move_tree ありの new-game は解析モードに入る）→ 両対局者を人間に戻す。枠・リージョン・ai:tsumego・回答帳・ソルバは一切通らない
- `web_partial` → 盤サイズの全面グリッドに絶対座標で石を配置して**既存の `tsumego-capture-apply` にそのまま合流**（枠張り・ソルバ抽出・回答帳キー・9路対応はすべて既存コードが処理）。素性（切れた辺・サイズ推定の別）は `capture_note` として詰碁ログに残す
- `app` → 従来どおり
- `window_title` はカンマ区切りの複数候補対応（先に書いた候補を優先＝BlueStacks とブラウザが両方開いていても従来挙動）。既定値を "BlueStacks,Puzzle Run,PlayGo" に更新（パッケージ＋ユーザーローカル両方）

## 実測でハマった点（同種の改修で最初に疑うこと）

1. **PIL の `convert("L")` は緑重視の輝度**（0.299R+0.587G+0.114B）。PlayGo の1線目の薄い線 RGB(140,123,80) は L=123 で暗判定(120)を外れるが、等重み平均なら 114。格子線・グリフの暗判定は `_web_mean_gray`（等重み）を使う。**19路の1線目だけが消える**という症状はこれ
2. **ラベルはセル比ではなく絶対サイズでフィルタする**。当初グリフ高さを `hsp*0.15` 以上とした結果、ズームの大きい盤（セル101px）で高さ14pxの文字が全滅した。固定UIフォントなので 8..30px の絶対レンジが正しい
3. **帯領域は最外線から 0.55 セル以遠に取る**。0.3 セルだと1線上の石の縁が帯に入り、巨大成分がグリフ候補を汚す（境界接触成分の除去と合わせて二重に防ぐ）
4. **19路の 'Q' ラベルだけ下帯で読めない**（盤領域の下端に接触して境界フィルタで落ちる）。上帯は読めるので実害なし＝冗長な帯を全部読む設計が効く

## 検証

- 実スクショ2枚: `validate_web_capture.py` が石・サイズ・種別の完全一致で PASS（部分表示 9路13子・全体表示 19路39子、期待値は目視読み）
- 合成盤回帰: `tests/test_tsumego_capture.py` の `test_web_*`（グリフテンプレート自身をラベルとして描画するのでフォント再現不要）
- 既存経路の不変性: BlueStacks サンプル3枚が kind="app"、既存テスト 31→35 全パス
- テンプレート再現性: `generate_glyph_templates.py` の出力が同梱モジュールと完全一致

## 追記1（2026-08-13）: モバイル風レイアウトの失敗3件と修正

初版リリース直後のユーザー実走で3枚のキャプチャが失敗（縦長ウィンドウ＝モバイル風レイアウト）。
原因は4つ、全て修正済み。校正データに `*-mobile-20260813.png` 3枚として追加し、
`validate_web_capture.py` は5枚の完全一致で回帰する。

1. **縦に並んだ座標ラベル列が幻の格子線になる**（失敗1: 右帯の 19..9 が12本目の縦線に化けて
   右帯領域そのものを潰し「行ラベルが読めません」／失敗4: 左帯の数字で幻の0列目が入り
   「列 0..9 の不整合」）。モバイル風はフォントが大きく（数字h23〜30px）、縦に積まれた数字が
   細い暗線プロファイルの 0.25 閾値を超える。**修正＝幻線トリム** `_web_trim_phantom_lines`:
   本物の線は帯のラベルが必ず指していることを使い、「ラベルが1本も付かない端の線」を落とす
   （片側最大2本・ラベルが線の2/3以上をカバーしているときだけ発動＝読み損ね1件で本物を落とさない）。
   トリムで帯領域が変わるので読み直しループ（最大3回）
2. **行番号ラベルが1つも無い構図**（失敗2: 下辺の文字ラベルだけの下寄せクロップ）。
   **修正＝辺アンカー**: 文字帯は盤の端にしか描かれないので「下帯があるなら最下線は 1 の線」
   （`row_c = len(hpos)`）。対称に「左帯（数字）があるなら最左線は A の線」。逆向きの検算
   （下端可視なのに最下線≠1 等）はエラーに倒す
3. **ラベルが盤領域の縁ぴったりまで描かれる**（失敗1: 数字の右端が黄色bboxの右端と同座標＝
   境界接触フィルタでグリフごと落ちる）。**修正＝帯領域の外側境界を bbox+4px まで拡張**
   （外の暗いUI領域は巨大成分としてサイズフィルタが落とす）。内側境界も 0.55→0.45 セルへ
   （0.55 だと9路全体表示の左帯の数字が境界にかかる。石は半径約0.5セルなので 0.45 まで届かない）。
   グリフ高さ上限 30→40px・幅 30→36px
4. **半透明のホバー石**（茶色のゴースト、マウス位置のプレビュー。実測 RGB(130,115,79)＝
   輝度108・spread 51 でどの分類にも入らず「判定できない交点」）。**修正＝`_classify_patch` に
   「輝度95〜150・spread≥35・R−B≥35 は空点」**を追加（盤色に半透明の黒が乗った帯だけを拾う。
   BlueStacks 経路と共有の関数だが、この帯は従来エラーだった領域なので既存分類は不変）

なお失敗4（9路ボス詰碁がモバイル風レイアウトで全体表示になったもの）は修正後 **web_full ＝
通常解析モード行き**になる。「全体表示＝盤面把握問題」というルーティング規則どおりだが、
これは実際には詰碁なので、9路の全体表示を詰碁経路に回すべきかはユーザーの実走感想待ち
（変える場合はトリガー分岐の `view.kind == "web_full"` に盤サイズ条件を足すだけ）。

## 既知の限界

- **部分表示で切れた線の上の石は原理的に見えない**（PlayGo は問題領域＋余白でクロップするので通常は起きない想定。起きたら capture_note の切れた辺をまず疑う）
- **上端・右端の両方が切れた部分表示は盤サイズを確定できない**（最小候補サイズへフォールバック。詰碁は局所死活なので開き方向の余白の過不足が効くのは稀）
- **ラベルの無い中央クロップは認識不能**（座標アンカーが無い）＝CaptureError で明示的に失敗する
- グリフテンプレートは PlayGo.gg のフォント由来。別サイト対応はスクリーンショットを校正データに足して `generate_glyph_templates.py` で作り直す
