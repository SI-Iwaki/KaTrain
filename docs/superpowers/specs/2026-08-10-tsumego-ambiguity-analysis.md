# 詰碁の誤答と「候補の曖昧さ」— 回答帳494件による解析

- 日付: 2026-08-10
- 発端: ユーザーの体感仮説「白の応手のあと、次の黒の一手で有力候補がほぼ1つに絞られる（visits・スコアともにダントツ）局面は正解し、有力候補が複数ある局面で誤答が多い」
- データ: 回答帳 494 entry / 496 手順（前回スイープ 420 手順・1373 判断＋新規 26 手順＋実 GUI ログ 59 本）
- 前提: `2026-08-09-tsumego-answer-book-replay-design.md`（リプレイ基盤）の続き

---

## 1. 要旨

**仮説は実測で強く裏付けられた。しかもユーザーが記述した状況（白の応手後）では、ほぼ決定的に成立する。**

| depth | 候補が1手に集中 (dominant) | 候補が複数 (ambiguous) |
|---|---|---|
| 0（初手） | 193/224 = **86.2%** | 128/196 = **65.3%** |
| **≥2（白の応手後）** | **619/624 = 99.2%** | **252/329 = 76.6%** |

白の応手後の失敗 82 件のうち **77 件（94%）が曖昧局面**で起きている。χ²(Yates) = 152.75（p < 0.001）。

この曖昧さは**判断を下す前に、追加クエリなしで計算できる**（root リージョン解析の visits と `relativePointsLost` だけ）。したがって「どこに手間を掛けるか」の振り分けに使える。

**採用した施策は 1 つだけ**（もう 1 つは実装して測った結果、却下した）:

- **採用**: dominant 局面ではクラス格上げに「格上げ先が実際に成立していること」を要求する（5 節）。追加クエリ 0 本。実測 **+3 手順・退行 0**。
- **却下**: 曖昧判断だけ読みを深くする（1800 → 5000 visits）。**実装して測ったら差引マイナスだった**（6.1 節）。

一方で**曖昧局面の「選び分け」を改善する施策は、測った限りすべて失敗した**。曖昧帯の不一致の 2/3 は**盤面に区別する情報が存在しない正当な別解**であり、判断時点で計算できる 62 指標を総当たりしても分離できない（7 節）。つまり曖昧さは「もっと読め」の合図であって「もっと賢く選べ」の合図ではない。

## 2. 曖昧さの定義と、それが何を測っているか

判断時点の root リージョン通常解析 `cn.candidate_moves` の visits 上位5手から:

```
v2_v1  = (2位の visits) / (1位の visits)
pl_gap = pointsLost の最良と次点の差
dominant := v2_v1 < 0.15 かつ pl_gap >= 1.0
```

追加クエリは不要（既に手元にある値だけ）。

### 2.1 帯が測っているもの: 選択則は曖昧帯で有益、dominant 帯で有害

「常に KataGo の visits 1位を打つ」という反実仮想との**対比較**（同一局面上の McNemar）:

| 帯 | 実際 | 常に v1 | 差引 | McNemar |
|---|---|---|---|---|
| dominant | 812/848 = 95.75% | 827/848 = **97.52%** | **−15** | **p = 0.0041（有意に有害）** |
| ambiguous | 380/525 = **72.38%** | 336/525 = 64.00% | **+44** | p = 1.4e-4（有意に有益） |

つまり曖昧さは「AI 独自の機構を働かせてよい局面か」の線引きになっている。**機構は曖昧帯では明確に元を取っており、dominant 帯では自傷している。**

（当初この節には「dominant 848 判断のうち 839 は `eligible <= 1` なので選択則が動いていない」と書いたが**誤り**。`eligible <= 1` が意味するのは gain / 同深さ検証 / 救済といった**比較ベースの段に対抗馬が居ない**ことだけで、クラス裁定・コウ脱出・`_pick_ko_win_move`・救済は `eligible <= 1` でこそ走る。実測で `eligible <= 1` の 53 判断が v1 以外を着手している。`ai.py:4040` の「全て不発」というログ文言も実態と合っていない。）

## 3. 曖昧局面の失敗の内訳（n=145）

| 区分 | 件数 | 内容 |
|---|---|---|
| A. 保守的すぎ | 82 (57%) | KataGo 本命に留まったが、正解は別の手だった |
| B. 攻めすぎ | 43 (30%) | 本命から外したが、本命が正解だった |
| C. 外した先が違った | 20 (14%) | 外したが、外し先も正解ではなかった |

**A の 72%（59/82）は正解手が既に候補プールの中にいた**（目数ガード `max_points_behind`=2.0 の内側・中央値わずか 0.48 目差、うち 32 件は 0.25 目以内）。`min_visits`(10) で落ちていたのは 82 件中 2 件のみ。つまり**到達性の問題ではなく選択の問題**である。

### 3.1 だが、その「選択の問題」は解けない

0.25 目の同着バンドに 2 手以上並ぶ判断（曖昧帯の 32%・n=166）で:

- 記録手が KataGo 本命である確率 = **55%**（ほぼコイン投げ）
- 記録手がバンド内にいる確率 = 81%
- **policy（prior）最大で選び直しても 53%** ＝ 改善しない

そしてこの帯の不一致 57 件を第2パスで分類すると **77% が「別解」**（AI の手も詰碁を解いている）、真の誤答は 1 件だけ。非同着帯の不一致（別解 40% / 判定不能 52%）と比べて明確に別解に偏る。

**アプリがどちらの正解手順を期待しているかは盤面に無い情報**（作意の問題）なので、選択則では原理的に当てられない。これを解く既存機構が回答帳そのものである。

## 4. 計測基盤の訂正（前回 design doc §9 の修正）

`answer_book_replay.py` の `decision_paths()` は `Final decision:` 行の括弧内しか見ておらず、取りうる値が 4 種類しかない（ai.py:4262 の `gain_text`）。結果:

- `declass` / `rescue` / `verified` / `tie_band` は**到達不能なデッドラベル**で、全部 `gain` に潰れていた
- `_pick_ko_win_move`（ai.py:5080）の Final decision 行は**全角括弧**なので split に失敗し、コウ勝ち前提 19 件が全部 `unknown` になっていた

不一致 181 件は `strategy_log` を持つので事後復元でき、ambiguous 帯の不一致 145 件の機構帰属は:

```
select 64 / solver 25 / no_rival 11 / rescue_adopt 10 / ko_escape 8 /
declass 8 / verify_adopt 6 / verified_revert 5 / class_promotion 4 / ko_win 4
```

**前回 design doc §9 の「ambiguous 帯の gain が 69%(n=336)」は帰属として無効。** 正しくは pipeline 66.9%(n=266) / no_rival 77.1%(n=70)。

一致した 1192 件には `strategy_log` が無いため、**各機構の分母（何回走ったか）は復元できない**。「select が最も多く外している」は「select が最も多く走っている」と区別できない。機構ごとの精度比較には再スイープが要る。

## 5. 採用した施策: dominant 帯のクラス格上げに「成立」を要求する

### 5.1 観測

dominant 局面で戦略が KataGo 本命から外した判断は **26 件**、うち正解はわずか **5 件**。全部本命のままにしていれば 20 件が正解だった。

| 帯 | 逸脱 n | 当たり | 本命なら当たり | 差引 |
|---|---|---|---|---|
| ambiguous | 150 | 87 | 43 | **+44**（機構は有益） |
| **dominant** | **26** | **5** | **20** | **−15**（機構が自傷） |

機構別（`dominant_override_probe.py` で全 26 件の役割石・同深さ ownership を実測）:

| 機構 | n | 当たり | 本命が正解 | 差引 |
|---|---|---|---|---|
| class_promotion | 8 | 2 | 6 | −4 |
| ko_escape | 9 | 2 | 6 | −4 |
| solver_or_book | 8 | 1 | 7 | −6 |
| unknown (ko_win) | 1 | 0 | 1 | −1 |

**`gain` は dominant 帯で一度も逸脱していない**ので触らない。solver_or_book は 2026-08-09 の `solver_cross_check` が既に担当している。

### 5.2 採用した形

**`_ko_promotion_choice` は、dominant 帯では「格上げ先がその手で実際に詰碁を成立させている」ことを要求する**（`promotion_dominant_requires_success`、既定 true）。

`tsumego_result_class` はコウ経路を `succeeds` と無関係に KO クラスへ置く（それ自体は正しい＝コウ手の ownership は「コウに勝った前提」で高く出るので、成立の読みでクラスを繰り上げてはいけない）。ところが **incumbent も shortlist も全員が閾値未満**の局面では ownership が「どの手が解くか」を一切表現しておらず、順位を決めているのは**コウ検出の二値だけ**になる。

実測でこの状態の格上げは全滅だった:

| 標本 | 格上げ採用 | 採用手の1子平均 | 結果 |
|---|---|---|---|
| リプレイ（回答帳420手順） | 6 件 | −1.00 〜 +0.17 | **6/6 誤答** |
| 実 GUI ログ（59本） | 3 件 | −1.00 〜 −0.75 | **3/3 誤答** |
| リプレイ（正答した格上げ） | 2 件 | **+0.94 / +0.99** | 2/2 正解 |

閾値 `ko_success_ownership`(0.5) で完全に分離する。**追加クエリは 0 本**（検証バッチは `_child_verdicts` で既に発行済みで、変わるのは採用判断だけ）。

### 5.3 実測（該当8手順の A/B）

| | 修正前 | 修正後 |
|---|---|---|
| 正解 | 2 / 8 | **5 / 8** |
| 問題の判断（格上げが起きた手番）が正しくなった | — | **6 / 6** |
| 以前正解だった手順の維持 | — | **2 / 2** |

差引 **+3 手順・退行 0**。残る 3 件は格上げの手番は直ったが、その先（d2 / d6 / d6）で別の理由により外れる。

**この施策が施策1（6.1 節）と違って安全なのは、解析を一切変えないから。** 発火しない手番はクエリも順序もビット単位で同一で、施策1 を殺した「手の入れ替えによるシャッフル」が構造的に起きない。

### 5.4 なぜ ko_escape は触らないか

dominant 帯で ko_escape は 9 件中 7 件が誤りだが、**判別子が無い**。frame 盤では own(want) と own(chosen) の相関が r=0.921 で、ko_escape の 9 件は全部 +0.72〜+1.00 の飽和帯に収まる。ブロック根拠になりうる delta は −0.02〜−0.08 ＝ run 間ノイズ（±0.95 の二峰性）以下。**ply1 ownership を frame 盤で細かい差の判定に使ってはいけない。**

また「dominant ならクラス裁定を丸ごと走らせない」という広い形（12 件回復・4 件破壊 = +8）も検討したが、壊れる 4 件に case O 型（root が読まない正解手を policy から拾う）が含まれるため採らなかった。

### 5.5 回帰（実施済み）

`e2e_suite.py`（29ケース×3run）: **27/29 PASS**、PART は `K@0`（1/3）と `U@0`（2/3）。**どちらもこのゲートの退行ではない**ことを確認済み:

| ケース | ゲート ON | ゲート OFF（対照） | 追加 run（ゲート ON） | 判定 |
|---|---|---|---|---|
| K@0 | 1/3 | **3/3** | **6/6 + debug 1/1 = 7/7** | run 間変動。K は格下げ（declass）経路で決まり、格上げは発火しない（debug ログで確認） |
| U@0 | 2/3 | **2/3（同一）** | — | ゲートと無関係。同条件の対照で同じ値 |

**校正ケースは全部無傷**: **case V2 3/3**（v2/v1=0.63・目数差 0.01 ＝ ambiguous 帯なのでゲートが構造的に掛からない）、**case O 3/3**（「root が読まない正解手を policy から拾う」型＝ゲートが壊す第一候補だった）、T / F2 / V / W / Y / R / P / M / L も 3/3。

ユニットテスト **696 passed**（`tests/test_tsumego_ambiguity.py` 7件を新規追加）。

## 6. 実測で却下した施策（すべて数値つき）

| 施策 | 却下理由（実測） |
|---|---|
| **逸脱コストの上限** | 正しい逸脱の最大 16.39 目 vs 誤った逸脱の中央値 2.69 目でレンジが完全に重なる。閾値 5 目なら +15 だが正しい逸脱を 11 件破壊。case O 型（visits 1 の正解手）をまさに殺す |
| **同着バンドの選び直し** | バンド内の不一致 57 件の 77% が正当な別解。policy で選び直しても 53%（現状 55%）。盤面に情報が無い |
| **class_promotion に「格上げ先が成功していること」を*無条件に*要求** | **答えがコウの詰碁では正解も ply1 で必ず失敗と読まれる**ため E2E の case V2 を壊す。→ **dominant 帯に限れば安全**（case V2 は ambiguous 帯）＝5 節で採用した形 |
| **frame 経路の判断時点指標による分離** | 判断時点で計算できる **62 指標を総当たりして全滅**。全指標で一致側と不一致側の min..max が完全に重なる。最良単変量 AUC 0.610、多変量ロジスティック 5-fold CV AUC 0.621、最良閾値の適合率 41.7〜48.6%（ベースライン 35.2%）＝3 手に 2 手が巻き添え |
| **曖昧局面で読みを深くする（1800→5000）** | **実装して測ったら差引マイナス**。誤答手順の 15.2% を直すが、正解手順の 15.0% を壊す＝シャッフル。420手順で −8.3 手順、所要は倍。詳細と教訓は 6.1 節 |
| **ko_escape の締め直し** | dominant 帯 9 件中 7 件が誤りだが、正誤どちらも delta（外し先 − 本命）が **±0.09 以内**でノイズ幅。判別子が無い（5.4 節） |
| **初手 dominant 失敗＝盤の破損 という仮説** | 正解手と実際に打った手の距離は中央値 2 路、4 路以上離れているのは 6% だけ（曖昧帯の 19% より**低い**）。盤は正しく、KataGo が局所で読み違えている |

### 6.1 却下: 曖昧局面で読みを深くする（1800 → 5000 visits）

**この節は当初「効いた施策」として書いたが、実装して測り直した結果、差引マイナスで却下した。経緯ごと残す — 同じ罠を二度踏まないため。**

#### 何を測り間違えたか

最初の実験は「曖昧局面で落ちた 145 手順」を 5000visits で回し、**22 件（15.2%）が回復**した（run 間ノイズ 3.3% の 4 倍）ことをもって「効く」と判断した。**これは結果で選別した標本で、手を入れ替える変更なら何であれ一定割合が「回復」する。** 必要だったのは反対側の測定＝**以前正解していた手順が壊れる率**で、それを一度も測っていなかった。

測ったところ:

| | 1800v（基準） | 5000v |
|---|---|---|
| 以前**誤答**だった 145 手順 → 正解に | 0（定義上） | **22 件 = 15.2%** |
| 以前**正解**だった 60 手順 → 誤答に | 0（定義上） | **9 件 = 15.0%** |

**回復率と破損率がほぼ同じ**＝深い読みは改善ではなく**シャッフル**。420 手順（正解 239 / 誤答 181）に外挿すると:

```
回復 0.152 × 181 = +27.5 手順
破損 0.150 × 239 = −35.9 手順
差引              = −8.3 手順
```

しかも所要時間は倍（1手順 中央 4.2 → 8.3 秒、p90 10.4 → 18.2 秒、**20 秒超が 1 → 8 件**）。

#### 実装しても同じ結論だった

「曖昧判断だけ 5000visits で撃ち直してノードにマージする」形（`_maybe_deepen_ambiguous`）を実装し、420 手順のスイープを回した。69 手順時点で **獲得 4 / 損失 7**。損失 7 件のうち **6 件は深掘りした判断そのもので失敗**していた。

マージ版がクリーンな 5000v よりさらに悪いのは、`GameNode.update_move_analysis` が「visits が増えた候補だけ上書きする」ため **1800v と 5000v の2つの探索結果が混ざる**から（同じ手でも noise の引き直しで visits が減ると古い `scoreLead` が残り、順位だけ新しくなる）。実際、マージ版が壊した 6 手順をクリーン 5000v で回し直すと **3 件は正解に戻り、3 件は壊れたまま**だった＝マージの害と深掘り自体の害が両方ある。

#### 教訓

**「効いた」を主張する前に、以前正解していた側の破損率を必ず測ること。** 誤答だけを集めた標本での改善率は、シャッフルと改善を区別できない。

### 6.2 却下した施策の詳細な数字（再検討する人向け）

- 5000visits 版の経路別の回復: **frame 15/102・solver 7/26・frameless 0/17**。枠なし盤は1件も回復しない
- 判断あたりの解析時間 0.81 → 2.37 秒（中央値・+1.56 秒）
- 曖昧判断は1手順あたり 0個が109件 / 1個174 / 2個77 / 3個46 / 4個11 / 5個3（420手順中）
- 実 GUI の所要はハーネスより速い（`.keep` ログ51問で中央 3.9 秒・p95 10.2 秒・最大 14.9 秒・20 秒超 0 件）ので、時間だけなら**上限2回＋曖昧限定**で 20 秒には収まる見込みだった。落ちたのは時間ではなく**正確さ**

## 7. なぜ曖昧局面が直せないのか（構造）

frame 経路の曖昧帯の不一致 101 件を役割石 ownership で分けると:

- **両方成立（別解）: 65 件**
- 両方不成立（コウ/セキ等 ply1 で決着しない）: 31 件
- AI の手だけ成立: 5 件
- **記録手だけ成立: 0 件**

`|delta| < 0.05` が 64 件。つまり **2/3 は本当に両方が解であり、残りも ply1 の ownership では決着しない**。第2パスの分類器（`answer_book_verify.py`）は提案しうるゲートの試作そのもの（同じ `_region_child_verdict`・同じ閾値 0.5）だが、frame/frameless の曖昧不一致 119 件で **true_miss は 0 件**。13 件の true_miss は全件ソルバ経路で、既に `_solver_answer_rejected` が担当している。

## 8. 副産物: policy 集中という第2軸

visits の集中とは**直交する**軸として、prior（生 policy）の集中が実在する:

- frame 曖昧帯で `prior2/prior1 < 0.15` なら **34/38 = 89.5%**
- `>= 0.15` なら 152/249 = 61.0%
- 無作為半分割 500 回の保持外差は中央 **+28.5pt**、0 以下は **0 回**

ただし**選択則としては使えない**（prior 最大を採ると 50.2% で現状 64.8% より悪い）。使えるのは「確信度」としてのみ。

4 セルに分けると、危険帯を「visits も policy も分散」に絞れば**全判断の 30.8% で誤答の 74.6% を捕捉**（曖昧帯全部だと 38.3% で 80.1%）＝ より少ない判断数で同じ捕捉力。追加解析を投じるならここ。ただし 6 節のとおり**投じる先の施策が今のところ無い**。

## 9. 計測の限界（今後の解釈に必須）

1. **ハーネスは楽観側にずれている。** 実 GUI ログ 30 問の真ラベルと突き合わせると、**実 GUI の誤答 19 件のうち 15 件（78.9%）しか再現しない**。逆向き（GUI 正 × harness 誤）は 0 件。したがって**ハーネスの A/B の効き幅は下限として読む**。
   - 実 GUI ログからの真ラベル抽出は健全（認識盤面を canonicalize した回答帳キーが **59/59 でログ記載のキーと一致**、白の応手は `Sending query` の `"moves"` から復元、記録モードの巻き戻し 12 件は検出して除外）。
   - **ただしラベル自体に汚染がある**: `ai_miss` 20 件のうち **6 件は同じ記録手順の後方に出てくる黒の手**（＝手順前後で、誤答ではない可能性）、別の **4 件は記録手順が白に割り当てている点**。真の誤答はもっと少ない。
   - 実 GUI の所要時間（`.keep` ログ 51 問）: 1 判断あたり中央 0.80 秒・p95 2.90 秒、枠の採否判定 中央 0.70 秒、**1 問あたり中央 3.9 秒・p90 7.3 秒・p95 10.2 秒・最大 14.9 秒・20 秒超 0/51**。現行実装は 20 秒制約を満たしている。
2. **新規 26 問では仮説が再現しない。** dominant 80.5%(n=41) vs ambiguous 74.1%(n=27)、χ² = 0.11（有意でない）。この 26 問は手順一致率 42.3%（既存 420 手順は 56.9%）で明確に難しく、「KataGo が確信して間違える」型に偏っている＝**ユーザーが記録する問題は選択バイアスがかかっている**。
3. **一致した判断の ownership は 1 件も測っていない。** 第2パスは不一致 181 件しか回していないので、ゲートが「何も壊さない」ことは**証明されていない**（何も直さないことは示せている）。
4. **機構ごとの分母が無い**（4 節）。
5. 1 run のスイープに基づく。KataGo は同一局面でも run 間で二峰性を持つ（実測ノイズ 3/90 = 3.3%）。二桁前半のセルは run 間で入れ替わりうる。
