# 詰碁専用 死活ソルバ 設計スペック（2026-08-01）

## 0. この文書の位置づけ

現行の詰碁機能（キャプチャ → 枠張り → `ai:tsumego` の ownership ベース選択則）を、
**目的付きの厳密探索（死活ソルバ）** に置き換えるための設計文書。

- **完全上位互換が要件**: 現行が解ける問題は全部解け、現行が使える場面では全部使える
- **速度が要件**: キャプチャ → 自動解答までを現行より速くする
- 実装規模の制約なし（ネイティブ拡張の追加を含む）

この文書は「なぜ作り直すか」の根拠を先に固定する。根拠はすべて
`2026-07-29-tsumego-ownership-design.md` の追記に記録した**実測**で、推測ではない。

## 1. なぜ作り直すか — 現行方式の構造的限界

### 1.1 現行方式の要約

```
キャプチャ（tsumego_capture）
  → 枠張り（tsumego_frame: 壁 + 代償地帯 + コウダテ配分）
  → 枠の採否判定（KataGo 400/1800visits × 最大3本）
  → リージョン限定解析（KataGo 1800visits, wideRootNoise=0.04）
  → 選択則（ai.py TsumegoOwnershipStrategy）
       目数ガード → gain（ownership 変化量）→ 同着バンド
       → 同深さ検証 → 救済 → コウ経路検査 → クラス格下げ/格上げ → コウ脱出
  → 着手（黒番のみ）。以降の手番で毎回同じ処理を繰り返す
```

**この構成の本質は「地を数えるエンジンを、死活の種類を判定する装置として使っている」こと。**

### 1.2 詰碁の正解は「点数」ではなく「結果のクラス」で決まる

```
攻め方（殺す）   無条件死 > コウ > セキ > 相手が無条件生き（＝失敗）
守り方（生きる） 無条件生き > セキ > コウ > 自石が無条件死（＝失敗）
```

守り方でセキがコウより上なのは、コウが**盤外のコウダテという条件**に依存するため。
KataGo が返すのは目数・勝率・ownership という**スカラー**で、この半順序を表現できない。
選択則は「クラスは構造検出（コウ形の到達判定）で、成否は ownership の絶対値で」と分けて
近似してきたが、これは本質的に**代理指標**である。

### 1.3 スカラーでは順序が作れない — 決定的な実測

`2026-07-29-...md` 追記36（2026-08-01）。同じ盤（case W・13路右下・枠なし・黒は守り方、
正解 H1 → 白G1 → 黒K1 のコウで黒生き）を、同深さ検証と同じ尺度
（全リージョン石の絶対 ownership）で、**リージョン拘束を深くし visits も 3 倍**にして測る:

```
untilDepth=6 × 2400visits（3run）

初手   H1(正解) -3.62 / -3.49 / -3.66   N4 -9.7 前後   L1 -10.1〜-11.2   N3 -11.1
       ＝正解が次点と 6.0 差で安定（自石 +0.54/+0.56/+0.54）      ← 正しい

3手目  K1(正解) -10.77 / -10.27 / -10.32
       J1       -8.83 / -8.49 / -6.93                            ← 正解を上回る
```

**同じ盤・同じ尺度で、1手目は正解を 6.0 差で正しく選び、3手目は別の手を選ぶ。**
visits を増やしてもばらつきが消えるだけで順序は変わらない（幅 3.3 → 0.8、収束先は
H1 -11.0 < N4 -8.9 のまま）。これはパラメータの問題ではなく、**尺度が「どの手が詰碁を
解くか」を表現していない**ことの証明である。

同じ結論に別経路からも到達している:

- 追記28（case T）: 守り方の正解がセキのとき、pointsLost・gain・同深さ検証値の**三つとも**
  コウ生きを上に並べる。正しく出るのは「自石だけ」の +1.00 vs +0.99/子
- 追記31/33（case V/W）: 「無条件」は「攻めないので何も起きず自明に clean」でも成立する
- 追記36: 救済経路の誤答を塞ぐ5案（成立ゲート / untilDepth / visit比の床 / 目数の到達幅 /
  visits 増）が**すべて**「正解側と誤答側のレンジが重なる」で失敗

### 1.4 リージョン限定解析が局面を作り変える

`avoidMoves` で領域外を禁じると、

- 守り方から**コウダテが取り上げられる** → コウを仕掛けるのが純損になり、
  **コウが争点の局面ほどエンジンはそのコウを打たない**（追記29 case U）
- `untilDepth=1` は root の着手選択しか縛らず、**ply2 以降の PV は枠外へ手抜きする**
  （追記20 case P）
- 枠は領域外を「守り側の代償地帯＋攻め方の地」に配るので、その代償地帯が未決着だと
  **スコアが詰碁の成否から切り離される**（追記21 case Q: 相手石12子すべて生存なのに +10.45目）

枠機構（`tsumego_frame.py` 941行）はこの歪みの**補正**として育ってきたが、補正である以上
原理的に完全にならない。枠の妥当性判定・役割推定・コウダテ配分の自動選択に
**KataGo クエリを最大5本（実測 1.1〜5.7秒）**使っているのも、この補正のコストである。

### 1.5 現在の到達点と残っている穴

- 全20ケースの正解手順を初手から通しで検証して **55局面中53 PASS**
- 未対処: **case I**（KataGo の探索崩壊）/ **case Q**（準備手の value 誤読）/
  **case R**（救済経路の残余 1/4）/ **case W**（救済経路の残余 5〜6/22）
- 枠の役割推定の反転（case S）は `extremum_stones` で是正したが、判定そのものは
  「手番側の本体石が生きているか」という**KataGo の読み**に依存し続けている

**残っている穴はすべて「スカラーで死活のクラスを判定している」ことに由来する。**

## 2. 目標と非目標

### 2.1 目標

| # | 目標 | 受入基準 |
|---|---|---|
| G1 | 詰碁を**厳密に**解く | 結果クラス（無条件生き/無条件死/セキ/コウ）とその手順を、探索の打ち切りなしに確定する |
| G2 | **完全上位互換** | 既存 E2E 20ケースで現行以上。現行が動く条件（枠あり/枠なし、9/13/19路、`auto_ai_black` の両設定）で全部動く |
| G3 | **速度** | キャプチャ → 初手着手までの実時間を現行以下（§8 に数値目標） |
| G4 | 手順全体を一度に解く | 2手目以降は**解析ゼロ**で応答（解答樹をなぞるだけ） |
| G5 | 解けないときに壊れない | 厳密に解けない場合は現行経路へ自動フォールバックし、品質を現行より下げない |
| G6 | 検証可能 | 既存の `e2e_suite.py` にソルバモードを足し、両モードを同じケース表で回せる |

### 2.2 非目標

- 一般の対局（`ai:tsumego` 以外の戦略）には関与しない
- 盤全体の死活・ヨセ・全局的判断
- 領域が広すぎて厳密解が現実的でない問題（→ G5 のフォールバック）
- 詰碁アプリの解答樹そのものの取得（読めないので「別解を打って不正解」問題は残る。§14）

## 3. 全体アーキテクチャ

```
[1] キャプチャ            tsumego_capture.capture_tsumego_grid        （現行流用・変更なし）
        ↓ 認識グリッド
[2] 問題の抽出            tsumego_problem.py（新規）
        - 領域の確定（外周の封鎖・脱出可能性の検査）
        - 対象石群と役割の決定
        - コウダテ仮定の設定
        ↓ Problem（純データ・KataGo 非依存）
[3] ソルバ                tsumego_solver/（新規・ネイティブ）
        - λ探索 + df-pn による AND/OR 探索
        - 終端判定（Benson pass-alive / 取られ確定 / セキ）
        ↓ Solution（結果クラス + 解答樹）
[4] 出題                  盤面をそのまま出す（枠を張らない）
[5] 着手                  ai:tsumego_solver（新規戦略）
        - 解答樹を参照して即着手（解析0本）
        - 樹から外れたら [3] へ再入（TT は温存）
        ↓ 解けなかった / 打ち切り
[F] フォールバック        現行 tsumego_frame + ai:tsumego（そのまま残す）
```

### 3.1 現行から**消える**もの

| 消えるもの | 理由 | 削減 |
|---|---|---|
| 枠張り（壁・代償地帯・コウダテ配分） | スコアを意味づける必要がなくなる | 認識時の処理 |
| 枠の採否判定（`frame_ko_auto` / `frame_validity_visits` / `frame_over_frameless`） | 「手番側が生きているか」をソルバが厳密に答える | **KataGo 最大5本・実測 1.1〜5.7秒** |

| 応手先読み（`ponder_replies`） | 解答樹が全応手を持つので先読み不要 | KataGo 3本/手 |

## 4. 問題の定式化

### 4.1 Problem（ソルバへの入力）

```python
@dataclass(frozen=True)
class Problem:
    size: tuple[int, int]            # 盤サイズ（9/13/19）
    black: frozenset[Point]          # 黒石
    white: frozenset[Point]          # 白石
    region: frozenset[Point]         # 領域の点集合（§5.1。初期に石がある点も含む）
    to_play: Color                   # 手番（詰碁モードは常に黒）
    target: frozenset[Point]         # 成否を担う石群（役割で決まる）
    goal: Goal                       # LIVE（target を生かす）/ KILL（target を殺す）
    komaster: Color | None           # あらゆるコウに勝つと仮定する側（§4.3）
    ko_budget: int | None            # komaster が使えるコウダテ数（None=無限。§4.4）
```

- `region` の**外は着手禁止**（両者とも）。ソルバは「領域外へ逃げる」手を持たない
- `region` は**点の集合**であって「初期の空点」ではない。取られて空いた点（取り跡）への
  打ち直しは詰碁で頻出（ウッテガエシ・石の下）なので、**着手可能 ＝ region 内 かつ 現在空点**。
  §5.1 の構成規則は at_risk 連や攻め合い相手の連の**石の点も region に含める**
- `target` と `goal` は §5 で自動決定する
- `to_play` が守り方でも攻め方でも同じ探索器を使う（goal で吸収）

### 4.2 結果クラス

```python
class ResultClass(IntEnum):     # 小さいほど「解く側にとって上位」
    UNCONDITIONAL = 0           # 無条件に目的達成（生き / 死）
    SEKI          = 1           # セキ（守り方視点では UNCONDITIONAL の次）
    KO            = 2           # コウ（コウダテという盤外条件に依存）
    FAILED        = 3           # 目的不達成
```

**攻め方はセキとコウの順序が逆**（攻め方: 無条件死 > コウ > セキ）。
順序表は `RESULT_ORDER[goal]` として持ち、比較はこの表を通す。
これは現行 `tsumego_result_class` の一般化で、**近似ではなく定義**になる。

#### 4.2.1 クラスだけでは手が決まらない — 解の値は**タプル**にする

AND/OR 探索（df-pn）は決定問題を解くので「最善の手順」ではなく
**最初に証明できた手順**を返す。クラスだけを値にすると次が区別できない:

- **手損・無駄手**: 黙って生きれば正解（1手）なのに、無駄なアタリを打ってから生きる
  手順も同じ `UNCONDITIONAL` になる
- **余計な犠打（目損）**: 3子捨てて生きるのが正解のところ、4子にしてから捨てる手順も
  同じ `UNCONDITIONAL` になる

詰碁アプリはこれらを**変化図・失敗図（＝不正解）**として扱う。詰将棋の
「最短手順」「駒余り」とまったく同じ問題で、解の値を多目的にすれば解決する。

```python
@dataclass(frozen=True)
class SolutionValue:
    result: ResultClass       # 1. 結果クラス（役割ごとの順序表を通す）
    ko_level: int             # 2. コウの深さ n*（§4.4。小さいほど上位）
    plies: int                # 3. 決着までの**解く側の着手数**（小さいほど上位）
    material: int             # 4. 最終盤面で失う自石数＝犠打（小さいほど上位）
    # 比較は sort_key(problem_type) = (RESULT_ORDER[type].index(result), ko_level, plies, material)
    # を通す。dataclass(order=True) の素の辞書順は result を IntEnum の生値で比べるので
    # 守り方の順序でしか正しくない（攻め方は コウ > セキ。§4.2）— order=True は使わない
```

**辞書順で比較する。** 上位の項が同点のときだけ下位を見るので、クラスの裁定が
手数や目数に覆されることはない（現行が「目数がクラスを覆す」で繰り返し失敗した点）。

- `plies` は**解く側の盤上の着手数のみ**を数える minimax（解く側が最小化、相手が最大化）。
  詰将棋の最短手順と同じ定式化で、攻め方・守り方で式は変わらない
  （守り方も「相手に最長を強要する」のではなく**自分の無駄手を打たない**が作法）
- **パスは plies に数えない**（「他所に打つ」は局所の手数ではない）。また相手の最大化では
  **盤上に合法手がある限りパスを選ばない**（＝最強の抵抗）。この規則が無いと
  「相手が全部パスし、解く側が眼を確定させる打ち足しを続ける」線（§4.7）が
  plies を水増しし、本手の順位づけと表示手順を歪める
- `material` は「終局時に盤上から消えている自石の数」（初期配置の石＋探索中に打った石の両方）。
  同じ手数なら犠打の少ないほうを本手とする

#### 4.2.2 二段階で解く（コストを増やさない）

多目的をそのまま探索に載せると df-pn の利点が消えるので、**分けて解く**:

1. **第1段階（決定問題）**: `ResultClass` と `ko_level` を確定する（§4.3 / §4.4）。
   ここは従来どおり df-pn
2. **第2段階（最適化）**: **クラスを維持する手だけに制限**して `(plies, material)` を
   αβ で最小化する。探索空間は激減しており TT も温まっているので追加コストは小さい

第2段階は `solver_optimize_line`（既定 true）。時間制限に達したら第1段階の解をそのまま
返す（＝手数・犠打が最適でない可能性はあるがクラスは正しい、という劣化で済む）。

### 4.3 コウの扱い（**この節が誤答の主戦場**）

#### 4.3.1 よくある誤解: 「詰碁は常に黒番なのでコウダテは考えなくてよい」

**半分正しい。** 正解手を**選ぶ**のにコウダテは要らない（詰碁は結果のクラスで順位が決まり、
「コウに勝てるか」は問わない）。しかし**コウダテ仮定を持たない局所探索はコウを検出できない**。

領域外が着手禁止であることと、コウのルール（直前に取られた点は取り返せない）が組み合わさると、
コウダテなしの探索では**コウが「先に取ったほうが無条件で勝つ」ただの手順に化ける**。
case W（正解 黒H1 → 白G1 → 黒K1 のコウで黒生き）で辿ると:

```
黒K1 でコウの形 → 白がコウを取る → 黒はコウ禁止で取り返せない
→ 黒は他に打つ手が無い（領域外は着手禁止）ので パス
→ 白がコウを解消 → 「黒の無条件死」と報告される
逆に黒が先に取れば、白がパスして黒が継ぎ → 「黒の無条件生き」と報告される
```

どちらも**クラスが `KO` にならない**。`ResultClass.KO` は永遠に返らず、ソルバは
「先手が勝つ」という手番だけの結論を出す。これは現行実装が抱えている病気
（スコアがコウを表現しない → PV の構造検出で無理やり拾う）とまったく同じものを、
ソルバ側に作り直すことになる。

**したがってコウダテ仮定は「コウを評価する道具」ではなく「コウを検出する道具」である。**

#### 4.3.2 定式化: komaster を2通り解いて突き合わせる

盤にコウダテ形を仕込む（＝現行の `frame_ko`）のではなく、
**「この対局者はあらゆるコウに勝つ」という仮定（komaster）** を探索に与える。

実装は単純で、**komaster はコウ禁止に縛られず、相手は縛られる**。
（コウダテを打って相手が受けた、という手順を1手に畳んだ抽象。盤面を変えないので
領域限定と両立し、コウダテを「置く」必要がない。）

守り方（黒が生きる。`goal=LIVE`）の判定手順:

| 順 | 問い（solve） | Yes のときの結論 |
|---|---|---|
| 1 | **攻め方が komaster** でも target が2眼で生きるか | **無条件生き** |
| 2 | 同じ仮定で、少なくともセキで残るか | **セキ** |
| 3 | **守り方が komaster** なら生きるか | **コウ**（守り方がコウに勝てば生き） |
| 4 | いずれも No | **無条件死**（失敗） |

攻め方（黒が殺す。`goal=KILL`）はセキとコウの順位が逆なので、問いの順序も入れ替わる:

| 順 | 問い（solve） | Yes のときの結論 |
|---|---|---|
| 1 | **守り方が komaster** でも target を殺せるか | **無条件死** |
| 2 | **攻め方が komaster** なら殺せるか | **コウ**（攻め方がコウに勝てば死） |
| 3 | 守り方が komaster のとき、最善がセキか | **セキ** |
| 4 | いずれも No | **相手の無条件生き**（失敗） |

**2通りの結果が一致 → その局面にコウは関与していない**（このときに限り、
ご指摘どおりコウダテは無関係）。**食い違いそのものが「コウ」の定義**になる。

#### 4.3.2.1 完全対応表（ラダーは短絡評価、定義はこの表）

上の2表は**評価順序**（短絡評価でコストを削る手順）であって、クラスの**定義**ではない。
定義は「述語2つ × komaster 2通り」の4つの solve の組合せで閉じる。ここを表で
固定しないと「コウに勝ってもセキ」のような混合ケースが未定義になり、ラダーの
書き方次第で**失敗クラスに落ちる**（初版のラダーは実際にそうなっていた）。

```
A  = solve(ALIVE,   komaster=攻め方)     S  = solve(SEKI以上, komaster=攻め方)
A' = solve(ALIVE,   komaster=守り方)     S' = solve(SEKI以上, komaster=守り方)
単調性: A ⇒ S、A ⇒ A'、S ⇒ S'、A' ⇒ S'。取り得る組合せは次の6つだけ:
```

| A | S | A' | S' | 客観的な結果 | 守り方の報告クラス | 攻め方の報告クラス |
|---|---|---|---|---|---|---|
| ✓ | ✓ | ✓ | ✓ | 無条件生き | UNCONDITIONAL | FAILED |
| ✗ | ✓ | ✓ | ✓ | セキは無条件・コウに勝てば生き | SEKI（コウ生き線は別解情報） | SEKI の下位細目「コウでセキ」（コウに勝ってもセキ止まり） |
| ✗ | ✓ | ✗ | ✓ | セキ確定（コウ無関係） | SEKI | SEKI |
| ✗ | ✗ | ✓ | ✓ | コウ（勝てば生き・負ければ死） | KO | KO |
| ✗ | ✗ | ✗ | ✓ | コウ（勝ってもセキ・負ければ死） | KO の下位細目「コウでセキ」 | KO |
| ✗ | ✗ | ✗ | ✗ | 無条件死 | FAILED | UNCONDITIONAL |

- 「下位細目」は同クラス内の順位づけ（`ko_level` の後の payoff）として持つ。
  実際の詰碁で出るのは稀なので、**まずはログに出す + 同クラス末尾に置く**で足りる
- これに伴い各ラダーに1段追加する: 守り方はステップ3の後に
  **3.5「守り方 komaster ならセキ以上を保てるか（S'）」**（Yes → コウでセキ、No → 失敗）、
  攻め方はステップ3の後に
  **3.5「攻め方 komaster なら相手の無条件生きを阻めるか（¬A）」**（Yes → コウでセキ、No → 失敗）
- クラス判定の solve は**最大4回**（短絡評価で大半は1〜2回。§4.3.3）
- 攻め合い（§5.2.2）も同じ枠で解く。述語が「相手 target の KILL ∧ 自 target の LIVE」に
  変わるだけで、komaster 2通りの突き合わせ構造は同一

#### 4.3.3 コスト: 大半は solve 1回で終わる

上表はどちらも **「相手が komaster」＝自分にとって最悪の仮定を先に解く**順序にしてある。
そこで目的を達成できれば無条件が確定するので、2回目の solve は不要。
**無条件が答えの問題（多数派）は常に1回で終わる。** コウが絡む問題だけ2回目に入る。

置換表のキーには `komaster` を含める（仮定が違えば別の探索木）。

| 現行 | 何をしていたか | 新方式 |
|---|---|---|
| `frame_ko` / `frame_ko_auto` | 枠にコウダテ形を仕込んで、どちらに渡すか自動選択 | `komaster` パラメータ（盤を触らない） |
| `ko_win_assumption` / `ko_win_visits` | コウ勝ち後の局面を KataGo で評価 | 不要 |

### 4.4 コウの細分（**正解がコウの問題では、ここまで要る**）

同じ「コウ」でも詰碁としての順位は違い、アプリの解答樹もそこを区別する:

```
守り方  無条件生き > セキ > 黒先劫（自分から取れる） > 白先劫（相手から取られる）
                          > ヨセコウ（n手ヨセ。n が小さいほど上）> 無条件死
```

4クラスだけだと「どちらもコウだが劣るほう」を選ぶ余地が残る。**答えがコウの問題は
実測でも最も誤りやすい**（case E/K/L/M/R/U/W）ので、ここは細分する。

**方法: komaster を「無限」ではなく「コウダテ n 個」にし、結果が反転する最小の n を求める。**

**`ko_budget` の消費規則（これが定義）**: komaster が**コウ禁止を無視して取り返す行為
1回につき budget を1消費**する（「コウダテを打ち、相手が受けた」2手を1手に畳んだ抽象なので、
無視回数＝必要コウダテ数）。budget が尽きた komaster は以後通常のコウ禁止に従う。
相手は常に budget 0（コウダテなし）で、通常のコウ禁止に従う。

```
ko_budget = 0, 1, 2, ... と増やして solve し、目的を達成できる最小の n を n* とする
  n* = 0        → コウ禁止の無視が不要＝自分が先に取り、相手は取り返せない（黒先劫）
  n* = 1        → 1回の無視（＝コウダテ1つ）が必要＝相手が先に取る形（白先劫）
  n* = k (k>=2) → k-1 手のヨセコウ相当
達成できる n が無い → そのクラスでは不可能
```

手の順位づけは `(ResultClass, n*)` の辞書順（クラス優先、同クラス内は n* 昇順）。
これで「両方コウだが自分から取れるほう」を正しく上に置ける。

実装は反復深化と同じ形で、`ko_budget` を増やしながら solve を繰り返す。
n* は実用上 0〜2 で頭打ちなので **最大3回**（クラス判定の最大4回〈§4.3.2.1〉と合わせて
最大7回。ただし短絡評価により実用上は1〜3回で終わる問題が大半）に制限する。
`solver_ko_refine`（既定 true）で無効化できるようにし、時間制限に達したら
細分を諦めてクラスのみで順位づけする（＝現行と同等の粗さに劣化するだけで壊れない）。

### 4.5 3値（死 < セキ < 生き）の2値分解

死活は Yes/No ではなく3値なので、そのままでは AND/OR 探索に乗らない。
**閾値ごとに別の boolean 探索として解く**（多値 → 2値の標準的な分解）:

- `solve(target が ALIVE〈2眼〉以上か)`
- `solve(target が SEKI 以上か＝取られずに残るか)`

§4.3.2 の表はこの2つの述語の組合せで書かれている。終端判定（§6.3）は
`DEAD / SEKI / ALIVE` の3値を返し、探索は閾値で2値化して扱う。

### 4.6 超コウ・repetition — **両コウ生きを潰さないこと**

素朴に PSK（Positional Superko）で「同一局面の再訪を禁止」すると、**両コウ生きが
無限ループとして処理され、守り方が目的不達成と判定される**。日本ルールでは両コウは
無条件生きと同等に扱われるので、これは実用上そのまま誤答になる。

**基本規則: repetition は「攻め手が詰まった」と読む＝守り方の勝ち**（既定則。
ただし**両コウ絡みのサイクルは §4.6.1 で別裁定**する — 定数則だけでは誤るため）。

```
局面（盤 + 手番）が探索経路上で再訪されたら、そのノードを終端とし
    goal=LIVE  の探索 → target は取られていない ⇒ その枝は成功（ALIVE 相当）
    goal=KILL  の探索 → 殺せていない            ⇒ その枝は失敗
と評価する（＝反復は常に「生かす側」に有利に裁定する）
```

根拠: 死活の文脈で同形反復が起きるのは「攻め方が有限手で殺せない」ことの証明であり、
それはそのまま「生きている」を意味する。長生はこの規則で**自動的に生きになる**
（両コウのサイクルは §4.6.1 の閉形式裁定が引き受ける — 両コウ生きは結果的に同じ「生き」、
両コウ死はここで「死」に分かれる）。

- 反復判定の履歴キーは**（盤 + 手番）のみ**。komaster や `ko_budget` の残量を含めると、
  komaster の取り返しで盤が元に戻るたび「budget が違うので別局面」となり、
  サイクルそのものを検出できなくなる
- 結果には `alive_by_repetition` フラグを立て、順位づけ上は `UNCONDITIONAL` と同格に扱う。
  ログ・GUI には「両コウ／同形反復による生き」と出す（利用者が納得できるように）

#### 4.6.1 両コウは反復の定数則だけでは裁けない（実装前に必ず読む）

「反復＝生かす側の勝ち」は**両コウ死で確実に誤る**:

- **両コウ死**（target に実眼0つ＋コウ口2つ、攻め方が両コウの取り返しを常に持つ形）:
  攻め方 komaster の solve でも「守り方が一方を取る → 攻め方が他方を取る」のサイクルが
  強制され、基本規則により ALIVE ⇒ **無条件生きと報告**。真の裁定は「死」
  （日本ルールで確立。攻め方は常に取り返しを持つので手を入れる必要すらない）
- 逆の定数則（反復＝komaster の勝ち）にすると、今度は**両コウ生き**（実眼1つ＋コウ口2つ）が
  攻め方 komaster の solve で死と報告される
- つまり**サイクルの勝敗は定数則では決まらない**。両者を分ける情報は反復規則の外＝
  局面の構造（サイクルに関与するコウの数・target の実眼の数）にしかない

採用する設計（3段構え）:

1. **両コウの閉形式裁定**: 反復検出時、サイクル中の着手がすべて「ちょうど2つのコウ点での
   取り合い」なら両コウと認識し、古典の閉形式で裁定する —
   target に実眼（コウ以外の確定眼）が1つ以上 → **生き** ／ 0 → **死** ／
   双方が実眼1つずつ＋両コウ → **セキ**（両コウゼキ）。
   実眼の判定は「その空点の隣接がすべて target 側の石で、Benson 流に欠け眼でないことが
   確認できる」場合のみ（保守的＝確信が持てなければ実眼と数えない）
2. **それ以外の反復**（長生・三コウ等）は基本規則（生かす側の勝ち）で裁定する
3. **taint の伝播と検算**: 反復裁定に依存した値には「サイクル裁定由来」ビットを立て、
   GHI と同じ要領で親へ伝播させる。root の結論が tainted なら
   `solver_cycle_verify`（既定 true）で **KataGo ownership 1本の検算**を掛け、
   食い違えばフォールバック（G5）。サイクル裁定に結論が依存する詰碁は稀なので、
   この検算が速度目標（§8.2）を害することはない

**日本ルールとの残差**（§12 の未解決に再掲）:

| 形 | 日本ルール | 本設計 | 扱い |
|---|---|---|---|
| 両コウ生き | 無条件生き | `UNCONDITIONAL`（`alive_by_repetition`） | 一致 |
| **両コウ死** | 死 | 閉形式裁定（§4.6.1）で **死** | 一致（基本規則だけでは誤るので専用裁定） |
| 両コウゼキ | セキ | 閉形式裁定で `SEKI` | 一致 |
| 長生 | 無勝負 | 生き扱い | 詰碁としては「殺せない＝失敗」なので実用上一致。テストケースを作って確認する |
| 三コウ | 無勝負 | 生き扱い（taint 付き） | 稀。taint → 検算 → 不一致ならフォールバック |
| 万年コウ | 手を出さず放置＝セキ的／仕掛ければコウ | `ko_level` 付きの `KO` | **要検証**。アプリの解答と突き合わせて判断する。基本形のテストを置く |

回帰は答えがコウの既存ケース（E/K/L/M/R/U/W）＋ 両コウ生き・**両コウ死**・両コウゼキ・
長生・万年コウの基本形で取る。

### 4.7 セキの定義 — **静的判定はしない（動的に落とす）**

初版は「静的に判定する」と書いていたが、これは**取り下げる**。一眼セキ・仮眼を含むセキを
静的に見切るのは Benson と違って厳密なアルゴリズムが自明でなく、誤検知（打てるのに
セキと判定／その逆）はクラスの誤りに直結する。**静的認識器は作らない。**

代わりに、セキを**探索の結果として定義する**:

```
セキ ＝ 「自分から打つとクラスが下がる手しか無く、パスすれば target が取られない」状態
```

これは §4.5 の2値分解と §4.8 のパスがあれば**自動的に出てくる**ので、専用ロジックが要らない。

**連続パス終端の評価（これが唯一の真の終端）**:

```
target = 危険な石の元座標の集合（§5.2.3）
残存連 := target の元石を1つ以上含む、盤上の連

残存連が無い                                  → DEAD
残存連のどれかが Benson の pass-alive         → ALIVE
それ以外（残っているが pass-alive ではない）  → SEKI
```

3行目が**セキそのもの**である。理由: 探索は「攻め方が取れるなら必ず取る」ので
（取れば目的が達成でき、値が上がる）、攻め方がパスしたということは
**取れないことの証明**になっている。

**注意 — この葉の裁定は「保守的」であって「正確」ではない**: 直四・板六のような
「攻められたら受ける」生き形は pass-alive ではないので、双方パスの葉では SEKI と
裁定される（真の値は生き）。それでもクラスが誤らないのは、**ALIVE の証明では守り方が
相手のパスに対して自陣内に打ち足して pass-alive 形へ変換できる**から
（直四なら中の1点に打てば実眼2つ＝Benson 成立。真に生きている連は、相手がパスを
続ける限り必ず有限手で pass-alive に到達できる — できないのはセキ生きと両コウ生きだけで、
前者は SEKI が正解、後者は反復規則〈§4.6〉が引き受ける）。
つまり ALIVE 判定の正しさは「葉の裁定が正確なこと」ではなく「守り方に打ち足しの
選択肢があること」に立っており、**この打ち足しは §4.2.1 の plies に数える**。
実対局では相手（アプリ）はパスしないので、表示上の本手順には現れない
（§4.2.1 の「相手はパスより盤上の手を優先」）。

この定義で自動的に片付くもの:

- **一眼セキ・仮眼セキ**: 静的認識器が要らない（「打つと下がるから打たない」が探索で出る）
- **捨て石（3子捨てて生きる）**: 捨てた石は消えるが、残存連が元石を含んでいれば `ALIVE`。
  target を**連ではなく点集合**で持つのはこのため（§5.2.3）
- **ダメ詰まりの深さ**: Benson の pass-alive は**ダメを詰めきる前に** `ALIVE` を確定できる
  ので、早期打ち切り（§6.3）が効く

残るのは「セキかどうかの見極めにダメを詰めるケース」だけで、region は必要十分に小さく
（§5.1）、TT + 対称性で同型局面の再訪も消える。それでも深い問題は時間制限 →
フォールバック（§8.4）で壊れない。

（`solve(SEKI 以上か)` は「target の元石を含む連が最後まで残るか」という**捕獲ゲーム**
そのものなので、実装も `ALIVE` 版と同じ探索器で述語だけ差し替わる。）

### 4.8 パスの扱い

領域外が着手禁止なので、**「他所に打つ＝パス」を両者の合法手として明示的に持つ**。
これが無いと「打つ手が無い側が損な手を強制される」ことになり、セキもコウも正しく出ない。
連続パスで終局し、そこで §4.7 の終端判定を行う。

## 5. 問題の抽出（`tsumego_problem.py`）— 枠の後継

**KataGo を一切使わない。** ここが現行との最大の違いで、キャプチャ時の 1.1〜5.7 秒が消える。

### 5.1 領域の確定 — **外ダメの過不足が結論を変える**

`region_pad` で一律に広げる方式は**採らない**。攻め合い・ナカデでは
**外ダメ（外気）が1つ違うだけで 無条件死 ↔ コウ ↔ 生き が入れ替わる**ため、

- **足りない** → 攻め合いに必要なダメが着手禁止領域に追いやられ、実際より攻め方有利になる
- **多すぎる** → 無関係なダメが双方の合法手として増え、手数（§4.2.1 の `plies`）が伸び、
  攻め合いの結論も変わりうる

**過剰包含も過少包含と同じくらい有害**なので、「必要十分な点だけ」を機械的に決める。

#### 構成規則: 呼吸点の推移閉包 + 空点連結の閉包

```
R := target の石（石の点も region に含める＝取り跡への打ち直しを合法にする。§4.1）
繰り返す:
    R += R に含まれる連のすべての呼吸点（空点）
    R += R の空点と**空点連結**な空点（壁石・盤端で止まる flood fill）   ← 眼空間の内部点
    R += R の空点に隣接する相手の連（＝攻め合いの相手）とその石の点
    R += その連のすべての呼吸点
終了条件: 新たに入る連が「外部と十分に連絡している」＝
          region 外に FRONTIER_LIBERTIES(既定 3) 以上の呼吸点を持つ
          （その連は壁として扱い、呼吸点は region に入れない）
```

2行目の**空点連結の閉包が無いと、「どの連の呼吸点でもない内部点」が region から漏れる**。
最小の反例は 3×3 の眼空間: 中心点の4近傍はすべて空点なので、呼吸点の閉包だけでは
中心が入らず、**ナカデの急所が着手禁止になる**（基本形が即誤答になるレベルの穴）。
また、この flood fill が壁・盤端で止まらず盤の広域へ抜けるなら、それ自体が
「閉じていない」の検出になる（封鎖検査と同じ計算を共有できる）。

これで「攻め合いに関与する連の呼吸点と眼空間の内部点はすべて入り、無関係なダメは
入らない」領域になる。
`region_pad` は**この規則が使えなかったとき（＝壁が見つからない）のフォールバック**に降格する。

**壁の仮定（明示しておく）**: 壁と判定した連は「生きている」ことをモデル上強制している
（壁の外側呼吸点は region 外＝詰める手が存在しないので、壁は探索中決して取られない）。
実盤面で壁が危ない問題では結論がずれるが、詰碁アプリの出題は壁が安全であることを
前提に作図されるので、この仮定は問題の設計と一致する。異常は下の region 検算で現れる。

#### 封鎖検査

1. region の境界に接する**解く側の石**が、region 外へ連絡できるか
   → できるなら「逃げ出せる」＝詰碁として閉じていない
2. target が region 外に呼吸点を持つか → 持つなら閉じていない
3. 閉じていなければ `FRONTIER_LIBERTIES` を上げて再構成。規定回数で閉じなければ
   **フォールバック**（現行の枠張りは「無理やり閉じさせる」道具として有効なので、
   ここでこそ使う）

#### region 妥当性の検算（CI・校正時のみ）

構成規則が正しく効いているかは、**領域を1周ぶん広げても結論が変わらないこと**で確かめる。

```
solve(region) と solve(region + 1ring) の (ResultClass, ko_level) が一致すること
```

一致しなければ region が不十分（または過剰）で、問題抽出のバグ。
実行時は重いので**校正スイート（`e2e_suite.py --check-region`）でのみ回す**。

現行の「壁を敷く」は、KataGo に領域外を無視させるための道具だった。ソルバは
`region` 外に着手しないので**壁石を置く必要がない**（盤面が認識どおりのまま出題される
＝GUI 表示も原問題と一致する、という副次的な利点がある）。

### 5.2 対象石群と問題の型の決定

現行は「枠の壁の色」から読むため**枠なしでは None**（＝役割非依存の劣化動作）。
新方式は KataGo を使わず静的に決める。

#### 5.2.1 「危険な石」の定義

```
at_risk(chain) ＝ chain が region 内で完結している（＝壁ではない）
                  かつ 初期局面で Benson の pass-alive でない
```

- **壁**は §5.1 の構成規則で「region 外に `FRONTIER_LIBERTIES` 以上の呼吸点を持つ」として
  既に切り出されているので、判定は使い回せる
- **既に2眼で生きている石は除外**される（Benson）。これが効くので、
  「関係ない生きた石が混ざって型を誤る」ことが起きない
- **限界**: Benson が除外できるのは pass-alive だけで、「直四のように明らかに生きているが
  pass-alive ではない」連は at_risk に**含まれてしまう**。含まれても LIVE の成否判定は
  正しい（実際に生きるので成立する）が、target の合併（§5.2.4）で region が不要に広がる・
  型判定が攻め合い側に振れる可能性がある。対策は §5.2.4 の合併 + region 検算 + ログで、
  P1 の実測で実害が出た場合のみ「候補連ごとの小 solve で既生き連を除外する」前処理を足す

#### 5.2.2 問題の型（初版の「両方 → 上位クラスを採る」は撤回）

初版は「黒白の両方に孤立群があれば両方解いて上位クラスを採る」としていたが、これは
**比較不能なものを比べている**（「黒が生きるか」と「白が死ぬか」は別の問いで、
`ResultClass` の尺度が違う）。攻め合いは**第3の型**として明示的に扱う:

| 黒に危険な石 | 白に危険な石 | 型 | 黒から見た順序 |
|---|---|---|---|
| ✓ | ✗ | **守り（生き）** | 無条件生き > セキ > コウ > 死 |
| ✗ | ✓ | **攻め（殺し）** | 無条件死 > コウ > セキ > 相手の生き |
| ✓ | ✓ | **攻め合い** | 攻め合い勝ち > コウ > セキ > 負け |
| ✗ | ✗ | 詰碁でない | 抽出失敗 → フォールバック |

攻め合いの順序が「攻め」と同じなのは、攻め合いでは**負ける＝自石が死ぬ**なので、
黒にとって実質的に攻め方の問題になるため（セキが下位に来るのもこの理由）。
`RESULT_ORDER[problem_type]` として3通り持つ。

#### 5.2.3 目的（goal）の述語

`target` は「危険な石」の**元の座標の集合**（連ではなく点集合）として持つ。
これは**捨て石を正しく扱う**ために必要で、連で持つと「3子捨てて生きる」が表現できない。

```
LIVE  成立 ⇔ 終局時に target の元石を含む連が残っており、それが生きている
KILL  成立 ⇔ 終局時に target の元石を含む連が1つも残っていない
攻め合い勝ち ⇔ 相手 target に KILL が成立し、かつ自 target に LIVE が成立
```

「3子捨てて生きる」は、捨てた3子は消えるが**残りの元石を含む連が生きている**ので
`LIVE` が成立する。逆に「全部取られた」ときだけ `DEAD` になる。

#### 5.2.4 同色に危険な石が複数あるとき

同色の危険な連が複数ある場合は**まとめて1つの target（点集合）にする**。
詰碁の図では通常ひとつの戦いなので、これで足りる。
分離した2つの戦いが同時に写り込んだ場合は誤るが、その場合は
§5.1 の封鎖検査か region 妥当性検算（1周広げても不変か）で異常として現れる。

**判定結果は必ずログに出す**（型・target の座標・壁と判定した連）。
今回の調査で最も効いたのは「どの経路で分岐したかがログから読めること」だった。

現行の `guess_black_to_attack`（極値線の石で推定）と `frame_destroys_problem`
（手番側が生きているかで枠を捨てる）は**まるごと不要**になる。case S（役割推定の反転）
も case N（有効な枠を捨てる）も、この段階で構造的に発生しなくなる。

### 5.3 出力

```python
def extract_problem(grid, *, board_size, to_play=BLACK, pad=1) -> Problem | ProblemError
```

`ProblemError` は「閉じていない」「対象群が無い」「領域が大きすぎる」等。
呼び出し側はこれを見てフォールバックする。

## 6. ソルバの設計

### 6.1 アルゴリズム

死活は**決定問題**（「target は生きるか？」の Yes/No）なので、評価関数で順位をつける
必要がない。AND/OR 木の証明・反証を数える探索が本命になる。

**採用: λ探索（Thomsen）+ df-pn（depth-first proof-number search, Nagai）**

- **OR ノード**（解く側の手番）: どれか1手で目的達成できれば証明
- **AND ノード**（相手の手番）: すべての応手で目的達成できれば証明
- **df-pn**: 証明数/反証数の小さい枝を深さ優先で掘る。置換表必須
- **λ探索**: 「λ^1 = 直接の取り」「λ^2 = 取りの脅威を含む」…と脅威の階層で
  着手生成を段階的に広げる。浅い λ で解ければそこで終わる＝典型的な詰碁が速い

補助として **αβ + 反復深化**も実装し、両者を切り替えられるようにする（df-pn は
GHI 問題〈同一局面異経路〉の扱いが繊細なので、正しさの相互検証に使う）。

### 6.2 着手生成

- `region` 内の**現在**空点のみ（取り跡を含む。§4.1）＋ パス（§4.8）
- 自殺手の除去（連結後の呼吸点0、かつ取れない）
- **明らかに無意味な手の除去**は入れない（厳密性を壊すため）。速度は順序付けで稼ぐ
- 順序: (a) 直前手の隣接 (b) アタリ/取り/逃げ (c) 眼形の急所（静的パターン）
  (d) **KataGo の policy**（任意・§8.5）

### 6.3 終端判定

**「早期打ち切り（健全な近道）」と「真の終端」を分けて考える。**
前者は誤ってはならないので、厳密性が証明されているものだけを使う。

**早期打ち切り（どちらも厳密。誤検知しない）**

1. **取られ確定**: target が盤上から消えた／呼吸点0で相手の手番 → `DEAD`
2. **Benson の無条件生存（pass-alive）**: target が以後何をされても取られないことを
   多項式時間で厳密判定 → `ALIVE`。**最も効く打ち切りで、ダメを詰めきる前に決まる**
3. **眼形テーブル**: 小さな眼のスペース（1〜7点）の生死を事前計算した表で即決。
   表は「厳密に解いた結果」を焼き込むので近似ではない

**真の終端**

4. **連続パス**: 双方がパスしたら終局。target が盤上に残っていれば `SEKI` 以上、
   そのうち Benson を満たすものが `ALIVE`（§4.7）
5. **同形反復**: §4.6 の規則で「生かす側の勝ち」として終端

**セキ専用の静的認識器は持たない**（§4.7 で取り下げ）。セキは 4 と §4.5 の
2値分解から自動的に出る。

Benson と眼形テーブルは**問題ごとに1回**構築すればよく、探索中は表引きになる。

### 6.4 置換表と対称性

- Zobrist ハッシュ（盤 + 手番 + コウ点 + λ レベル）
- **キーには探索条件を全部含める**: `(position, komaster, goal, threshold, ko_budget)`。
  同じ盤面でも仮定が違えば答えが違うので、ここを省くと静かに誤答する（§6.6）
- TT エントリ: `(key, proof, disproof, best_move, depth, flags)`
- **8対称の正規化**でヒット率を上げる（領域が矩形なら対称性が残る）
- **証明済みエントリは sticky**（暫定値と別扱いにし、置換対象から外す）＝§6.6 の証明ストア
- 反復判定の履歴キーだけは**（盤 + 手番）のみ**で、komaster / `ko_budget` 残量を含めない
  （§4.6。含めると komaster の取り返しで盤が戻るたび「budget が違うので別局面」となり、
  サイクルそのものを検出できなくなる）
- 問題をまたいで保持する（同じ詰碁の再出題・樹から外れた再探索が速くなる）

### 6.5 出力（解答樹）

```python
@dataclass
class Solution:
    value: SolutionValue                  # (result, ko_level, plies, material)
    komaster: Color | None                # どの仮定で成立したか
    alive_by_repetition: bool             # 両コウ等（§4.6）
    cycle_tainted: bool                   # 結論がサイクル裁定に依存（§4.6.1 → 検算対象）
    root_moves: list[Move]                # root の同格手すべて（先頭が本手。§6.5.1）
    principal_line: list[Move]            # 本手順（表示・ログ用）
    nodes: int
    elapsed_ms: float
```

**「全応手を展開した辞書」は持たない**（§6.6 でサイズが破綻するため）。
2手目以降の即応答は**証明ストア**（§6.6）が担う。

#### 6.5.1 別解（同格の複数正解）を持つ

詰碁には「A でも B でも無条件生き」という**同格の別解**が普通にある。
OR ノードの手を1つしか持たないと、利用者が B を打った瞬間に「樹から外れた」と判定され、
**正解なのか不正解なのかをアプリ側で答えられない**。そこで `list[Move]` にして
**`SolutionValue` が同値の手をすべて**（既定で最大 `solver_max_alternatives`=8）保持する。

コストは無視できないので**深さで使い分ける**:

| ノード | 探索の打ち切り | 保持 |
|---|---|---|
| **root（初手）** | 打ち切らず**全合法手を評価**する | 同値の手を全部（別解リスト） |
| 深い OR ノード | 最初の証明で打ち切る（従来どおり） | 本手1つ |

root だけ全手評価にする理由は3つあり、いずれも root でしか効かない:

1. **§4.2.1 のタイブレーク**（手数・犠打）は全手の値を比べないと決まらない
2. **別解リスト**が要るのは利用者に見せる初手だけ
3. **§12 の「解答樹に無い別解」の緩和**: 同値の手が複数あるとき、アプリの解答樹に
   載っていそうなほう（＝犠打が少なく手数が短い本手、必要なら KataGo policy 最上位）を
   選べる。現行のスコア同着コイン投げ（case J/K）より当たりやすくなる

**「全手評価」＝「全手をフル分類する」ではない。** αβ と同じ要領で
**現職最良値（incumbent）との閾値テスト**で振るう: 最初の候補（着手順序の先頭）だけ
フル分類して incumbent とし、以降の手は「incumbent と同値以上か」を判定できる最小限の
solve（大半は最悪仮定1本の速攻反証）で落とす。incumbent に並ぶ／上回る手だけ
細分（ko_level・plies・material）まで解く。root 全手評価の上界が「合法手数 × フル分類」
に見えるのは見かけだけで、実際は「合法手数 × 反証1本 + 同格手数 × フル分類」で済む。

深い OR ノードで利用者が別解を打った場合は、その局面から**再探索**する
（証明ストアが温まっているので数 ms〜数十 ms）。再探索の結果が同じクラスなら
「別解として正解」、下がっていれば「不正解」と**明確に答えられる**（現行は答えられない）。

### 6.6 解答樹のサイズ制御 — **樹は materialize せず、証明ストアで持つ**

初版は `tree: dict[PositionKey, Move]` に「AND ノードの全応手を展開して持つ」としていたが、
これは**サイズが破綻する**。空点 25 点の region で AND ノードの分岐が ~25、OR ノードが 1 なら

```
深さ 6手  25^3 ≒ 1.6 万エントリ      （持てる）
深さ 10手 25^5 ≒ 970 万エントリ      （持てない）
深さ 14手 25^7 ≒ 60 億エントリ       （論外）
```

詰碁は 10手を超えるものが普通にあるので、全展開は成立しない。

#### 採用する設計: 証明ストア（persistent proof store）

**探索の置換表そのものを解答樹として使う。** df-pn は各局面の証明/反証を TT に書くので、
**証明済みエントリを消さずに保持すれば、樹を別途作る必要がない**。

```
proof store: key = (position_hash, komaster, goal, threshold, ko_budget) → 証明済みの値
```

- **キーに探索条件を全部含める**（同じ盤面でも komaster や閾値が違えば別の答え）。
  ここを省くと静かに誤答するので、実装上の最重要ポイント
- 証明済み（`proved`）エントリは**sticky** にし、探索中の暫定値（bound）とは別扱いで
  置換対象から外す。容量が尽きたら LRU で落とす
- **落としても正しさは壊れない**（ミス＝再探索するだけ）。容量は
  `solver_proof_store_mb`（既定 64MB ≒ 100万エントリ規模）

#### 応答フロー

```
利用者（白）が着手
  → その局面を証明ストアに問い合わせ
      ヒット   → 即座に手が出る（< 10ms）             ← G4 の根拠
      ミス     → その局面から再探索。部分木の大半は証明済みなので通常 < 50ms
  → 着手が region の外だった場合は問題を再抽出してから解き直す（§5.1。ログに残す）
```

つまり「全応手を先に展開しておく」のではなく、**必要になった枝だけ即座に返す**。
最悪でも再探索1回ぶんで、しかも証明済み部分木を再利用するので実用上は無視できる。

#### 永続キャッシュ

`solver_cache` が有効なら、**root の `Solution` だけ**をディスクに保存する
（`~/.katrain/tsumego_cache/<problem_hash>.json`）。同じ詰碁を再出題したときに
初手が 0 秒で出る。証明ストア本体はメモリのみ（永続化するとサイズが読めないため）。

### 7.1 言語

探索は Python では成立しない（1局面あたり数十万〜数百万ノード）。

## 8. 速度設計（要件の中心）

### 8.1 現行の実測ベースライン

| 区間 | 実測 |
|---|---|
| キャプチャ〜認識 | 0.1〜0.3 秒 |
| 枠の採否判定（KataGo 最大5本） | **1.1 秒（健全枠）/ 2.9 秒（枠を救う）/ 3.3〜5.7 秒（全枠が死）** |
| 初手のリージョン解析（1800visits・コールド） | 1.5〜2.5 秒（エンジン起動直後は 37〜46 秒） |
| 初手の選択則（追加解析 1〜12本） | **2.0〜9.5 秒** |
| 2手目以降 | 0.2〜4.5 秒（先読みヒット時 0.2〜0.4 秒） |

**合計: 出題まで 1.4〜6.0 秒、初手まで さらに 3.5〜12 秒。**

### 8.2 新方式の目標

| 区間 | 目標 | 根拠 |
|---|---|---|
| キャプチャ〜認識 | 0.1〜0.3 秒 | 現行流用・変更なし |
| 問題抽出（領域・役割） | **< 0.05 秒** | 純粋な静的解析（Benson は多項式時間） |
| ソルバ（13路・典型的な詰碁） | **< 1.0 秒** | §8.3 |
| 初手着手 | **< 1.2 秒**（現行 3.5〜12 秒） | 上記の合計 |
| 2手目以降（証明ストアにヒット） | **< 0.01 秒** | 表引き（§6.6） |
| 2手目以降（ミス＝再探索） | **< 0.05 秒** | 部分木の大半が証明済み |
| 同じ問題の再出題 | **0 秒** | 永続キャッシュ（§6.6） |

**KataGo のクエリ往復・GPU 推論が経路から消えることが速度改善の主因。**
死活は決定問題なので NN 評価を必要としない。

### 8.3 ソルバの高速化の柱

1. **NN 不要** — GPU 往復（1本 0.2〜2.5 秒）がゼロになる
2. **Benson + 眼形テーブル** — 典型的な形は探索せず即決
3. **λ探索の段階化** — 浅い λ で解ける問題（大半）は探索が小さいまま終わる
4. **置換表 + 8対称の正規化** — 同型局面の再探索を消す
5. **着手順序** — killer / history / 直前手隣接 / 眼形の急所
6. **証明ストア（§6.6）** — 2手目以降を表引きにする。樹を materialize しないので
   メモリが読め、ミスしても再探索するだけで壊れない
7. **投機実行** — ホットキー押下 → 認識完了の直後にソルバを開始し、GUI 描画と並行させる
   （Rust 側は GIL を解放して走る。証明ストアはソルバ内部のデータで、Python 側と
   共有するのは結果オブジェクトだけ＝スレッド安全性の問題を作らない）
8. **root Solution の永続キャッシュ** — 盤面ハッシュ → Solution（`~/.katrain/tsumego_cache/`）。
   同じ問題を2回目に出したときは **0 秒**

### 8.4 探索が爆発したときの制御

- **事前の門前払い**: region の点数が `solver_max_region_points`（既定 40）を超える問題は
  solve を試みずフォールバックする（探索爆発を事後検出でなく事前に避ける）。
  上限値は P1 で全20ケースの region 点数と solve 時間の分布を実測して調整する
- `solver_node_limit`（既定 2,000 万ノード）と `solver_time_limit_ms`（既定 3000）
- 到達したら **未解決として返し、現行経路へフォールバック**（G5）
- λ レベルごとに時間を配分し、浅い λ で解けたらそこで返す

### 8.5 KataGo の残る役割（任意）

ソルバの**着手順序**にだけ policy を使える（`solver_use_policy`）。

- 厳密性には影響しない（順序を変えるだけ）
- ただし policy 取得に 0.2〜2.5 秒かかるため、**既定は OFF**。
  ソルバ単体が時間制限に達する難問でのみ有効化する価値がある
- 現行の value ベースの誤読（case Q の「準備手を負けと読む」）に**引きずられない**

## 9. 戦略への統合

### 9.1 新戦略 `ai:tsumego_solver`

```
generate_move():
    1. 証明ストアに現局面がある → その手を返す（解析0本・< 10ms。§6.6）
    2. 無ければ
       a. 着手が region の外だった等で問題が変わっていれば Problem を再抽出
       b. ソルバを起動（証明ストアは温存されているので部分木を再利用）
       - 解けた → root の Solution を保存し、手を返す
       - 解けない/打ち切り → フォールバック（§9.2）
```

**照会プロトコル（キーの取り違えは静かな誤答になるので明文化する）**: 戦略は出題時に
確定した**問題コンテキスト**（Problem・問題の型・確定クラス・そのクラスを成立させた
`komaster` / `ko_budget` / threshold）を保持し、ステップ1の証明ストア照会は
**このコンテキストのキー**で行う（§6.6 のキーは5要素タプルなので、局面ハッシュだけでは
引けない）。相手の着手で局面が想定から外れたら、まず同じコンテキストで再 solve し、
値が変わりうる（相手が緩めた／逆に厳しい手を発見した）場合は分類ラダー（§4.3.2）を
回し直してコンテキストを更新する。

**実対局のコウ（違法手の防止）**: 解の手順には「komaster 仮定でのみ合法な取り返し」が
含まれうる。**実盤面でコウ禁止に当たる手は絶対に打たない** — 着手前に必ず実ルールでの
合法性を検査し、違法なら region 内の別手（クラスを保つ手があれば）かパスを返し、
ログに「コウ待ち」と残す。実用上、答えがコウの問題はアプリ側が最初のコウ取りで
正解判定を出すことが多いので、ここに到達すること自体が稀。

利用者（白）が本手順から外れても、**外れた局面から解き直すだけ**なので破綻しない。
解が下位クラスに落ちたなら「白の手が緩んだ」ということなので、黒はより良い結果を取りに行く。

`ai:tsumego`（現行）は削除せず残し、設定で選べるようにする。

### 9.2 フォールバック方針（G5 の担保）

| 状況 | 動作 |
|---|---|
| 領域が閉じていない | 現行の枠張り経路へ（枠は「閉じさせる」道具として有効） |
| 対象石群が決まらない | 現行経路へ |
| ノード/時間制限に到達 | 現行経路へ。ログに「ソルバ未解決」と残す |
| ソルバが `FAILED`（＝この詰碁は解けない）を返した | **詰碁側/認識側の問題**として警告し、現行経路へ |

フォールバックは**必ずログに理由を出す**。現行機能の調査で最も効いたのは
「どの経路で分岐したか」がログから読めることだった（`--debug`）。

## 10. 検証計画

### 10.1 単体（KataGo 不要・CI で回る）

- **教科書の基本形**: 直四・曲四・板六・欠け眼・ナカデ各種・セキの基本形・両コウ …
  期待クラスを直書きしたテーブルテスト
- **コウの分類（§4.3/§4.4 の受入テスト。最優先）**: 答えがコウの基本形について
  `(ResultClass, n*)` を直書きで検証する。特に
  - **単一 solve では `KO` が返らないこと**を明示的にテストする（回帰の要）。
    komaster を片方だけ与えた solve が「無条件」と報告し、2通りの突き合わせで
    初めて `KO` になることをアサートする
  - 黒先劫（n*=0）と白先劫（n*=1）が区別されること
  - ヨセコウ（n*>=2）がコウより下に順位づけされること
- **同クラス内のタイブレーク（§4.2.1）**: 「黙って生きれば1手で正解」の形に対し、
  無駄なアタリを挟む手順が**選ばれないこと**（`plies` で落ちる）。
  3子捨てが正解の形で、4子にしてから捨てる手順が選ばれないこと（`material` で落ちる）
- **セキ（§4.7）**: 一眼セキ・仮眼セキの基本形で `SEKI` が返ること。
  **静的認識器を持たない**ので、テストは「探索の結果として出る」ことの確認になる
- **同形反復（§4.6）**: 両コウ生きが `UNCONDITIONAL`（`alive_by_repetition=True`）に
  なること。**両コウ死が「死」と裁定されること**（「反復＝生かす側の勝ち」の定数則では
  無条件生きと誤る回帰点。§4.6.1 の閉形式裁定が効いていることの確認）。
  両コウゼキが `SEKI` になること。taint → `solver_cycle_verify` の検算 → 不一致で
  フォールバック、の経路が通ること。長生・万年コウは期待値を実測してから固定する
- **混合クラス（§4.3.2.1）**: 「コウに勝ってもセキ」（A=✗ S=✗ A'=✗ S'=✓）の人工形で、
  失敗クラスに落ちずに KO の下位細目として報告されること（初版ラダーの回帰点）
- **取り跡への打ち直し**: 石の下・ウッテガエシが正解の基本形。region を「初期の空点」で
  持つ実装はここで壊れる（§4.1 の回帰点）
- **眼空間の内部点**: 3×3 眼空間（中心がどの連の呼吸点でもない形）で、ナカデの急所が
  region に入り、殺しが成立すること（§5.1 の空点連結の閉包の回帰点）
- **隅の曲がり四目**: ソルバは `KO`（攻め方 komaster で殺し成立）を返す。日本ルールの裁定
  「無条件死」との差は**既知の残差**として期待値をテストに直書きする（変えるときは意図的に）
- **別解（§6.5.1）**: A/B 二通りの無条件生きがある形で、root の別解リストに両方入ること
- **region 構成（§5.1）**: 外ダメが1つ違うと結論が変わる攻め合いの基本形で、
  構成規則が必要な呼吸点をすべて含み、無関係なダメを含まないこと。
  `solve(region)` と `solve(region + 1ring)` が一致すること
- **問題の型と target（§5.2）**: 守り / 攻め / 攻め合い の3型が正しく判別されること。
  特に **(a)** 生きた石が混ざっても Benson で除外されて型がぶれないこと、
  **(b)** 攻め合いが「守り」や「攻め」に落ちないこと、
  **(c)** 捨て石（3子捨てて生きる）で `LIVE` が成立すること（target を点集合で持つ効果）
- **証明ストア（§6.6）**: キーに `komaster / goal / threshold / ko_budget` を含めないと
  誤答することを、**わざとキーを削った実装で再現するテスト**で固定する。
  ストアを空にしても結論が変わらないこと（＝ミスは再探索するだけで正しさに影響しない）
- **Benson**: pass-alive の既知例（KataGo/GnuGo のテストケースと突き合わせ）
- **参照実装との差分**: 同じ Problem に対し Python 参照実装と Rust 実装が同じ
  `ResultClass` を返すこと（ランダム生成した小領域問題 1000 件）
- **問題抽出**: 既存20ケースの SGF から Problem を作り、役割・対象群が期待どおりか

### 10.2 E2E（既存資産の再利用）

`e2e_suite.py` に `--solver` を足し、**同じケース表**（SGF・region・正解手順 `line`・
回帰点 `expect`）で両モードを回す。

```bash
python docs/superpowers/specs/calibration-data/tsumego/e2e_suite.py --full            # 現行
python docs/superpowers/specs/calibration-data/tsumego/e2e_suite.py --full --solver   # ソルバ
```

**受入基準**:

| ケース | 現行 | ソルバの目標 |
|---|---|---|
| D/E/F2/G2/H/J/K/L/M/O/P/T/U/V/V2 | PASS | PASS（維持） |
| **R**（答えがコウ・枠なし） | 3手目に 1/4 の誤答 | **PASS（コウを厳密に分類）** |
| **W**（答えがコウ・枠なし） | 初手に 5〜6/22 の誤答 | **PASS** |
| **I**（守り方の無条件生き） | 未対処 | **PASS**（KataGo の探索崩壊に依存しない） |
| **Q**（準備手が正解） | 未対処 | **PASS**（value の誤読に依存しない） |
| **F**（壊れた枠の盤） | 参考値 | 「閉じていない/解けない」と正しく報告 |

**case I / Q / R / W が解けることが、この作り直しの成否そのもの**である。
これらはすべて「スカラーでは分離できない」と実測で結論した局面で、
厳密解ならクラスが直接出る。

### 10.3 性能回帰

`e2e_suite.py` の `[analyse Xs / generate Ys]` 表示を拡張し、ソルバモードでは
`[extract Xms / solve Yms / nodes N]` を出す。ケースごとの solve 時間を
`docs/.../calibration-data/tsumego/solver-timings-<date>.md` に記録する。

### 設計から実装への具体化（スペックの記述を上書きするもの）

1. **反復検出キーは（盤 + 手番 + コウ禁止点 + パス数）**。§4.6 の「（盤 + 手番）のみ」に
   コウ禁止点を足した。含めないと **komaster がコウ禁止を無視して取り返した直後に
   偽の同形反復が発生**し（盤と手番が2手前と一致する）、単劫が基本則「生かす側の勝ち」で
   誤裁定される。komaster / budget 残量を含めない点は設計どおり（サイクル検出を保つ）。
2. **ネイティブは PyO3 でなく C ABI（cdylib + ctypes）**。ビルド・配布が単純で
   Python 側のバージョン非依存になる。ツールチェーンは MSVC が無い環境のため
   **stable-x86_64-pc-windows-gnu**（rustup で導入済み、`rustup default` 設定済み）。
   ビルド: `cd native/tsumego && cargo build --release --target x86_64-pc-windows-gnu`
   → `katrain/core/tsumego_solver/katrain_tsumego.dll` へコピー。DLL が無い環境は
   自動的に Python 参照実装で動く（§12 の想定どおり）。
3. **役割分担: 分類ラダー・コウ細分・root 全手評価は Python（ReferenceSolver）に一本化**し、
   ネイティブは solve_after / optimize_after の2カーネルだけを差し替える（NativeSolver は
   ReferenceSolver のサブクラス）。繊細な裁定ロジックが一箇所になり、差分テストも自然に成立する。
4. **df-pn の GHI 対応**は DFS と同じ「経路依存の証明/反証は TT に書かない」方式。
   実装上の要点3つ（どれを落としても壊れる）:
   - **子の状態は初回 probe 後、再帰の戻り値で更新する**。probe（TT 照会）だけに頼ると
     GHI 抑制で TT に載らなかった証明が親から見えず、同じ子を無限に選び直すライブロックになる。
   - **taint / dep は「値を決めた子」だけから取る**（OR の証明 / AND の反証 = 決め手の子1つ、
     OR の反証 / AND の証明 = 全子）。全子から min すると、コウ近傍の証明が軒並み TT 抑制になり
     再展開の連鎖で爆発する（実測 case D: 3M ノードでも終わらず → 修正後 60k）。
   - しきい値は 1+ε（ε=1/4）で渡す（再降下の抑制。実測 case D の S'(C2) 反証: 3M 超 → 60k）。
5. **毎ノードの Benson をやめ、「同一連の完全眼2つ」の安価な生存確定**を早期打ち切りに使う
   （両眼への打ち込みは常に自殺手なので健全）。Benson は連続パス終端（§4.7 の裁定）でだけ走る。
   大きな眼空間の pass-alive は見えなくなるが、探索が数手先で眼を確定させるので値は変わらない。
6. **§5.1 の空点連結の閉包は「全部入れる」と枠のチャンバーで爆発する**（実測 case E:
   壁内の空点 50+）。吸収連からの空点 BFS を深さ2（呼吸点 + 眼空間内部点）+
   12点以下の小成分は丸ごと、に制限し、**残る遠地帯は境界が単色のときだけその色の石で埋めて
   region から外す**（fill。壁の生存仮定〈§5.1〉と同種の「地の仮定」。Problem.fill_black/white
   に保持し、GUI 表示には使わない）。
7. **種（§5.1 の R の初期値）は「単独で閉じ、かつその閉包の中で自色の壁/地へ到達できない連」**
   （anchor）。全候補を種にすると壁側の連（地に裏打ちされた囲い）が region を膨張させる
   （実測 case D: 16点 → 43点）。「到達できる」には呼吸点 7 以上（SAFE_LIBERTIES）も含む。
8. **チャンバー内に散在する複数連の fight**（実測 case T/U/J: 遠地帯の境界に未吸収の fight 連が
   混在して閉包が失敗）は、遠地帯境界の hint 内非壁連を発見的に吸収して繰り返す。
9. **石で閉じない枠なし盤（実測 case W/I/G2/R）は「矩形 region モード」**: hint 矩形そのものを
   region にする（現行パイプラインの region_of_interest と同じ意味論）。開いた境界
   （盤端でない辺）に呼吸点を持つ連は「外の石」として target から除外し、両色が内部に残る
   場合は極値線の石の多数決（現行 `extremum_stones` の移植 + 総石数タイブレーク）で攻め方を
   推定する。§5.2 の「KataGo を使わず静的に決める」は維持。
10. **攻め合い判定に共有呼吸点テスト**を追加（§5.2.2 の具体化）: 両者が「内包」または
    「非内包」で対称なときは、危険な連同士が呼吸点を共有する（=ダメを争う）ときだけ攻め合い。
    共有が無ければ内外の関係で、呼吸点の少ない側が target。
11. **§9.1 の「着手が region の外だった場合は問題を再抽出」を実装**（セッションと P1 スイートの
    両方）。再抽出後の problem には現局面の石が焼き込まれるので、カーネル再生成時の二重適用を
    `_baked_moves` で防ぐ。実測 F2@4: ply0 の region のままだと SEKI に化ける（正解の
    コウ手 N11 の周辺が region 外）→ 再抽出で KO/N11 に戻る。
12. **SolutionValue の順序は (class, sub_demotion, ko_level, plies, material)**。§4.3.2.1 の
    「下位細目は ko_level の後」と「同クラス末尾に置く」の2記述が衝突するため、後者
    （細目は常にクラス末尾）を採用。
13. **root 候補としてのパスに二重パス終端のアーティファクト**がある: 攻め方の問題で
    「攻め方が root でパス → 守り方もパス → §4.7 評価で SEKI」となり、パス候補が実際より
    良く（SEKI に）分類される。攻め方の順序では KO > SEKI なので実手を差し置いて選ばれる
    ことはなく、方向は安全（パスの過小評価は起きない。守り方のセキでパスが本手になるのは正しい）。
14. `solver_time_limit_ms` の既定は当面 **30000**（§9.3 の 3000 は P4 最適化完了後の値として
    再検討）。時間切れは現行経路へのフォールバックなので安全側だが、3000 だと現状は
    難しめの問題が軒並みフォールバックしてソルバの意味がなくなる。
15. **証明ストアの手番またぎ**は Rust 側の `advance_root`（op="play"）で実現（§6.6 / G4）。
    盤を root ごと進めて TT（位置キー）を温存する。実対局のコウ禁止点は root_ban として
    カーネルにも伝わる。永続キャッシュは root Solution の本手だけを
    `~/.katrain/tsumego_cache/<sha1>.json` に保存（§6.6 の設計どおり）。
