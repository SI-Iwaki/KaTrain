# 詰碁キャプチャ: 枠なしモード（認識盤面そのまま＋タイトなリージョン）設計書

日付: 2026-07-29
ステータス: 実装済み・**既定は枠モードに差し戻し**（下記「実機検証の結果と結論の訂正」参照）

## 目的

詰碁キャプチャで枠（tsumego frame）を張るのをやめ、**詰碁アプリと完全に同一の盤面**をそのまま解析する。
盤全体の手が最善手になる問題は、枠ではなく**解析リージョンを石群に密着させること**で防ぐ。

枠は盤面を約80子書き換えるため、攻守判定・充填バランス・壁の配置・非コア石の削除と壊れる箇所を大量に作る。
枠を廃せばこれらの故障モードがまとめて消え、盤面がアプリと同一になるので
「アプリの正解手と KataGo の最善手が食い違う」ときの切り分けも容易になる。

## 詰碁の正解判定ルール（ドメイン前提）

アプリ側の正解判定は**対象石群の死活ステータス**で決まる。盤全体の目数ではない。

| 手番 | 正解 | 不正解 |
|---|---|---|
| 黒が攻める | 白を殺す／完全に殺せなくてもコウ・セキにする | 白が生きる |
| 黒が守る | 黒が生きる／完全に生きられなくてもコウ・セキにする | 黒が死ぬ |

ここから2つの帰結がある。

1. **正解手は複数あり得る**。殺す手とコウにする手はどちらも正解。KataGo が別の手を選んでも
   それがコウ・セキ以上を達成していれば正解になる。逆に、目数で最善でも白を生かす手は不正解
2. **KataGo の目的関数（盤全体の目数最大化）と正解判定の目的関数（局所の死活）は一致しない**。
   目数では僅差でも死活が変わる手があり、これが誤答の一因になる

本設計はリージョンを石群へ密着させることで、死活に関係しない手を候補から外して両者を近づける
アプローチである。目的関数そのものを死活に置き換える案は「将来の方向性」に記す。

## 背景: 枠バランス校正が成立しないことの実測

先行ブランチ（`ee0376c` でマージ）で配線バグ4件を修正した後も誤答が残った。
原因は「枠バランスが飽和し、詰碁の成否が勝敗を決めていない」ことだと判断し、
バランスをクローズドループで校正する案を検討したが、**実測により3段階で否定された**。

### 1. `defense_area` は使えるノブではない

M10 ケースで `put_outside` の `defense_area` を delta セルずらして測定:

| delta | 外側 B/W | root scoreLead |
|---|---|---|
| −8 | B2 / W44 | +8.74 |
| 0 | B2 / W40 | +9.44 |
| +8 | B2 / W38 | +12.29 |

±8セル動かしても 1〜3目しか変わらず、単調ですらない。原因は `put_outside` の
`empty_p` 市松模様で、外側の大半が石ではなく**空点**であること（黒石は全条件で2子のまま）。
配分をずらしても守り側の石が空点に変わるだけで地の帰属が動かない。

### 2. コミは線形なノブだが、バランスを取っても正解にならない

case B でコミを 7.0 → −19.5 に変更すると root scoreLead は −26.77 → **+1.46**
（シフト26.5に対し実測28.2でほぼ線形）。ノブとしては機能する。
なお **KataGo はコミが 0.5 刻みでないとクエリを拒否する**（16.4 で root が返らなかった）。

しかしバランスを取った状態でも正解手は選ばれない:

```
A5   -0.24   winrate 0.995   1561 visits   ← 選択された手
B4   +3.14   winrate 0.043      2 visits   ← アプリの正解手
```

飽和していれば「どちらでもいい」になるはずだが、KataGo は正解手 B4 を
**3.4目悪い勝率4%の負け手**と明確に否定している。つまり case B は飽和問題ではなく、
**枠つき局面の死活が元の詰碁と別物になっている**疑いが濃い。校正機能を作っても直らない。

### 3. 枠を張らなければ正解する

M10 ケースの認識盤面（枠なし・30子）にリージョンだけ掛けて測定:

| リージョン | 結果 |
|---|---|
| コアbbox+2（x5..12 y2..12） | M10 542 visits / **J3 688** ← 空き地の手が競合して負け |
| コアbbox+1（x6..12 y3..12） | **M10 1113** / H4 302 / G4 204 ← 正解 |
| さらにタイト（x7..12 y3..12） | **M10 1276** / H4 350 ← 正解 |

枠を一切張らず、リージョンを石群に寄せるだけで正解手が1位になる。
リージョンが緩いと空き地の手が競合するので、**pad の大きさが唯一の効くパラメータ**。

なお枠なしの root は +28.5目 / 勝率99.9% と完全に飽和しているが、それでも M10 が
目数で正しく1位になる。**手の順位は候補手どうしの目数差で決まり、盤全体の一定オフセットは
差に影響しない**ため、飽和そのものは順位付けを壊さない。
枠の目的のうち「詰碁の成否で勝敗を決める」は、順位付けには不要だった。

## アプローチ

採用: **枠を張らず、コアクラスタ bbox + pad をリージョンにする**。

不採用:

- **枠バランスのクローズドループ校正** — 上記1・2により成立しない
- **枠を残したまま pad だけ調整** — 枠が死活を変えている疑いが晴れず、故障モードが残る
- **リージョンを矩形でなく「コア石からの距離マスク」にする** — 空き地をさらに厳密に除ける
  が、`game.py` / `game_node.py` / `engine.py` / `badukpan.py` の4ファイルがリージョンを
  矩形前提で扱っており変更が大きい。pad=1 の矩形で実測上は足りているため YAGNI。
  検証で空き地の手が競合するようなら次の手として残す。

## 設計

### 1. 枠なしモードのフロー

```
認識グリッド → dense_core_bbox() → リージョン = コアbbox + pad（盤内クランプ）
             → grid_to_sgf(認識グリッドそのまま) → _do_new_game
             → set_region_of_interest → 2段解析（全盤fast → リージョン限定）
```

`tsumego_frame_board()` は呼ばない。枠石の生成・攻守判定・充填・コウダテ・非コア石削除は
一切走らないので、**盤面は認識結果と1子も違わない**。

`_do_tsumego_capture_apply` に分岐を入れ、リージョン設定と2段解析は既存の
`_apply_tsumego_region` をそのまま再利用する（座標変換も含め変更なし）。

### 2. コア検出の判定基準（新規 `dense_core_bbox`）

既存の `mark_core_stones` は「**枠が張れないときだけ**絞る」（`fit_margin` が `None` を
返すかで判定）。枠のない世界ではこの基準は意味を持たず、実際 M10 ケースでは絞らずに
全石 bbox（離れた D10 を含む）になってしまい、空き地の手が競合する。

枠なしモード用に独立した関数を新設する:

```
dense_core_bbox(stones) -> (imin, jmin, imax, jmax)
  gap を 1 から cluster_gap まで昇順に見て、
  最大クラスタが CORE_MIN_FRACTION(0.6) 以上の石を保持する最初の gap を採用し、
  そのクラスタの snap 済み bbox を返す。
  どの gap でも 60% に届かなければ全石の snap 済み bbox を返す。
```

密な詰碁本体は小さい gap で取れ、離れた石は落ちる。石が2路飛びに並ぶ緩い形は
gap=1 で分断されて60%を割るため gap=2 へ上がり、正しく1塊になる。
M10 ケースは gap=1 で 26/30（87%）を保持し、離れた D10 / F11 / F9 / G6 が落ちる。

既存の `mark_core_stones` は枠モード用にそのまま残す（枠なしモードからは呼ばない）。
辺スナップ（`snapped_bbox`）は流用する。詰碁が端に届いている場合に第一線を
リージョンへ含めるため、スナップは枠なしモードでも望ましい。

### 3. リージョン

`dense_core_bbox` の結果に pad を足し、盤内へクランプする。

- pad の既定値は **1**（実測でこの値が正解、2 だと空き地の手が競合する）
- 「正解手は石群のすぐ外側まで」という前提に基づく
- `tsumego_capture.region_pad` で設定可能にし、検証で調整できるようにする

リージョンが盤全体になる場合は `set_region_of_interest` が `None` に正規化するため、
リージョンなし＝全盤解析になる。これは詰碁が盤全体に広がっている場合であり、許容する。

### 4. 設定

`katrain/config.json` の `tsumego_capture` に2キー追加:

- `use_frame`（既定 `false`）— `true` で従来の枠モードに戻る
- `region_pad`（既定 `1`）— 枠なしモードのリージョン pad

`frame_margin` / `frame_ko` は枠モード用として残す。
**ユーザーのローカル設定 `C:\Users\iwaki\.katrain\config.json` にも同じキーを追加する**
（パッケージ側だけ更新するとGUIに出ない。この編集はメインセッションで直接行う）。

## 検証

### ユニットテスト

- `dense_core_bbox` が M10 ケースの盤面で 26子のクラスタを選び、bbox が `(0, 7, 8, 12)` になる
- `dense_core_bbox` が gap=1 で分断される緩い形では gap を上げて1塊にまとめる
- 枠なしモードの盤面が認識グリッドと完全一致する（1子も増減・変色しない）
- 枠なしモードのリージョン（pad=1）が M10 を含み、空き地の J3 を除外する
- `use_frame: true` で従来の枠モードの挙動が変わらない（既存テストが全て通ること）

### 実機検証

手元の問題群で枠あり／なしを A/B 比較する。特に既知の失敗ケース（case A の L1、case B の B4）で
枠なしがどう振る舞うかを確認する。case B で枠なしでも B4 が選ばれない場合、
**枠が死活を変えていたのではなく KataGo がアプリの正解に同意していない**ことが確定し、
別解の扱いという別問題に切り分けられる。

判定は上記「詰碁の正解判定ルール」に従う。AIが正解手と異なる手を打っても、
それが白を殺す／コウ・セキにするならアプリ側で正解になるため、
**「アプリが正解と判定したか」を成否の基準にする**（KataGo の最善手が正解手と一致したか、ではない）。

## 限界（既知・未解決）

- **囲みの保証がなくなる**: 枠は詰碁の外周石を無条件で生きた状態にしていた。枠なしでは
  外周が薄い問題で KataGo が詰碁を解かずに外周への反撃を選ぶ可能性が残る。
  兆候は「最善手が石群の外周ぎりぎりに出る」こと。当たった場合は対象石群の ownership を
  見る評価など別途検討が必要
- **コウダテがなくなる**: 枠はコウダテ形を配置していた。コウで決まる問題では
  結果が変わりうる
- **別解問題は解決しない**: 囲碁的に成立するがアプリの唯一解と異なる手が選ばれるケースは
  枠の有無と無関係に残る
- **飽和は残る**: root は勝率99.9%等に飽和したままだが、実測上は手の順位付けを壊さない

## 実機検証の結果と結論の訂正

**枠なしモードは実機の失敗ケースを直さなかった。既定は `use_frame: true`（枠モード）に戻した。**
枠なしのコードとテストは ownership 方式の土台として残す。

### 測定（枠なし・生盤面・リージョンは実装済みの frameless_region が算出）

| ケース | root scoreLead / 勝率 | 1位 | 正解手 |
|---|---|---|---|
| case B 枠なし | +37.72 / **1.000** | A5 (1630 visits) | B4 +1.84 (114) |
| case B 枠なし + komi 44.5 | +0.98 / 0.712 | A5 (1747) | B4 +1.23 (22) |
| case C 枠なし | −53.29 / **0.000** | J1 (1289) | H1 +2.24 (489) |
| case C 枠なし + komi −46.5 | +0.34 / 0.464 | **G7（リージョン角の空き地）** (1415) | H1 +4.22 (**2**) |

パイプライン自体は設計通り動作していた（リージョンは正しく算出され、正解手も選択手も圏内、
退化警告も出ていない）。

### 構造的ジレンマ（本設計の誤り）

- **飽和させると**（root が ±40〜50目・勝率0/1）詰碁の成否が勝敗に影響しないため、
  KataGo は死活を読む動機を持たない。候補手の目数差が 0.3〜2目に潰れ、正解手が埋もれる
- **バランスを取ると**（勝率0.5付近）今度はリージョン内に残る空き地の手が価値を持ち、
  詰碁と無関係な点が最善手になる（case C の G7 は 1415 visits、正解 H1 は 2 visits）

**枠はこの両方を同時に解いていた** — 盤を埋めて空き地を消し、かつバランスを取る。
つまり枠の2つの目的（空き地の除去とバランス調整）は設計として一貫しており、
本設計書が「2番目は順位付けには不要」と結論したのは **M10 の1ケースからの早すぎる一般化で誤りだった**。
枠なし＋リージョンだけではこのジレンマを解けない。

**追記（2026-07-30, case N）**: 枠が壊れていると判定されたときのフォールバック（追記9）としての
枠なしにも、この飽和が同じように出る。実測: 枠なし盤の root −75.1目・手番側コア −0.75/子で、
gain も目数も「相手の外側の石を攻める手」を首位に置き詰碁と無関係な手を打った（有効な枠なら
同じ選択則が正解する）。**枠なしは「枠より安全な出題」ではない**ので、枠を捨てる判断は
捨てる先を測ってから下す（`frame_over_frameless`。ownership spec 追記18）。

### case B について

komi を合わせて完全に非飽和（勝率0.712）にしても KataGo は A5 を選ぶ。case B は飽和でも枠でもなく、
**KataGo がアプリの正解に同意していない**ケース。ただし auto_ai_black は黒の全ての手を打つため、
初手 A5 は成立していて3手目以降で誤った可能性も残る（ユーザーに見える失敗は最終結果のみ）。

## 将来の方向性: 死活ステータスによる着手選択

本設計は「リージョンを絞って死活と無関係な手を候補から外す」ことで、KataGo の目的関数
（盤全体の目数）と正解判定の目的関数（局所の死活）を近づける。より直接的な方法として、
**目的関数そのものを死活に置き換える**案がある。

KataGo の解析クエリは `includeMovesOwnership` で**候補手ごとの ownership マップ**を返せる
（現在は `false`。実機ログで確認済み）。対象石群の点の ownership を見れば、
その手が石群を殺しているか・生かしているか・どちらでもない（コウ／セキ相当の中間値）かを
直接測れる。これを使えば:

- 盤全体の飽和と無関係に順位を付けられる
- 「殺す＞コウ・セキ＞生かす」という正解判定と同じ順序で手を選べる
- 死活に影響しない手（空き地の手）は ownership を動かさないので自動的に沈む

未解決の課題は**対象石群の同定**（どの石群が問題の対象かをどう決めるか）。
リージョン内で ownership が最も中間値に近い＝最も争われている連が候補になる。

**A/B の結果、この方向が本命になった。** 上記のジレンマは「盤全体の目数を目的関数にしている」ことに
起因するので、目的関数を対象石群の ownership に変えれば両側とも消える:

- 空き地の手は対象石群の ownership を動かさない → 自動的に沈む（case C の G7 問題が消える）
- コウ・セキは ownership の中間値として現れる → 「殺す ＞ コウ・セキ ＞ 生かす」の順序がそのまま出る
- 盤全体が飽和していても順位が付く

ただし **komi バランスは併用する価値がある**。飽和時（勝率0/1）は KataGo の探索自体が甘くなり、
ownership の推定精度も落ちるため。case C は非飽和（勝率0.464）にすると実際に探索が働いていた。
komi は盤面を一切変えない正確な線形ノブであることを実測済み（コミ26.5シフトで scoreLead が28.2動く。
KataGo はコミが0.5刻みでないとクエリを拒否する点に注意）。

枠なしモードはこの方向の前提条件（盤面がアプリと同一で ownership が元問題の死活を素直に反映する）
なので、コードは残す。

## 追記1（2026-08-05・case AG）: 正解手が枠の外に出る問題のための枠なしホットキー

### 症状

13路・ログ `tsumego_20260805_015813`。ユーザーが白の正解手 **M4** を打とうとしたが、そこに
**黒の枠石**があって着手できなかった。実際に打たれた手順は
`B L11, W L12, B M11, W L10, B N10, W K11, B N11, W N12, B N9, W L8, B M9, W M7, B K10,
W M6, B M5, W L5, B L6` で、白が **L8→M7→M6→L5 と下辺へ走っている**。その続きが M4。

### 原因

枠は「認識石の外接矩形 + margin」の**閉じた箱**で、`fit_margin` が枠外に守り側の代償地帯
`(盤面積 - komi - 5)/2` を要求する。この盤の実測:

```
認識石 bbox = 行6〜13 / 列G〜N（8行×7列）   必要な枠外面積 = (169 - 7 - 5)/2 = 78.5点
  margin=4: 内側=132点 外側=37点 -> NG
  margin=3: 内側=110点 外側=59点 -> NG
  margin=2: 内側= 90点 外側=79点 -> OK   ← 採用（設定は frame_margin=4）
```

つまり **枠の内側は盤の約半分が上限**で、設定の margin 4 は 2 に縮む。壁は認識石のわずか
2線外＝row 4 に来て、`put_border` が攻め方（黒）の色で敷くため M4 が黒石になる。

**「枠を広げる」方向では直せない**（margin 3 が構造的に不成立）。19路へ置き直しても、隅の
問題で伸びるのは2辺だけとはいえ内側上限 186点 に対し margin 6 止まりで、走り出す問題に
必要な長さは保証できない。

### 自動判定は却下（実測）

「対象が問題自身の石で囲われているか」＝ `extract_problem` の閉包判定を枠の可否シグナルに
使う案は、**直近30キャプチャ中25件（83%）で「閉じていない」と出る**ため使えない
（`_closure` は FRONTIER_LIBERTIES と FILL_CAP を課すので、空き地の多い13路では正常な問題でも
まず通らない）。これで枠を切り替えると正常な問題まで枠なしに落ちて正答率を壊す。

### 対処: `hotkey_noframe`（役割指定ホットキーと同じ発想）

役割（case X）と同じく、**確実に知っているのはアプリの解答手順を見ているユーザーだけ**なので
押し分けてもらう。実装は `capture_settings_for_frame_mode(settings, frameless)` 一点で、
枠なし指定が無ければ**設定オブジェクトをそのまま返す**＝既存3ホットキーの経路は不変。

- `hotkey_noframe`（パッケージ既定 `shift+ctrl+f4` / ユーザー設定 `ctrl+alt+v`）
- 枠なし時は `use_frame: false` に落とし、リージョンを **`noframe_region_pad`（既定3）** で取る。
  既定の `region_pad`(1) のままだと人間（白）は盤全体に打てる一方で **AI（黒）の候補が
  壁の内側（行5〜13）に留まる**ため、箱の外へ出た戦いを追えない。pad=3 なら 行3〜13/列D〜N で
  M4 を含む
- 枠なしでは壁の色が無いので `tsumego_solver_attacks` は None＝従来どおり役割非依存の挙動。
  よって役割指定との組合せは持たない（ホットキーは1つ）

頻度はユーザー報告で **約1000問キャプチャして初の事例**。既定を変えずエスケープハッチだけ
用意するのが費用対効果で正しい。
