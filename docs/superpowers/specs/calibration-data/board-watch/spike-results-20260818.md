## 「2枚の差が相手の1手ぶん」が NG だった理由

`--save tests/data/board_watch_after.png` を実行したのは `before` 実行から数分後（このスパイクの Step 2 と Step 3 の間にレポート作成・コーディネータとの往復が挟まった）。その間に盤は1手ではなく2手分（白の応手＋黒＝アプリAIの再応手）進んでいた:

- before: 黒1子（`grid[4][5]`）のみ。**棋譜表示バーに「1. 黒4-5」と表示されており**（after の「3. 黒6-6」と同じUI要素・同じ位置）、手数1は画面から直接読み取れる（石数からの推測ではない）
- after: 黒2子・白1子。棋譜表示「3. 黒6-6」＝3手目まで進行済み
- 新規セルは2つだけ（プログラムで diff 済み）:
  - `row=3 col=3`: `.` → `B`（3手目・黒・最終手マーカーあり＝**アプリAI(KaasanBot)の着手**）
  - `row=4 col=3`: `.` → `W`（2手目・白＝**人間(Sithle)の着手**）
- 取られた石はなし（`W` は2手目、盤上に残っている）
- **経過時間の直接証拠**: 画面左上の時計が before「22:12」→ after「22:14」、Sithle（白番・人間）の残り時間が before「02:43」→ after「00:57」と、いずれも両スクリーンショットの同じUI要素で確認できる。この時間差の間に人間の着手（2手目・白）とアプリAIの応手（3手目・黒）の両方が行われたと考えられる

これは「相手が1手だけ打った」を確認する狙いのペアとしては**成立していない**（コーディネータの事前指示どおり、石2個以上の差はそのまま正直に報告し、きれいな1手差ペアを捏造しない）。ただし認識器そのものの動作（rect/size/石分類/マーカー）は before・after の両方で独立に検証でき、どちらも問題なし。この2枚を Task 13 の回帰テストに使う場合は、**「1手ぶんの差」の回帰には使えない**（実際の差は2手ぶん）ことに注意。回帰テストとして有効に主張できるのは:
- 各キャプチャ単体の rect/size/grid が期待値と一致すること
- 最終手マーカーが乗った石が `.` に化けないこと（before の黒1子、after の黒3手目の両方で確認済み＝**黒マーカーのサンプルのみ**。白石にマーカーが乗るケースは今回のペアでは検証できていない）

## 判定

- [x] 既存の認識器がそのまま使える → Task 2 へ進む
- [ ] 最終手マーカーで石が "." に化ける → 設計どおり §2.5(c) の進捗ウォッチドッグが要る（Task 6 で実装）。
      加えて board_watch 専用の分類関数が必要かをここで判断する（**詰碁経路の関数は変更しない**）
- [ ] 盤が検出できない → 設計の前提が崩れる。ここで止めてユーザーと相談する

認識器（`find_window_rect` / `capture_screen_rect` / `detect_board` / `detect_size_and_classify`）は今回の対局アプリの盤面に対してそのまま通った。board rect・盤サイズ・石の分類・最終手マーカーの4項目すべて OK。Task 2 以降は既存認識器をそのまま使える前提で進めてよい。

**このペア（`board_watch_before.png` / `board_watch_after.png`）が回帰用に保証する範囲**:
- カバーする: 9路盤・黒石/白石混在・最終手マーカーつきの**黒石**が正しく `B` と読める・盤面の一部だけに石がある疎な局面
- カバーしない: 差分が「相手の応手ちょうど1手ぶん」であること（実際は2手ぶん進んでいる）／白石に最終手マーカーが乗るケース／盤上の石が密集した局面／取られた石があるケース（capture）／13路・19路盤

**追加の発見（設計上の注意点）**: このマッチアップ（vs `:KaasanBot`）では**アプリAIが黒番、人間(`Sithle`)が白番**だった。Task 2 以降で「アプリAIの着手を検出する」ロジックを組むときに色を固定で仮定しない（対局ごと、あるいはアプリ側のマッチメイキングで手番の色が入れ替わりうる）。今回は対局者アイコンの色（黒丸/白丸）と着手履歴バーの「黒/白」表記から色を判別した。

# 実機での通し確認（2026-08-19）

Task 14。KaTrain と BlueStacks を並べ、9路の実対局で確認した。

## 構成

| 項目 | 値 |
|---|---|
| アプリ側 | ユーザー=黒 / アプリ AI=白 |
| KaTrain 側 | 黒=AI（難解戦略）/ 白=人間 |
| 盤サイズ | 9路 |
| ホットキー | `ctrl+alt+b`（ユーザーのローカル設定。詰碁は ctrl+alt+z/x/c/v） |

対応関係は「**アプリ側 AI が打つ色を KaTrain では人間に設定する**」。アプリ AI の手が
KaTrain へ人間側の手として注入され、KaTrain の AI が生成した手をユーザーが手でアプリへタップする。

## 1回目: 対局開始で三者デッドロック（設計欠陥・修正済み）

新規対局同士で `ctrl+alt+b` を押しても、KaTrain の AI が初手を打たなかった。

ログ（`~/.katrain/logs/game_20260819_012616.log`）:

```
board_watch: アプリの局面（9路）を取り込みました（手番=W）
board_watch: 監視を開始しました
```

原因は spec §3.2 の「取り込み時の手番は人間側（アプリ AI の色）に固定する」という
**設計判断そのもの**。石数パリティで手番が決まらないこと（`b − w = cw − cb`）を根拠に
安全側へ倒したルールだが、**実際に KaTrain の AI の手番であるケースを構造的に到達不能に
していた**。空の9路盤が「手番=W（人間）」で取り込まれた結果:

- KaTrain: 白（人間）の着手待ち → 黒番の AI は打たない
- ユーザー: KaTrain の AI の手待ち
- アプリ AI: ユーザーの着手待ち

の三すくみ。20秒の停滞ウォッチドッグは作動するので無音ではないが、初手から使えない。

**修正**（`8e823f4` / `4f1de44`）: 石が1つも無い盤に限り手番は**黒**（囲碁のルール＝対局開始で
あり取りも起き得ないので、パリティの議論が不要）。石がある局面は従来どおり人間側に倒す。
判定は純関数 `board_watch.import_next_player(grid, human_color)` に切り出してテスト済み。

## 2回目: 修正後の通し

ユーザー確認: **問題なし**。新規対局同士で `ctrl+alt+b` → KaTrain の AI が初手を打ち、
それをアプリへタップ → アプリ AI の応手が KaTrain へ自動反映される、という一連の流れが動作した。

## 3回目: 相手の初手が乗った盤から始めると同じ膠着（設計欠陥・修正済み）

構成を入れ替えた対局（アプリ側: ユーザー=白 / アプリ AI=黒。KaTrain 側: 人間=黒 / AI=白＝難解（9路））で、
**アプリ AI が初手を打ってから**監視を ON にしたところ、KaTrain の白番 AI が2手目を打たなかった。

ログ（`~/.katrain/logs/game_20260819_112356.log`・全4行）:

```text
board_watch: アプリの局面（9路）を取り込みました（手番=B・人間側に固定）
Sending query QUERY:887: {... "initialStones": [["B", "F4"]], "initialPlayer": "B", "moves": [] ...}
board_watch: 監視を開始しました
[0.5][QUERY:887][done] KataGo analysis received: 81 candidate moves, 2020 visits
```

原因は1回目とまったく同じ「取り込み時の手番を人間側に倒す」ルール。1回目の修正が**空盤だけ**を
例外にしたため、盤に1子でも乗っていると同じ膠着に戻る（解析は完了しているのに `next_player.ai` が
偽で AI が呼ばれず、ウォッチャーは `InSync` を返し続ける）。

**修正**: 「**盤上2子以内なら取りが起き得ないので石数から手番が確定する**」へ一般化した
（空盤ルールはその特殊ケースとして吸収）。最初の取りは3手目より前には起こせず、その3手目の取りが
作る盤は 黒2子・白0子＝`b − w = 2` なのでガードから外れる。確定できるのは `(0,0)→黒` /
`(1,0)→白` / `(1,1)→黒` の3通り。3路・4路の合法手列を総当たり（深さ7/5）して確認済みで、
`tests/data/board_watch_before.png`（このスパイクで保存した「黒1子だけの9路」＝報告と同じ局面）
そのものも回帰に追加した。詳細は design §12。

## 残る限界（既知・仕様に明記）

**3子以上進んだ局面から監視を開始し、そのときたまたま KaTrain の AI の手番だった場合**は同じ膠着が起きる。
盤面1枚からは取られた石の数が分からないため手番を確定できない（これが上のパリティの議論そのもの）。
逃げ道は既存の `ai-move`（Enter / numpad-Enter、および GUI ボタン）で AI に1手打たせること。
停滞ウォッチドッグの警告文にもこの2つの原因を書いてある。
