# エンジン更新 A/B: KataGo v1.18.1 ＋ transformer b10c384 vs 現行 v1.16.4 ＋ b18（2026-09-04）

上流 KaTrain v1.19/v1.20 が同梱エンジンを KataGo v1.17.1→v1.18.1、同梱ネットを transformer `b10c384h6nbttflrs` に
替えたので、この fork（詰碁・難解が b18＋v1.16.4 の解析で校正されている）に同じ更新を入れてよいかを実測した。
**結論: 現時点では入れない。** 難解の尺度は保たれるが、詰碁 E2E の回帰点が 2 件（F2@4・AA@6）**3/3 で系統的に壊れ**、
どちらもネット（transformer）起因（エンジンだけ替えた対照 B′ は通る）。速度も手元の TensorRT 10.9.0 では現行より遅い。

## 0. 環境の確認（TensorRT の版）

| 項目 | 実測 |
|---|---|
| 現行エンジン | `~/.katrain/katago.exe` = KataGo **v1.16.4 TensorRT** backend（`katago version`） |
| TensorRT | **10.9.0**（`~/.katrain/nvinfer_10.dll` 群。trtcache 名 `trt-100900_…` = 10.9.0） |
| cuDNN | 8.9.7 の DLL も同居（未使用） |
| GPU / ドライバ | RTX 3080 / 591.86（CUDA 13.1 対応） |
| v1.18.1 の Windows TRT ビルド | `trt10.16.1-cuda13.2` / `trt10.2.0-cuda12.5` / **`trt10.9.0-cuda12.8`** |

手元の TRT 10.9.0 の DLL をそのまま使える **`katago-v1.18.1-trt10.9.0-cuda12.8-windows-x64.zip`** を採用した
（10.16.1 版は NVIDIA から TensorRT 10.16 を別途入れる必要がある）。KataGo 作者の注記「transformer では古い TRT は
CUDA＋cuDNN に負けることがある。TRT 10.16＋CUDA 13 を推奨」はこの構成に該当する。

## 1. 構成（切り替え可能なまま残してある）

- 新エンジン: `~/.katrain/katago-v1.18.1-trt/katago.exe`（zip 展開＋ `nvinfer*_10.dll` / `nvonnxparser_10.dll` を
  `~/.katrain/` からハードリンク。`version` で v1.18.1 TensorRT を確認）
- 新ネット: `~/.katrain/b10c384h6nbttflrs.bin.gz`（v1.17.1 リリースから 38MB）
- 腕の設定（ローカル config のコピーで engine.katago / engine.model だけ差し替え。humanSL モデル・解析 cfg は共通）:
  - **A** = `~/.katrain/config.json`（現行 v1.16.4 + b18）
  - **B** = `~/.katrain/config_ab_v1181_b10c384.json`（v1.18.1 + transformer b10c384）
  - **B′** = `~/.katrain/config_ab_v1181_b18.json`（v1.18.1 + b18＝エンジンだけ替えた対照）
- ハーネス改修: `generate_move_e2e.py` / `e2e_suite.py` に `--config=<path>`（既定は `~/.katrain/config.json`）。
  `katrain_debug` は元から `--config` を持つ
- **両腕が本当に別の設定で走ることの確認**（着手前に実施・`raw/verify_*.txt`）: E2E と同じ入口で
  `Starting KataGo with [...]` の exe / model が A=現行 exe＋b18、B=新 exe＋b10c384、B′=新 exe＋b18 と出ることを確認
- TensorRT プランの温め: transformer 約 50 秒、humanSL モデル（新 exe 用に再構築）約 60 秒。以後は timing cache で即起動
- スクリプト: `ab_prep.py`（温め＋ベンチ）→ `ab_run.py`（本番）→ `ab_cross_run.py`（交差評価・診断）→ `ab_e_run.py`（E 尺度）、
  集計 `ab_summarize.py` / `ab_e_summarize.py`。生出力は `raw/`

## 2. 速度（`katago benchmark -t 24 -v 3000`・解析 cfg・各 3 回の最終値）

| 構成 | visits/s | nnEvals/s |
|---|---|---|
| A: v1.16.4 TRT + b18 | **2307** | 1711 |
| B′: v1.18.1 TRT + b18 | 1845（−20%） | 1370 |
| B: v1.18.1 TRT + b10c384 | 1956（−15%） | 1452 |

v1.18.1 の TensorRT 経路は ONNX エミッタ経由に変わり、TRT 10.9.0 では同じ b18 でも 2 割遅い。transformer は
b18 より 1 visit あたり強いので「同 visits で質が上がる」方向だが、visits 自体は 15% 減る。
実務の所要（E2E 1 周 14.4 / 15.2 / 16.2 分、難解バッチ 2.2 / 2.1 / 2.2 分、難解の着手決定 0.73 / 0.65 / 0.75 秒）は
ほぼ同じ＝解析待ちより Python 側とクエリ発行が支配的。

## 3. 詰碁 E2E（`e2e_suite.py` 既定＝回帰点 29・各 3 repeats・別プロセス）

| case | A | B | B′ |
|---|---|---|---|
| F2@4 | PASS 3/3（M12） | **FAIL 0/3（J10 ×3）** | PASS 3/3（N11 1・M12 2） |
| AA@6 | PASS 3/3（N5） | **FAIL 0/3（N1 ×3）** | PASS 3/3（N5） |
| O@0 | PASS 3/3 | PART 2/3（C10 1） | PASS 3/3 |
| U@0 | PASS 3/3 | PASS 3/3 | PART 2/3（A3 1） |
| Z@0 | PART 1/3（N7 2） | PASS 3/3 | PART 1/3（M7 1・J5 1） |
| 他 24 点 | PASS | PASS | PASS |
| 合計 | 28/29 | **26/29** | 27/29 |

Z@0・U@0・O@0 は 1/3〜2/3 の run 間分散（既知の分散帯）。**F2@4 と AA@6 は B だけ 3/3 で外れ、B′ は通る＝ネット起因。**

### 3.1 F2@4（枠なし・正解 N11/M12）: root の value が違う

B の `--debug`（`raw/diag_B_F2at4.txt`）: 目数順 J11 pt+1.27 / M7 +1.27 / J10 +1.38 に対し **N11 pt+5.14（v79）・M12 +5.41（v63）で
gain も −3.4 / −3.7**。J10/J11/M7 は全部コウ経路 → コウ脱出で policy 上位 M12（p0.0018）・N11（p0.0017）を同深さで測るが
−0.58 / −0.49 /子でコウ経路と出て、「無条件で成立する手が無い」として J10 を維持。b18 では N11/M12 が救済経路で
拾われる（README の「N11/M12 はコイン投げ」）。transformer はこの局面の N11/M12 を 4 目悪いと読んでおり、閾値の際どさではない。

### 3.2 AA@6（正解 N5）: 応手 PV のコウ検出＋脱出先 N1 が ownership 判定を通る

E2E と同じ手順（ply 0,2,4,6 を同一プロセス）で再現（`raw/diag_B_AA_protocol.txt`・N1 1/1）: N5 は v1728/pt−0.38 で
対抗馬なしだが、**コウ経路検査が「応手 K1 の PV がリージョン内のコウ形に到達」と判定**し、コウ脱出が policy 上位 N1
（p0.219・root では v65/pt+16.33）を同深さ 800visits で測ると **+0.94/子＝成立** と出て N1 を採用。
ply 6 だけを新プロセスで回すと（`raw/diag_B_AAat6.txt`）K1 の PV にコウ形が無く N5（clean）を採用＝**同一プロセス内の
先行解析（NN キャッシュ）で PV が変わる**。b18 では 4 run とも clean。「PV を証拠にするコウ検出は探索依存」という
既知の弱点が、ネットを替えると別の局面で顔を出す例。

### 4.1 交差評価（審判エンジンを固定して両腕の r1 の選択手を測り直す・`ab_cross_eval.py`）

| g0823・50 手 | 審判 A（b18） | 審判 B（transformer） |
|---|---|---|
| A の選択手の平均損失 | 1.67 | 1.80 |
| B の選択手の平均損失 | 1.23 | 0.96 |
| 不一致 21 手だけ: A / B | 2.18 / 1.16 | 2.70 / 0.70 |

どちらの審判でも B の選択のほうが安い。ただし難解は「予算内で最も難解な手」を選ぶ設計で、勝勢では消費モードが
数目を意図的に払うので、**損失が小さい＝良い、ではない**（B の外し数がやや少ない＝予算を使い切っていない可能性）。
transformer は A の外しを b18 より 1 目ほど高く見積もる（不一致手で 2.18→2.70）。

### 4.2 E 尺度（`ab_enigma_e.py`・同じ 50 局面で戦略を走らせ Score 行を採取）

|---|---|---|---|

## 5. 判断

- **詰碁**: 回帰 29 点のうち 2 点が系統的に壊れる（回復は分散帯の Z@0 1 点）。原因は (a) root value の食い違い（F2）、
  (b) 応手 PV のコウ検出と脱出先の ownership 判定（AA）で、どちらも閾値の際どさではなく**ネットの読みそのもの**。
  導入するなら詰碁パイプライン（`.claude/rules/tsumego-parameters.md` の各閾値・E2E の期待値）の再校正が前提。
  CLAUDE.md の原則どおり「回復側」だけでなく「破損側」を数えた結果、差引は **−1 点（回復 1・破損 2）**。
- **難解**: E 尺度・外し率・所要はほぼ不変。実戦での E 較正（実損失 ≈ 1.06×E・memory `project_enigma_e_calibration`）は
  実対局でしか測れないので未確認だが、オフラインで見る限り再校正の必要は薄い。
- **速度**: 手元の TRT 10.9.0 では現行より遅い（−15〜20%）。速度目的なら TensorRT 10.16＋CUDA 13 の導入
  （`trt10.16.1-cuda13.2` ビルド）か CUDA＋cuDNN 9.x ビルドに替えてから測り直す必要がある。
- **上流の狙い**（1 visit あたりの強さ・対応ハードの拡大）はこの fork の用途（校正済み閾値の上で走る詰碁と難解）とは
  噛み合わない。**現行 v1.16.4＋b18 を維持**し、エンジン更新は詰碁の再校正を引き受けるときに別件として扱う。

## 6. 再現手順

```
python docs/superpowers/specs/calibration-data/engine-ab/ab_prep.py        # 温め＋ベンチ（prep.log）
python docs/superpowers/specs/calibration-data/engine-ab/ab_run.py         # 腕の確認 → E2E A/B → 難解バッチ → B′（run.log・約 70 分）

python docs/superpowers/specs/calibration-data/engine-ab/ab_e_run.py       # E 尺度（e.log）
python docs/superpowers/specs/calibration-data/engine-ab/ab_summarize.py <out_dir>
python docs/superpowers/specs/calibration-data/engine-ab/ab_e_summarize.py out/e_A_g0823.json out/e_B_g0823.json out/e_B2_g0823.json
```

スクリプトは `AB = 自分のディレクトリ`・`OUT = AB/out` を前提にし、20 分超のジョブは `Start-Process` で切り離して
ログを `tail -F` で監視した（memory `project_long_katago_runs_orchestration`）。GPU を共有するので腕は直列に回す。
