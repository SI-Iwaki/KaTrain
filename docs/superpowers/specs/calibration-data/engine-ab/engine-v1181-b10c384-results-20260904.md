# エンジン更新 A/B: KataGo v1.18.1 ＋ transformer b10c384 vs 現行 v1.16.4 ＋ b18（2026-09-04）

上流 KaTrain v1.19/v1.20 が同梱エンジンを KataGo v1.17.1→v1.18.1、同梱ネットを transformer `b10c384h6nbttflrs` に
替えたので、この fork（詰碁・難解が b18＋v1.16.4 の解析で校正されている）に同じ更新を入れてよいかを実測した。
**結論: 現時点では入れない。** 難解の尺度は保たれるが、詰碁 E2E の回帰点が 2 件（F2@4・AA@6）**3/3 で系統的に壊れ**、
どちらもネット（transformer）起因（エンジンだけ替えた対照 B′ は通る）。速度も手元の TensorRT 10.9.0 では現行より遅い。

## 0. 環境の確認（TensorRT の版）

| 項目 | 実測 |
|---|---|
| 現行エンジン | `~/.katrain/katago.exe` = KataGo **v1.16.4 TensorRT** backend（`katago version`） |
| TensorRT | **10.9.0**（`~/.katrain/nvinfer_10.dll` 群。trtcache 名 `trt-100900_…` = 10.9.0） |
| cuDNN | 8.9.7 の DLL も同居（未使用） |
| GPU / ドライバ | RTX 3080 / 591.86（CUDA 13.1 対応） |
| v1.18.1 の Windows TRT ビルド | `trt10.16.1-cuda13.2` / `trt10.2.0-cuda12.5` / **`trt10.9.0-cuda12.8`** |

手元の TRT 10.9.0 の DLL をそのまま使える **`katago-v1.18.1-trt10.9.0-cuda12.8-windows-x64.zip`** を採用した
（10.16.1 版は NVIDIA から TensorRT 10.16 を別途入れる必要がある）。KataGo 作者の注記「transformer では古い TRT は
CUDA＋cuDNN に負けることがある。TRT 10.16＋CUDA 13 を推奨」はこの構成に該当する。

| 合計 | 28/29 | **26/29** | 27/29 |

Z@0・U@0・O@0 は 1/3〜2/3 の run 間分散（既知の分散帯）。**F2@4 と AA@6 は B だけ 3/3 で外れ、B′ は通る＝ネット起因。**

### 3.1 F2@4（枠なし・正解 N11/M12）: root の value が違う

B の `--debug`（`raw/diag_B_F2at4.txt`）: 目数順 J11 pt+1.27 / M7 +1.27 / J10 +1.38 に対し **N11 pt+5.14（v79）・M12 +5.41（v63）で
gain も −3.4 / −3.7**。J10/J11/M7 は全部コウ経路 → コウ脱出で policy 上位 M12（p0.0018）・N11（p0.0017）を同深さで測るが
−0.58 / −0.49 /子でコウ経路と出て、「無条件で成立する手が無い」として J10 を維持。b18 では N11/M12 が救済経路で
拾われる（README の「N11/M12 はコイン投げ」）。transformer はこの局面の N11/M12 を 4 目悪いと読んでおり、閾値の際どさではない。

### 3.2 AA@6（正解 N5）: 応手 PV のコウ検出＋脱出先 N1 が ownership 判定を通る

E2E と同じ手順（ply 0,2,4,6 を同一プロセス）で再現（`raw/diag_B_AA_protocol.txt`・N1 1/1）: N5 は v1728/pt−0.38 で
対抗馬なしだが、**コウ経路検査が「応手 K1 の PV がリージョン内のコウ形に到達」と判定**し、コウ脱出が policy 上位 N1
（p0.219・root では v65/pt+16.33）を同深さ 800visits で測ると **+0.94/子＝成立** と出て N1 を採用。
ply 6 だけを新プロセスで回すと（`raw/diag_B_AAat6.txt`）K1 の PV にコウ形が無く N5（clean）を採用＝**同一プロセス内の
先行解析（NN キャッシュ）で PV が変わる**。b18 では 4 run とも clean。「PV を証拠にするコウ検出は探索依存」という
既知の弱点が、ネットを替えると別の局面で顔を出す例。

## 5. 判断

- **詰碁**: 回帰 29 点のうち 2 点が系統的に壊れる（回復は分散帯の Z@0 1 点）。原因は (a) root value の食い違い（F2）、
  (b) 応手 PV のコウ検出と脱出先の ownership 判定（AA）で、どちらも閾値の際どさではなく**ネットの読みそのもの**。
  導入するなら詰碁パイプライン（`.claude/rules/tsumego-parameters.md` の各閾値・E2E の期待値）の再校正が前提。
  CLAUDE.md の原則どおり「回復側」だけでなく「破損側」を数えた結果、差引は **−1 点（回復 1・破損 2）**。
- **難解**: E 尺度・外し率・所要はほぼ不変。実戦での E 較正（実損失 ≈ 1.06×E・memory `project_enigma_e_calibration`）は
  実対局でしか測れないので未確認だが、オフラインで見る限り再校正の必要は薄い。
- **速度**: 手元の TRT 10.9.0 では現行より遅い（−15〜20%）が、**CUDA 13.2＋cuDNN 9.24 なら transformer で現行比 +34〜54%**
  （§2 追記）。速度だけならエンジンを CUDA 版 v1.18.2 に替える価値はある。ただし詰碁の 2 件はネット起因なので
  transformer を使う限り残る。**b18 のまま速度を保つなら v1.18.1＋TRT 10.16（D′ 2284〜2675 ≈ 現行 2307）が最良**、
  CUDA 版＋b18（C′ 1719〜1962）は現行より遅い。transformer なら CUDA 版 v1.18.2（C）が最速。
- **上流の狙い**（1 visit あたりの強さ・対応ハードの拡大）はこの fork の用途（校正済み閾値の上で走る詰碁と難解）とは
  噛み合わない。**現行 v1.16.4＋b18 を維持**し、エンジン更新は詰碁の再校正を引き受けるときに別件として扱う。

## 7. 採用（同日・ユーザー判断）

速度と解析精度を優先し、**本番を v1.18.2 CUDA 13.2＋cuDNN 9.24＋transformer b10c384（腕 C）に切替**（`~/.katrain/config.json` の
engine.katago / engine.model。旧設定は `config.json.bak-20260904-pre-cuda`）。詰碁の F2@4・AA@6 はこのネットで壊れる既知事項として
残し、再校正は別件。切替前の理解合わせ: 「TRT 10.16＋b18」はネットが同じで評価不変・速度 ±0〜+16%、「CUDA＋transformer」は
解析 +34〜54%・1 visit あたりの強さも上、AI の着手時間は Python 側が支配的でどちらも僅差。力戦派・持碁など他戦略の閾値も
b18 の評価で決めたものなので挙動が少し変わりうる（難解だけ E 尺度不変を確認済み）。

切替後の本番設定でのベースライン（`raw/e2e_C.txt`・CUDA 版＋transformer・3 repeats）: **26/29 PASS**、F2@4 0/3（J10）・AA@6 0/3（N1）・
O@0 1/3（C10 2）。O@0 は B で 2/3、C で 1/3＝transformer 2 腕の合計 3/6 に対し b18 3 腕は 9/9 なので、これも
ネット起因で落ちやすくなった回帰点として扱う（A11 は root の value が壊れていて policy 経由で拾う case O の性質上、
ネットの policy 分布の違いがそのまま出る）。GUI 起動も確認（`raw/gui_smoke.png`・KataGo engine ready・候補手表示）。

## 8. 詰碁の再校正（2026-09-04・切替後）

### 8.1 広い母集団での実測: 回答帳リプレイ 538 手順（20260815b と同じ手順集合・1 run・新エンジン＝`answer-book-replay-20260904-transformer.jsonl`）

- 正答 **320 → 302 / 538**（−18・−3.3pt）。対ごとの内訳: 両方正解 260 / 両方不正解 176 / **破損 60**（b18 正解→transformer 不正解）/ **回復 42**。
- 同一コードの run 間シャッフル（memory: 回復 23〜29 / 破損 23）より両方向とも大きい＝ネットが違うぶん決定が入れ替わる手番が増えた。差引 −18 はシャッフル幅（±5 程度）の 3 倍。
- 破損 60 を**新規プロセス 2 run**（＋sweep の 1 run）で再測: **3/3 不正解 42** / 混在 16 / sweep だけが外れ 2。
- 機構別の失敗率はどれも大きく動かない（gain 165→177 / solver 23→26 / 格上げ 10→16（発火 25→29）/ 脱出 15→11（発火 29→22））＝**壊れた機構は無く、拡散した揺れ**。
- 破損の型: 目数同着に近い（|Δpt|<=0.5・両者 v>=100）22 / root が別の手を明確に選好 20 / その他 12 / 格上げ・脱出 4 / 未読 2。回復側も同じ構成。
- **gain による最多 visits 手の覆し**（decider=gain・chosen が visits 1 位でない）: b18 は help 57 / HURT 36（差引 +21）、transformer は help 58 / HURT 48（差引 +10）＝この機構の純益が半減。

### 8.2 E2E 回帰点 3 件の原因（切替後の本番設定で再現・プローブ）

- **AA@6（正解 N5・誤答 N1）**: 正解 N5 の応手 K1 の PV が **K4（着手前からアタリの白 K5 を取る後始末）**でコウ形になり N5 がコウ経路に化ける
  → コウ脱出が policy 上位 N1 を同深さ 800visits・ud12 で測ると +0.94/子（白全滅）＝採用。全盤 3000visits（拘束なし）では
  N1 の白は +0.29/子＝生き・N5 比 −16 目（PV: K1 N5 N2 C10…＝白が K1 でアタリを絡めて 5 子を取り返す）。拘束 ud12 だと白のコウダテが
  取り上げられて N1 でも「白全滅」に出る＝脱出の成立判定が「コウに勝った前提」の値を見ていた（既知の非対称性）。**b18 では K1 の PV が

### 8.3 改修: PV コウ検出で「打つ側が着手前から打てたコウ」を候補の性質と数えない（判定のみ・解析不変）

`tsumego_pv_reaches_region_ko` の判定1（PV が 1 子取りコウ形に到達）は、守り方側の判定2 が持つ「候補手より前から打てたコウは

### 8.5 閾値の再校正は不要（反実仮想）

gain 覆し（decider=gain・chosen が visits 最多手でない）97 手順を `--debug` で撮り直し、`gain順`/`目数順` の値から

| `points_epsilon` | 0.25（現行） | 0.5 | 0.75 | 1.0 | 1.5 | 3.0 |
|---|---|---|---|---|---|---|

最良でも差引 +4（1437 判断中）＝run 間シャッフル（±25 手順）の内側なので、**閾値は動かさない**。transformer で増えた
